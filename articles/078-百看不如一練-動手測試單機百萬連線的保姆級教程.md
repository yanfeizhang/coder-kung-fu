### 一、TCP 併發理論基礎

在做這個實驗之前，需要你具備一些理論基礎。這些在之前的文章都單獨詳細講過，這裡我把它們都簡單再概括一下。

1.1 伺服器理論最大併發數

TCP連線四元組是由源IP地址、源埠、目的IP地址和目的埠構成。

當四元組中任意一個元素髮生了改變，那麼就代表的是一條完全不同的新連線。

我們算下伺服器上理論上能達成的最高併發數量。拿我們常用的 Nginx 舉例，假設它的 IP 是 A，埠80。這樣就只剩下源IP地址、源埠是可變的。

IP 地址是一個 32 位的整數，所以源 IP 最大有 2 的 32 次方這麼多個。 埠是一個 16 位的整數，所以埠的數量就是 2 的 16 次方。

2 的 32 次方（ip數）× 2的 16 次方（port數）大約等於兩百多萬億。

所以理論上，我們每個 server 可以接收的連線上限就是兩百多萬億。（不過每條 TCP 連線都會消耗伺服器記憶體，實踐中絕不可能達到這個理論數字，稍後我們就能看到。）

1.2 客戶端理論最大併發數

> 注意：這裡的客戶端是一個角色，並不具體指的是哪臺機器。當你的 java/c/go 程式響應使用者請求的時候，它是服務端。當它訪問 redis/mysql 的時候，你這臺機器就變成客戶端角色了。這裡假設我們一臺機器只用來當客戶端角色。

我們再算一下客戶端的最大併發數的上限。

很多同學認為一臺 Linux 客戶端最多隻能發起 64 k 條 TCP 連線。因為TCP 協議規定的埠數量有 65535 個，但是一般的系統裡 1024 以下的埠都是保留的，所以沒法用。可用的大約就是 64 k 個。

但實際上客戶端可以發出的連線遠遠不止這個數。咱們看看以下兩種情況

情況1：這個 64 k 的埠號實際上說的是一個 ip 下的可用埠號數量。而一臺 Linux 機器上是可以配置多個 IP 的。假如配置了 20 個 IP，那這樣一臺客戶端機就可以發起 120 萬多個 TCP 連線了。

情況2：再退一步講，假定一臺 Linux 上確實只有一個 IP，那它就只能發起 64 k 條連線了嗎？ 其實也不是的。

根據四元組的理論，只要伺服器的 IP 或者埠不一樣，即使客戶端的 IP 和埠是一樣的。這個四元組也是屬於一條完全不同的新連線。

比如下面的兩條連線裡，雖然客戶端的 IP 和埠完全一樣，但由於伺服器側的埠不同，所以仍然是兩條不同的連線。

- 連線1：客戶端IP 10000 伺服器IP 10000

- 連線2：客戶端IP 10000 伺服器IP 20000

所以一臺客戶端機器理論併發最大數是一個比伺服器的兩百萬億更大的一個天文數字（因為四元組裡每一個元素都能變）。這裡就不展開計算了，因為已經沒有意義了。

1.3 Linux 最大檔案描述符限制

linux 下一切皆檔案，包括 socket。所以每當程序開啟一個 socket 時候，核心實際上都會建立包括 file 在內的幾個核心物件。該程序如果開啟了兩個 socket，那麼它的核心物件結構如下圖。

程序開啟檔案時消耗核心物件，換一句直白的話就是開啟檔案物件吃記憶體。所以linux系統出於安全形度的考慮，在多個位置都限制了可開啟的檔案描述符的數量，包括系統級、程序級、使用者程序級。

- fs.file-max： 當前系統可開啟的最大數量

- fs.nr_open： 當前系統單個程序可開啟的最大數量

- nofile： 每個使用者的程序可開啟的最大數量

本文的實驗要涉及對以上引數的修改。

1.4 TCP 連線的記憶體開銷

介紹記憶體開銷之前，需要先理解核心的記憶體使用方式。只有理解了這個，才能深刻理解 TCP 連線的記憶體開銷。

Linux 核心和應用程式使用的是完全不同的兩套機制。 Linux 給它的核心物件分配使用 SLAB 的方式。

一個 slab 一般由一個或者多個 Page 組成（每個 Page 一般為 4 KB）。在一個 slab 內只分配特定大小、甚至是特定的物件。這樣當一個物件釋放記憶體後，另一個同類物件可以直接使用這塊記憶體。透過這種辦法極大地降低了碎片發生的機率。

Linux 提供了 slabtop 命令來按照佔用記憶體從大往小進行排列，這對我們檢視核心物件的記憶體開銷非常方便。

在 Linux 3.10.0 版本中，建立一個socket 需要消耗 densty、flip、sock_inode_cache、TCP 四個核心物件。這些物件加起來總共需要消耗大約 3 KB 多一點的記憶體。

> 如果連線上有資料收發的話，還需要消耗傳送、接收快取區。這兩個快取區佔用記憶體影響因素比較多，既受收發資料的大小，也受 tcp_rmem、tcp_wmem 等核心引數，還取決於伺服器程序能否及時接收（及時接收的話快取區就能回收）。總之影響因素比較多，不同業務之間實際情況差別太大，比較複雜。所以不在本文討論範圍之內。

### 二、方案一，多 IP 客戶端發起百萬連線

瞭解了理論基礎後，可以開始準備實驗了。

本文實驗需要準備兩臺機器。一臺作為客戶端，另一臺作為伺服器。如果你選用的是 c 或者 php 原始碼，這兩臺機器記憶體只要大於 4GB 就可以。 如果使用的是 Java 原始碼，記憶體要大於 6 GB。對 cpu 配置無要求，哪怕只有 1 個核都夠用。

本方案中採用的方法是在一臺客戶端機器上配置多個 ip 的方式來發起所有的 tcp 連線請求。所以需要為你的客戶端準備 20 個 IP，而且要確保這些 IP 在內網環境中沒有被其它機器使用。如果實在選不出這些 IP，那麼可以直接跳到方案 2。

> 除了用 20 個 IP 以外，也可以使用 20 臺客戶端。每個客戶端發起 5 萬個連線同時來連線這一個server。但是這個方法實際操作起來太困難了。

客戶端機和伺服器分別下載原始碼：[https://github.com/yanfeizhang/coder-kung-fu/tree/main/tests/network/test02](https://github.com/yanfeizhang/coder-kung-fu/tree/main/tests/network/test02)

下面我們來詳細看每一個實驗步驟。

2.1 調整客戶端可用埠範圍

預設情況下，Linux 只開啟了 3 萬多個可用埠。但我們今天的實驗裡，客戶端一個程序要達到 5 萬的併發。所以，埠範圍的核心引數需要修改。

```
#vi /etc/sysctl.conf
net.ipv4.ip_local_port_range = 5000 65000
```

執行 sysctl -p 使之生效。

2.2 調整客戶端最大可開啟檔案數

我們要測試百萬併發，所以客戶端的系統級引數 fs.file-max 需要加大到 100 萬。另外 Linux 上還會存在一些其它的程序要使用檔案，所以我們需要多打一些餘量出來，直接設定到 110 萬。

對於程序級引數 fs.nr_open 來說，因為我們開啟 20 個程序來測，所以它設定到 60000 就夠了。這些都在 /etc/sysctl.conf 中修改。

```
#vi /etc/sysctl.conf
fs.file-max=1100000
fs.nr_open=60000
```

sysctl -p 使得設定生效。並使用 sysctl -a 檢視是否真正 work。

```
#sysctl -p
#sysctl -a
fs.file-max = 1100000
fs.nr_open = 60000
```

接著再加大使用者程序的最大可開啟檔案數量限制（nofile）。這兩個是使用者程序級的，可以按不同的使用者來區分配置。 這裡為了簡單，就直接配置成所有使用者 * 了。每個程序最大開到 5 萬個檔案數就夠了。同樣預留一點餘地，所以設定成 55000。 這些是在 /etc/security/limits.conf 檔案中修改。

> 注意 hard nofile 一定要比 fs.nr_open 要小，否則可能導致使用者無法登陸。

```
# vi /etc/security/limits.conf
*  soft  nofile  55000
*  hard  nofile  55000
```

配置完後，開個新控制檯即可生效。 使用 ulimit 命令校驗是否生效成功。

```
#ulimit -n
55000
```

2.3 伺服器最大可開啟檔案控制代碼調整

伺服器系統級引數 fs.file-max 也直接設定成 110 萬。 另外由於這個方案中伺服器是用單程序來接收客戶端所有的連線的，所以程序級引數 fs.nr_open， 也一起改成 110 萬。

```
#vi /etc/sysctl.conf
fs.file-max=1100000
fs.nr_open=1100000
```

sysctl -p 使得設定生效。並使用 sysctl -a 驗證是否真正生效。

接著再加大使用者程序的最大可開啟檔案數量限制（nofile），也需要設定到 100 萬以上。

```
# vi /etc/security/limits.conf
*  soft  nofile  1010000
*  hard  nofile  1010000
```

配置完後，開個新控制檯即可生效。 使用 ulimit 命令校驗是否成功生效。

2.4 為客戶端配置額外 20 個 IP

假設可用的 ip 分別是 CIP1，CIP2，......，CIP20，你也知道你的子網掩碼。

> 注意：這 20 個 ip 必須不能和區域網的其它機器衝突，否則會影響這些機器的正常網路包的收發。

在客戶端機器上下載的原始碼目錄 test02 中，找到你喜歡用的語言，進入到目錄中找到 tool.sh。修改該 shell 檔案，把 IPS 和 NETMASK 都改成你真正要用的。

為了確保區域網內沒有這些 ip，最好先執行程式碼中提供的一個小工具來驗證一下

```
make ping
```

當所有的 ip 的 ping 結果均為 false 時，進行下一步真正配置 ip 並啟動網絡卡。

```
make ifup
```

使用 ifconfig 命令檢視 ip 是否配置成功。

```
#ifconfig
eth0
eth0:0
eth0:1
...
eth:19
```

2.5 開始實驗

ip 配置完成後，可以開始實驗了。

在服務端中的 tool.sh 中可以設定伺服器監聽的埠，預設是 8090。啟動 server

```
make run-srv
```

使用 netstat 命令確保 server 監聽成功。

```
netstat -nlt | grep 8090
tcp  0   0.0.0.0:8090  0.0.0.0:*  LISTEN
```

在客戶端的 tool.sh 中設定好伺服器的 ip 和埠。然後開始連線

```
make run-cli
```

同時，另啟一個控制檯。使用 watch 命令來實時觀測 ESTABLISH 狀態連線的數量。

實驗過程中不會一帆風順，可能會有各種意外情況發生。這個實驗我前前後後至少花了有一週時間，所以你也不要第一次不成功就氣餒。 遇到問題根據錯誤提示看下是哪裡不對。然後調整一下，重新做就是了。 重做的時候需要重啟客戶端和伺服器。

對於客戶端，殺掉所有的客戶端程序的方式是

```
make stop-cli
```

對於伺服器來說由於是單程序的，所以直接 ctrl + c 就可以終止伺服器程序了。 如果重啟發現埠被佔用，那是因為作業系統還沒有回收，等一會兒再啟動 server 就行。

當你發現連線數量超過 100 萬的時候，你的實驗就成功了。

```
watch "ss -ant | grep ESTABLISH"
1000013
```

這個時候別忘了檢視一下你的服務端、客戶端的記憶體開銷。

先用 cat proc/meminfo 檢視，重點看 slab 記憶體開銷。

```
$ cat /proc/meminfo
MemTotal:        3922956 kB
MemFree:           96652 kB
MemAvailable:       6448 kB
Buffers:           44396 kB
......
Slab:          3241244KB kB
```

再用 slabtop 檢視一下核心都是分配了哪些核心物件，它們每個的大小各自是多少。

如果發現你的核心物件和上圖不同，也不用驚慌。因為不同版本的 Linux 核心使用的核心物件名稱和數量可能會有些許差異。

2.6 結束實驗

實驗結束的時候，伺服器程序直接 ctrl + c 取消執行就可以。客戶端由於是多程序的，可能需要手工關閉一下。

```
make stop-cli
```

最後記得取消為實驗臨時配置的新 ip

```
make ifdown
```

### 三、方案二，單 IP 客戶端發起百萬連線

如果不糾結於非得讓一個 Server 程序達成百萬連線，只要是 Linux 伺服器上總共能達到就行，那麼就還有另外一個方法。

那就是在伺服器端的 Linux 上開啟多個 server，每個 server 都監聽不同的埠。然後在客戶端也啟動多個程序來連線。每一個客戶端程序都連線不同的 server 埠。客戶端上發起連線時只要不呼叫 bind，那麼一個特定的埠是可以在不同的 server 之間複用的。

同樣，實驗原始碼也有 c、java、php 三個語言的版本。
準備好兩臺機器。一臺作為客戶端，另一臺作為伺服器。分別下載如下原始碼：

[https://github.com/yanfeizhang/coder-kung-fu/tree/main/tests/network/test03](https://github.com/yanfeizhang/coder-kung-fu/tree/main/tests/network/test03)

3.1 調整可用埠範圍

同方案一，客戶端機埠範圍的核心引數也是需要修改的。

```
#vi /etc/sysctl.conf
net.ipv4.ip_local_port_range = 5000 65000
```

執行 sysctl -p 使之生效。

3.2 客戶端加大最大可開啟檔案數

同方案一，客戶端的 fs.file-max 也需要加大到 110 萬。程序級的引數 fs.nr_open 設定到 60000。

```
#vi /etc/sysctl.conf
fs.file-max=1100000
fs.nr_open=60000
```

sysctl -p 使得設定生效。並使用 sysctl -a 檢視是否真正生效

客戶端的 nofile 設定成 55000

```
# vi /etc/security/limits.conf
*  soft  nofile  55000
*  hard  nofile  55000
```

配置完後，開個新控制檯即可生效。

3.3 伺服器最大可開啟檔案控制代碼調整

同方案一，調整伺服器最大可開啟檔案數。不過方案二服務端是分了 20 個程序，所以 fs.nr_open 改成 60000 就足夠了。

```
#vi /etc/sysctl.conf
fs.file-max=1100000
fs.nr_open=60000
```

sysctl -p 使得設定生效。並使用 sysctl -a 驗證。

接著再加大使用者程序的最大可開啟檔案數量限制（nofile），這個也是 55000。

```
# vi /etc/security/limits.conf
*  soft  nofile  55000
*  hard  nofile  55000
```

> 再次提醒： hard nofile 一定要比 fs.nr_open 要小，否則可能導致使用者無法登陸。

配置完後，開個新控制檯即可生效。

3.4 開始實驗

啟動 server

```
make run-srv
```

使用 netstat 命令確保 server 監聽成功。

```
netstat -nlt | grep 8090
tcp  0  0  0.0.0.0:8100  0.0.0.0:*  LISTEN
tcp  0  0  0.0.0.0:8101  0.0.0.0:*  LISTEN
......
tcp  0  0  0.0.0.0:8119  0.0.0.0:*  LISTEN
```

回到客戶端機器，修改 tool.sh 中的伺服器 ip。埠會自動從 tool.sh 中載入。然後開始連線

```
make run-cli
```

同時，另啟一個控制檯。使用 watch 命令來實時觀測 ESTABLISH 狀態連線的數量。

期間如果做失敗了，需要重新開始的話，那需要先殺掉所有的程序。在客戶端執行`make stop-cli`，在伺服器端是執行`make stop-srv`。重新執行上述步驟。

當你發現連線數量超過 100 萬的時候，你的實驗就成功了。

```
watch "ss -ant | grep ESTABLISH"
1000013
```

記得檢視同樣一下你的服務端、客戶端的記憶體開銷。

```
# cat /etc/redhat-release
Red Hat Enterprise Linux Server release 6.2 (Santiago)

# ss -ant | grep ESTAB |wc -l
1000013

# cat /proc/meminfo
MemTotal:        3925408 kB
MemFree:           97748 kB
Buffers:           35412 kB
Cached:           119600 kB
......
Slab:            3241528 kB
```

再用 slabtop 檢視一下 top 核心物件。

實驗結束的時候，記得`make stop-cli`結束所有客戶端程序，`make stop-srv`結束所有伺服器程序。

### 最後，多扯一點

經過網路篇這幾篇文章的學習，相信大家已經不會再覺得百萬併發有多麼的高深了。併發只是描述伺服器端程式的指標之一，並不是全部

一條不活躍的 TCP 連線開銷僅僅只是 3 KB 多點的記憶體而已。現代的一臺伺服器都上百 GB 的記憶體，如果只是說併發，單機千萬（C10000K）都可以。

在網際網路伺服器端應用場景裡，除了一些基於長連線的 push 場景以外。其它的大部分業務裡討論併發都要和業務結合起來。拋開業務邏輯單純地說併發多高其實並沒有太大的意義。 因為在這些場景中，伺服器開銷大頭往往都不是連線本身，而是在每條連線上的資料收發、以及請求業務邏輯處理。

這就好比你作為一個開發同學，在公司內建立了和十個產品經理的業務聯絡。這並不代表你的併發能力真的能達到十，很有可能是一位產品的需求就能把你的時間打滿。

另外就是不同的業務之間，單純比較併發也不一定有意義。

假設同樣的伺服器配置，A 業務的單機能支撐 1 萬併發，B 業務只能撐 1 千。這也並不一定就說明 A 業務的效能比 B 業務好。因為 B 業務的請求處理邏輯可能是相當的複雜，比如要進行復雜的壓縮、加解密。而 A 業務的處理很簡單記憶體讀取個變數就返回了。

擴充套件說一下，本文配套程式碼中僅僅只是作為測試使用，所以寫的比較簡單。是直接阻塞式地 accept，將接收過來的新連線也雪藏了起來，並沒有讀寫發生。

如果在你的專案實踐中真的確實需要百萬條 TCP 連線，那麼一般來說還需要高效的 IO 事件管理。在 c 語言中，就是直接用 epoll 系列的函式來管理。對於 Java 語言來說，就是 NIO。（Golang 中不用操心，net 包中把 IO 事件管理都已經封裝好了）
