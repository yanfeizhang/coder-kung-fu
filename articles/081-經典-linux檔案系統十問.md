## 一、磁碟構成及分割槽

## 1、磁碟實體結構

還是先從最基本的磁碟實體結構說起吧，注意本文只討論機械磁碟，SSD 不在本文討論範圍之內。我們人類管理任何事物總是習慣先劃分出一定的結構，再此規則的基礎上進行管理。軍隊分軍、師、旅、團和營。公司分事業群、部門、中心和小組。然後對於管理磁碟，分磁碟面、磁頭、磁軌、柱面和扇區。

- 磁碟面：磁碟是由一疊磁碟面組成，見圖。
- 磁頭 (Heads)：每個磁頭對應一個磁碟面，負責該磁碟面上的資料的讀寫。。
- 磁軌 (Track)：每個盤面會圍繞圓心劃分出多個同心圓圈，每個圓圈叫做一個磁軌。
- 柱面 (Cylinders)：所有碟片上的同一位置的磁軌組成的立體叫做一個柱面。
- 扇區 (Sector)：以磁軌為單位管理磁碟仍然太大，所以電腦前輩們又把每個磁軌劃分出了多個扇區，見下右圖

本人愛上 Linux 的一個原因就是隻要你願意下功夫，你就能把 Linux 的內部邏輯徹底鋪開來看，這點比 Windows 要好太多了。Linux 上可以透過   `fdisk` 命令，來檢視當前系統使用的磁碟的這些實體資訊。

以上是我本人的一臺虛擬機器的磁碟實體資訊。可以看出我的磁碟有 255 個 heads，也就是說共有 255 個盤面。3263 個 cylinders，也就是說每個盤面上都有 3263 個磁軌， 63 `sectors/track` 說的是每個磁軌上共有 63 個扇區。命令結果也給出了 Sector size 的值是 512 bytes。那我們動筆算一下該磁碟的大小吧。

255 盤面 3263 柱面 63 扇區 * 每個扇區 512 bytes = 26839088640 byte。

結果是 26.8 G,和磁碟的總大小基本相符（至於   `fdisk` 給出的詳細結果相差了約 4M 的大小，筆者也沒有弄徹底明白，有興趣的讀者可以繼續研究）。

不過要注意一點就是上面的盤面等資料是邏輯上的，是實體盤面對映轉化而來的，這個轉化關係我現在還沒搜到特別好的資料。

## 2、分割槽

分割槽是作業系統對磁碟進行管理的第一步，這也是我們任何一個電腦使用者都非常熟悉的概念。例如 Windows 下的 C、D、E、F 盤。那麼請思考一下，

思考：前面的磁碟的詳細實體結構已經有了，如果讓你把整塊磁碟分成 C、D 等分割槽，你會怎麼分呢？

- 方案一： 255 個盤面，C 盤是 0-100 盤面， D 盤是 101-200 個盤面， ……
- 方案二：3263 個柱面，C 盤 0-1000 個柱面，D 盤 1001-20001 個柱面， ……

對於以上的兩個方案，你會選擇哪一種呢？？先說下磁碟 IO 時的過程。

- 第一步，首先是磁頭徑向移動來尋找資料所在的磁軌。這部分時間叫尋道時間。
- 第二步，找到目標磁軌後透過盤面旋轉，將目標扇區移動到磁頭的正下方。
- 第三步，向目標扇區讀取或者寫入資料。到此為止，一次磁碟 IO 完成。

故單次磁碟 IO 時間= 尋道時間 + 旋轉延遲 + 存取時間。

對於旋轉延遲，現在主流伺服器上經常使用的是 1W 轉/分鐘的磁碟，每旋轉一週所需的時間為 60*`1000/10000`=6ms，故其旋轉延遲為（0-6ms）。對於存取時間，一般耗時較短，為零點幾 ms。對於尋道時間，現代磁碟大概在 3-15 ms，其中尋道時間大小主要受磁頭當前所在位置和目標磁軌所在位置相對距離的影響。
其實採用哪一種，最主要看的是那種方式效能更快。因為同一分割槽下的資料經常會一起讀取，假如採用第一種，那麼這樣磁頭就需要在 3000 多個 track 間不停地跳來跳去，這樣磁碟的尋道時間就會翻倍，磁碟效能就會下降。而對於方案二，假如對於磁碟 C，只需要在磁頭在 1-1000 個磁軌間移動就可以了，大大降低了尋道時間。（實際上分割槽並不是從 0 開始的，磁碟的第一個磁軌對應的柱面會被用來安裝引導載入程式以及磁碟分割槽表）。所以，方案二的分割槽方式可以降低磁碟 IO 時間中的尋道時間部分，所以所有的作業系統採用的都是方案二，沒有用方案一的。

在 Linux 下使用過   `fdisk` 進行分割槽的話可以注意到以下資訊。

這充分證明了作業系統是採用方案二的。

回到開篇問題 1，作業系統是採用什麼技巧來降低隨機讀寫的效能問題的呢？作業系統透過按磁軌對應的柱面劃分分割槽，來降低磁碟 IO 所花費的的尋道時間 ，進而提高磁碟的讀寫效能。

你可能會問我為什麼檔名變成了 3 倍後，佔用的 block 數目為什麼沒有變成 3 倍。其實 Linux 檔案系統關於檔案的結構體中除了檔名以外，還有其他的一些欄位的，檔名變長 3 倍不會導致結構體變大 3 倍的，這點可以參考 Linux 系統核心相關書籍。

好了，到現在開篇問題 6 也有了答案了。檔名長了當然會對系統效能產生影響，因為這可能會導致更多的磁碟 IO。很多程式設計師都喜歡將檔案命名為有意義的長串，使人一看檔名就知道用途。當然我沒說這樣不好，但是如果你的檔案數量相當大的時候，你就要考慮你的檔名是否導致你的目錄 block 佔用太多了。

佔用的空間倒是小事，磁碟很便宜，但是你得考慮下在目錄下查詢檔案時作業系統的感受，作業系統可需要用你你提供的檔名進行字串比較，而且運氣不好的話需要將其名下所有 block 都讀取一遍才行啊。（當然了，你的檔名長度不變態，而且數量沒有達到十萬數量級的話實際上這個開銷也不會太大，但是這個開銷你還是知道的為好）

至於開篇問題 5，檔名最長多長。實際上 Linux 作業系統就是為了避免程式設計師不節制地使用長檔名，強加了個限制，不得超過 255 byte。

另外，大家有沒有經驗，在目錄下檔案很多的時候，我們使用 ls 命令時會很慢。現在大家知道原因了吧，這時實際上作業系統在讀取當前目錄的所有 block ，如果 block 比較多的話，可能得需要多次 IO 操作才能完成這個簡單的 ls 命令。
我在自己的電腦某個目錄下建立了一 100W 個空檔案，ls 命令 1 分鐘還沒出結果，被我 ctrl+c 掉了。在自己的專案中可不要這麼做，雖然作業系統可以 cache 住你的目錄資料，使你下次呼叫時會塊很多，但我還是建議你單個目錄下檔案數目不要過萬。否則你的程式在重啟後首次執行時可能會出現效能不佳的情況。

好了，回到開篇問題 7，你有答案了嗎？一個目錄下最多能建多少個檔案，這個最多其實是受限於你目錄所在分割槽的 inode 數量，你有 100W 個 inode，你最多就可以新建 100W 個檔案。但是，上面說了，單個目錄下檔案數量最好不要過萬，否則會帶來系統效能的問題。

## 4、檔案的 block

再做個關於檔案的實驗。我新建了個空目錄，並在其下新建了個檔案，裡面只寫了一個空格資料，儲存後 du 命令顯示如下：

這 8K 裡有 4K 是目錄的，也就可以算出作業系統為只包含一個空格的檔案分配了 4KB。其實檔案的 block 比較簡單的了，不像目錄的 block 裡會存很多檔案系統的結構體，檔案的 block 裡只會儲存檔案的資料。上面這個實驗表明，作業系統分配空間時是以 block 為最小單位。也就是說只要你的檔案資料不為空，作業系統就至少會給你分配一個 block 來儲存，直到你超過了 4KB，作業系統再給你分配下一個 block，就是這樣。所以對於開篇問題 8，新建一個內容大小為 1k 的檔案，實際會佔用 1 個 block（一般為 4k）和一個 inode（一般為 256byte）。

其實檔案系統在向磁碟發起 IO 請求的時候，也是以 block size 為單位的。哪怕你只向作業系統發起讀取檔案的 2 Byte，但是作業系統會一次性給你讀取 4KB 回來。因此磁碟 IO 真的是很慢，而且我們只要存取了這 2 Byte，確實很有可能接下來繼續存取這 2byte 後面的內容，這也就是程式區域性性原理，所以作業系統索性一次性就多讀取些回來了。呵呵，這就是開篇問題 9 的答案。
這就像我們去逛超市，逛一次真的是很浪費時間，這可要比坑爹的磁碟 IO 也慢許多了。我們總不會逛了一圈超市就買了一個蘋果就回來了吧，我們肯定會多買些東西為家裡以後的需求準備著，反正買一堆東西比買一個蘋果也沒多花多少時間，何樂為不為呢，就是這個道理。

再說說開篇問題 10，我們攻城獅怎麼樣設計你的檔案能提高一些 IO 速度呢？那就是如果你知道你的要新建的檔案大概會佔用多大的空間的話，例如 1M。那麼你新建檔案時就順便和作業系統說一下，讓它幫你將檔案的 size 預留下來。這樣實際上作業系統時會儘可能為你分配連續的 block，這樣你再讀取這個檔案時，磁頭就省去很多尋道時間了，IO 速度就顯得快多了。

## 三、寫在後面的話

前面我們說的都是根據我自己的檔案系統，情形是一個 block size 是 4KB，一個 inode size 是 256byte，包括我虛擬機器上的 inode 數量才只有 140 多萬個。這些值實際上不是固定的，你完全可以在格式化你的硬碟的時候設定成其他的值。設定的原則就是看你的硬碟的容量，以及你的用途。

如果你的檔案都是大於 4KB，甚至是幾 M，幾 G 的檔案，那麼建議你的 block 還是儘可能的大一點吧，這樣 inode 裡就能少記幾個位址。

如果你的檔案大部分都是 1K 以下的，那麼確實使用 4K 的 block 會造成一點點浪費，如果你的老闆對成本要求異常苛刻的話，你可以適當考慮把你的 block 設定得小一點。

另外，要關注你的檔案系統的 inode。作業系統在檢視目錄和檔案佔用的磁碟空間資訊時把 inode 節點的佔用給隱藏起來了，其用意在於為使用者提供一個白盒的環境，把資料佔用的空間交給我們來認知，而把 inode 資訊隱藏起來為了降低我們理解作業系統的難度。而實際上，我們作為非普通使用者的開發人員應該具備這個知情權。這個東西直接關係到你檔案系統能建立檔案數量。否則哪天等你發現線上機器磁碟還剩大把大把的空間，但就是 inode 使用光了，那時候就只有重新格式化或者遷移伺服器了。這兩個操作想想都覺得很慘啊，還是能避免就儘量避免吧。

思考題：我們大家有個經驗就是目錄下小檔案太多的情況下，往其他地方複製的話，速度會非常的慢，我們這時往往會把目錄壓縮一下再複製。現在你能說出這樣做為什麼會快嗎？
