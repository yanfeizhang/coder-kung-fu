# 明明還有大量記憶體，為啥報錯“無法分配記憶體”？

> 原文標題：明明还有大量内存，为啥报错“无法分配内存”？

> 原文連結：http://kfngxl.cn/index.php/archives/532/

---

大家好，我是飛哥！

讀者群裡一位同學的線上伺服器出現一個詭異的問題，執行任何命令都是報錯“fork:無法分配記憶體”。 這個問題最近出現的，前幾次重啟後解決的，但是每隔 2-3 天就會出現一次。

看到這個提示，大家的第一反應肯定是懷疑記憶體真的不夠了。我們這位讀者也是這麼認為的。但檢視記憶體佔用卻發現根本沒有，記憶體還空閒了一大把！（多試幾次才有機會執行成功一次）

飛哥和群裡的同學們一起參謀這個問題以後，幫出了三個思路。讓這位讀者回去挨個試。

1.是不是numa架構下，程序啟動的時候繫結了node，導致只有一個node裡的記憶體在起作用？

2.numa架構下，如果所有記憶體都插到一個槽，其它node就會沒記憶體

3.檢視下現在的進(線)程數是多少，是不是超過最大限制了

在經過一段時間的排查以後，這位讀者的問題順利解決。這裡直接和大家彙報結論，前面關於 numa 記憶體不足的猜測是錯誤的。真實的原因是上面第 3 個， 這臺伺服器上面的某幾個java程序建立了太多的執行緒，導致了這個報錯的產生 ，並不真的是記憶體不夠。

一、底層過程分析

這個問題中， Linux 報錯提示存在誤導人的地方。導致大家並沒有第一時間往程序數上想。所以才有了這麼複雜曲折的排錯過程，以至於在群裡討論才得以解決。

於是我想深入到核心裡看看，報錯到底是如何提示出來這麼一個不恰當的錯誤提示的。然後順便咱們也來了解了解建立程序的過程。

1.1 do_fork 剖析

在 Linux 核心裡，無論是建立程序還是執行緒，都會呼叫到最核心的 do_fork 上來。在這個函式內部，透過複製的方式來建立新的程序（執行緒）所需要的核心資料物件。

透過以上程式碼可以看出，Linux 核心建立整個程序核心物件的建立過程都是透過分別呼叫不同的 copy_xxx 的方式來實現的，包括 mm 結構體、包括 namespaces等等。

我們來重點 alloc_pid 相關的這一段。在這一段中，目的是要申請一個 pid 物件出來。如果申請失敗就返回錯誤了。 大家注意這段程式碼的細節：無論 alloc_pid 返回的是何種型別的失敗，其錯誤型別都寫死的返回 -ENOMEM。。。 為了方便大家理解，我單獨把這段邏輯再展示一遍。

在準備呼叫 alloc_pid 的時候，直接就先將錯誤型別設定成了 -ENOMEM(retval = -ENOMEM)， 只要 alloc_pid 返回的不正確，都是將 ENOMEM 這個錯誤返回給上層。而不管 alloc_pid 記憶體究竟是因為什麼原因產生的錯誤 。

我們來檢視一下 ENOMEM 的定義。它代表的是 Out of memory 的意思。（核心只是返回錯誤碼，應用層再給出具體的錯誤提示，所以實際提示的是中文的“無法分配記憶體”）。

不得不說。核心的這個錯誤提示太成問題了。給使用者造成了很大的困惑。

我們平時說的 pid 在核心中並不是一個簡單的整數型別，而是一個小結構體來表示的（struct pid），如下。

所以需要先到記憶體中申請一塊記憶體用來儲存這個小物件。第一種錯誤情況是如果記憶體申請失敗，alloc_pid 會返回失敗。這種情況下確實是記憶體問題，出錯後核心返回 ENOMEM 無可厚非。

接著往下看第二種情況，alloc_pidmap 是要為當前的程序申請程序號，就是我們平時所說的 PID 編號。如果申請失敗，也會返回錯誤。

對於這種情況來說， 只是分配程序編號出錯了，和記憶體不夠用半毛錢的關係都沒有。但在這種情況下核心卻會導致返回給上層的錯誤型別是 ENOMEM（Out of memory） 。這實在是挺不合理的。

透過這裡我們還額外學習到了另外一個知識！一個程序並不只是申請一個程序號就夠了。而是透過一個 for 迴圈去申請了多個。

假如說當前建立的程序是一個容器中的程序，那麼它至少得申請兩個 PID 號才行。一個 PID 是在容器名稱空間中的程序號，一個是根名稱空間（宿主機）中的程序號。

這也符合我們平時的經驗。在容器中的每一個程序其實我們在宿主機中也都能看到。但是在容器中看到的程序號一般是和在宿主機上看到的是不一樣的。比如一個程序在容器中的 pid 是 5，在宿主機名稱空間下是 1256。那麼該程序在核心中的物件大概是如下這個樣子。

二、新版本是否有所改觀

接下來，我首先想到的可能是因為咱們用的核心版本太舊了。（熟悉飛哥的讀者都知道，我用的核心版本是 3.10.1，這是為了和我們公司線上伺服器的版本保持一致。）

所以我又到非常新的 Linux 5.16.11 翻了一翻，看看新版本是否有修復這個不恰當的提示。

貌似看起來有戲， retval 不再寫死的是 ENOMEM 了，而是根據 alloc_pid 實際的錯誤進行了設定。我們再來看 alloc_pid 是不是正確地設定錯誤型別了呢？

當我開啟 alloc_pid 的原始碼裡，看到一大段註釋的時候，我的心涼了半截。。。

我把這段註釋給大家大致翻譯一下。它的意思是“ENOMEM不是最明顯的選擇，尤其是對於 pid 建立失敗的情況下。但是，ENOMEM 是我們長期暴露給使用者空間的東西。因此，即使有更適合的錯誤程式碼，我們也無法輕易更改它”

看到這兒，我想起了有不少人也稱 Linux 為屎山，可能這就是其中的一坨吧！​​最新的版本里也並沒有很好的解決這個問題。

結論

在 Linux 裡建立程序時，如果在 pid 不足的時候竟然返回的錯誤提示是“記憶體不足”。這個不恰當的錯誤提示導致很多同學都困惑不已。

透過今天的文章，以後你再遇到這種記憶體不足錯誤的時候，你就要多留個心眼兒了，別被核心被矇騙了，先來看看自己的程序（執行緒）數是不是過多了。

至於說發現了這個問題該如何解決嘛，可以透過修改核心引數加大可用 pid 數量(/proc/sys/kernel/pid_max)。

但是我覺得最根本的方法還是要揪出來為啥系統中會出現這麼多的程序（執行緒），然後把它幹掉。預設情況下的兩三萬個程序數對於絕大多數的伺服器來說已經是一個過於龐大的數字了，連這個數都超過了，一定是不合理的。
