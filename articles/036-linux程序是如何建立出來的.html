一、Nginx 之 fork 建立 worker

在 Linux 程序的建立中，最核心的就是 fork 系統呼叫。不過我們先不著急介紹它，先拿多程序服務中的一個經典例子 - Nginx，來看看他是如何使用 fork 來建立 worker 的。

Nginx 服務採用的是多程序方式來工作的，它啟動的時候會建立若干個 worker 程序出來，來響應和處理使用者請求。建立 worker 子程序的原始碼位於 nginx 原始碼的 src/os/unix/ngx_process_cycle.c 檔案中。透過迴圈呼叫 ngx_spawn_process 來建立 n 個 worker 出來。

我們在來看下負責具體程序建立的 ngx_spawn_process 函式。

在 ngx_spawn_process 中呼叫 fork 來建立程序，建立成功後 Worker 程序就將進入自己的入口函式中開始工作了。

二、Linux 中對程序的表示

在深入理解程序建立之前，我們先來看一下程序的資料結構。

在 Linux 中，是用一個 task_struct 來實現 Linux 程序的（其實 Linux 執行緒也同樣是用 task_struct 來表示的，這個我們以後文章單獨再說）。

我們來看看 task_struct 具體的定義，它位於 include/linux/sched.h

2.1 程序執行緒狀態

程序執行緒都是有狀態的，它的狀態就儲存在 state 欄位中。常見的狀態中 TASK_RUNNING 表示程序執行緒處於就緒狀態或者是正在執行。TASK_INTERRUPTIBLE 表示程序執行緒進入了阻塞狀態。

一個任務（程序或執行緒）剛建立出來的時候是 TASK_RUNNING 就緒狀態，等待排程器的排程。排程器執行 schedule 後，任務獲得 CPU 後執行。當需要等待某個事件的時候，例如阻塞式 read 某個 socket 上的資料，但是資料還沒有到達的時候，任務進入 TASK_INTERRUPTIBLE 或 TASK_UNINTERRUPTIBLE 狀態，任務被阻塞掉。

當等待的事件到達以後，例如 socket 上的資料到達了。核心在收到資料後會檢視 socket 上阻塞的等待任務佇列，然後將之喚醒，使得任務重新進入 TASK_RUNNING 就緒狀態。任務如此往復地在各個狀態之間迴圈，直到退出。

2.2 程序 ID

我們知道，每一個程序都有一個程序 id 的概念。在 task_struct 中有兩個相關的欄位，分別是 pid 和 tgid。

其中 pid 是 Linux 為了標識每一個程序而分配給它們的唯一號碼，稱做程序 ID 號，簡稱 PID。對於沒有建立執行緒的程序(只包含一個主執行緒)來說，這個 pid 就是程序的 PID，tgid 和 pid 是相同的。

2.3 程序樹關係

在 Linux 下所有的程序都是透過一棵樹來管理的。在作業系統啟動的時候，會建立 init 程序，接下來所有的程序都是由這個程序直接或者間接建立的的。透過 pstree 命令可以檢視你當前伺服器上的程序樹資訊。

那麼，這棵程序樹就是由 task_struct 下的 parent、children、sibling 等欄位來表示的。這幾個欄位將系統中的所有 task 串成了一棵樹。

2.4 程序排程優先順序

在 task_struct 中有幾個欄位是表示程序優先順序的，在程序排程的時候會根據這幾個欄位來決定優先讓哪個任務（程序或執行緒）開始執行。

static_prio: 用來儲存靜態優先順序，可以呼叫 nice 系統直接來修改取值範圍為 100~139

rt_priority: 用來儲存實時優先順序,取值範圍為 0~99

prio: 用來儲存動態優先順序

normal_prio: 它的值取決於靜態優先順序和排程策略

2.5 程序地址空間

對於使用者程序來講，記憶體描述符 mm_struct( mm 代表的是 memory descriptor)是非常核心的資料結構。整個程序的虛擬地址空間部分都是由它來表示的。

程序在執行的時候，在使用者態其所需要的程式碼，全域性變數資料，以及 mmap 記憶體對映等全部都是透過 mm_struct 來進行記憶體查詢和定址的。這個資料結構的定義位於 include/linux/mm_types.h 檔案下。

其中 start_code、end_code 分別指向程式碼段的開始與結尾、start_data 和 end_data 共同決定資料段的區域、start_brk 和 brk 中間是堆記憶體的位置、start_stack 是使用者態堆疊的起始地址。整個 mm_struct 和地址空間、頁表、實體記憶體的關係如下圖。

在核心記憶體區域，可以透過直接計算得出實體記憶體地址，並不需要複雜的頁表計算。而且最重要的是所有核心程序、以及使用者程序的核心態，這部分記憶體都是共享的。

另外要注意的是，mm（mm_struct）表示的是虛擬地址空間。而對於核心執行緒來說，是沒有使用者態的虛擬地址空間的。所以核心執行緒的 mm 的值是 null。

2.6 程序檔案系統資訊（當前目錄等）

程序的檔案位置等資訊是由 fs_struct 來描述的，它的定義位於 include/linux/fs_struct.h 檔案中。

透過以上程式碼可以看出，在 fs_struct 中包含了兩個 path 物件，而每個 path 中都指向了一個 struct dentry。在 Linux 核心中，denty 結構是對一個目錄項的描述。

拿 pwd 來舉例，該指標指向的是程序當前目錄所處的 denty 目錄項。假如我們在 shell 程序中執行 pwd，或者使用者程序查詢當前目錄下的配置檔案的時候，都是透過訪問 pwd 這個物件，進而找到當前目錄的 denty 的。

2.7 程序開啟的檔案資訊

每個程序用一個 files_struct 結構來記錄檔案描述符的使用情況， 這個 files_struct 結構稱為使用者開啟檔案表。它的定義位於 include/linux/fdtable.h。

在 files_struct 中，最重要的是在 fdtable 中包含的 file **fd 這個陣列。這個陣列的下標就是檔案描述符，其中 0、1、2 三個描述符總是預設分配給標準輸入、標準輸出和標準錯誤。這就是你在 shell 命令中經常看到的 2>&1 的由來。這幾個字元的含義就是把標準錯誤也一併打到標準輸出中來。

在陣列元素中記錄了當前程序開啟的每一個檔案的指標。這個檔案是 Linux 中抽象的檔案，可能是真的磁碟上的檔案，也可能是一個 socket。

2.8 namespaces

在 Linux 中，namespace 是用來隔離核心資源的方式。透過 namespace 可以讓一些程序只能看到與自己相關的一部分資源，而另外一些程序也只能看到與它們自己相關的資源，這兩撥程序根本就感覺不到對方的存在。

具體的實現方式是把一個或多個程序的相關資源指定在同一個 namespace 中，而程序究竟是屬於哪個 namespace，都是在 task_struct 中由 *nsproxy 指標表明了這個歸屬關係。

名稱空間包括PID名稱空間、掛載點名稱空間、網路名稱空間等多個。飛哥在咱們「開發內功修煉」前面的一篇文章《動手實驗+原始碼分析，徹底弄懂Linux網路名稱空間》這一文中詳細介紹過網路名稱空間，感興趣的同學可以詳細閱讀。

三、解密 fork 系統呼叫

前面我們看了 Nginx 使用 fork 來建立 worker 程序，也瞭解了程序的資料結構 task_struct ，我們再來看看 fork 系統呼叫的內部邏輯。

這個 fork 在核心中是以一個系統呼叫來實現的，它的核心入口是在 kernel/fork.c 下。

這裡注意下呼叫 do_fork 時傳入的第一個引數，這個引數是一個 flag 選項。它可以傳入的值包括 CLONE_VM、CLONE_FS 和 CLONE_FILES 等等很多，但是這裡只傳了一個 SIGCHLD（子程序在終止後傳送 SIGCHLD 訊號通知父程序），並沒有傳 CLONE_FS 等其它 flag。

在 do_fork 的實現中，核心是一個 copy_process 函式，它以複製父程序的方式來生成一個新的 task_struct 出來。

在建立完畢後，呼叫 wake_up_new_task 將新建立的任務新增到就緒佇列中，等待排程器排程執行。

3.4 複製 mm_struct

前面我們說過，對於程序來講，地址空間是一個非常重要的資料結構。而且程序之間地址空間也必須是要隔離的，所以還會新建一個地址空間。

建立地址空間的操作是在 copy_mm 中執行的。

do_fork 被呼叫時也沒有傳 CLONE_VM，所以會呼叫 dup_mm 申請一個新的地址空間出來。

在 dup_mm 中，透過 allocate_mm 申請了新的 mm_struct，而且還將當前程序地址空間 current->mm 複製到新的 mm_struct 物件裡了。

地址空間是程序執行緒最核心的東西，每個程序都有獨立的地址空間

3.5 複製程序的名稱空間 nsproxy

在建立程序或執行緒的時候，還可以讓核心幫我們建立獨立的名稱空間。在預設情況下，建立程序沒有指定名稱空間相關的標記，因此也不會建立。新舊程序仍然複用同一套名稱空間物件。

3.6 申請pid

接下來 copy_process 還會進入 alloc_pid 來為當前任務申請 PID。

注意下，在呼叫 alloc_pid 的時候，其引數傳遞的是新程序的 pid namespace。我們來深看一下 alloc_pid 的執行邏輯。

這裡的 PID 並不是一個整數，而是一個結構體，所以先試用 kmem_cache_alloc 把它申請出來。接下來呼叫 alloc_pidmap 到 pid 名稱空間中申請一個 pid 號出來，申請完後賦值記錄。

回顧我們開篇提到的一個問題：作業系統是如何記錄使用過的程序號的？ 在 Linux 內部，為了節約記憶體，程序號是透過 bitmap 來管理的。

在每一個 pid 名稱空間內部，會有一個或者多個頁面來作為 bitmap。其中每一個 bit 位（注意是 bit 位，不是位元組）的 0 或者 1 的狀態來表示當前序號的 pid 是否被佔用。

在 alloc_pidmap 中就是以 bit 的方式來遍歷整個 bitmap，找到合適的未使用的 bit，將其設定為已使用，然後返回。

在各種語言中，一般一個 int 都是 4 個位元組，換算成 bit 就是 32 bit。而使用這種 bitmap 的思想的話，只需要一個 bit 就可以表示一個整數，相當的節約記憶體。所以，在很多超大規模資料處理中都會用到這種思想來進行最佳化記憶體佔用的。

3.7 進入就緒佇列

當 copy_process 執行完畢的時候，表示新程序的一個新的 task_struct 物件就建立出來了。接下來核心會呼叫 wake_up_new_task 將這個新建立出來的子程序新增到就緒佇列中等待排程。

等作業系統真正排程開始的時候，子程序中的程式碼就可以真正開始執行了。

四、總結

在這篇文章中，我用 Nginx 建立 worker 程序的例子作為引入，然後帶大家瞭解一些程序的資料結構 task_struct，最後又帶大家看一下 fork 執行的過程。

在 fork 建立程序的時候，地址空間 mm_struct、掛載點 fs_struct、開啟檔案列表 files_struct 都要是獨立擁有的，所以都去申請記憶體並初始化了它們。但由於今天我們的例子父子程序是同一個名稱空間，所以 nsproxy 還仍然是共用的。

其中 mm_struct 是一個非常核心的資料結構，使用者程序的虛擬地址空間就是用它來表示的。對於核心執行緒來講，不需要虛擬地址空間，所以 mm 成員的值為 null。

另外還學到了核心是用 bitmap 來管理使用和為使用的 pid 號的，這樣做的好處是極大地節約了記憶體開銷。而且由於資料儲存的足夠緊湊，遍歷起來也是非常的快。一方面原因是資料小，載入起來快。另外一方面是會加大提高 CPU 快取的命中率，訪問非常快。
