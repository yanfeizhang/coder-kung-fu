# TCP連線中客戶端的埠號是如何確定的？

> 原文標題：TCP连接中客户端的端口号是如何确定的？

> 原文連結：http://kfngxl.cn/index.php/archives/313/

大家好，我是飛哥！

在 TCP 連線中，客戶端在發起連線請求前會先確定一個客戶端埠，然後用這個埠去和伺服器端進行握手建立連線。那麼在 Linux 上，客戶端的埠到底是如何被確定下來的呢？

事實上很多我們平時遇到的問題都和這個埠選擇過程相關，如果能深度理解這個過程，將有助於我們對這些問題的深刻理解。

Cannot assign requested address 報錯是怎麼回事？

一個客戶端埠可以同時用在兩條 TCP 連線上嗎？

還是讓我們藉助一段簡單到只有兩句的程式碼，從這個來講起！

一、建立 socket

客戶端在發起連線的時候，需要事先建立一個 socket。在 c 語言中，就是呼叫 socket 函式，例如 socket(AF_INET,SOCK_STREAM, 0) 這句。

socket 函式執行完畢後，在使用者層視角我們是看到返回了一個檔案描述符 fd。但在核心中其實是一套核心物件組合，大體結構如下。

從上圖我們看到，socket 在核心裡並不是一個核心物件。而是包含 file、socket、sock 等多個相關核心物件構成，每個核心物件還定義了 ops 操作函式集合。 在後面的核心原始碼執行過程中，我們需要時不時回頭來看這些核心物件，這裡先簡單瞭解一下就行。

這些核心物件都是在 socket 系統呼叫執行過程中建立出來的。為了避免喧賓奪主，這裡只列出入口程式碼，詳細過程就不展開介紹了。

二、connect 發起連線

接下來我們就進入到 connect 函式的執行過程中來。由於這個過程比較長，所以我們分成幾個小節來進行討論。

2.1 connect 呼叫鏈展開

當我們在客戶端機上呼叫 connect 函式的時候，事實上會進入到核心的系統呼叫原始碼中進行執行。

這段程式碼首先根據使用者傳入的 fd（檔案描述符）來查詢對應的 socket 核心物件。在第一節中我們看了 socket 核心物件結構，據此可以知道接下來 sock->ops->connect 其實呼叫的是 inet_stream_connect 函式。

剛建立完畢的 socket 的狀態就是 SS_UNCONNECTED，所以在 \_\_inet_stream_connect 中的 switch 判斷會進入到 case SS_UNCONNECTED 的處理邏輯中。

上述程式碼中 sk 取的是 sock 物件。繼續回顧第一節中 socket 的核心資料結構圖，可以得知 sk->sk_prot->connect 實際上對應的是 tcp_v4_connect 方法。

我們來看 tcp_v4_connect 的程式碼，它位於 net/ipv4/tcp_ipv4.c。

在 tcp_v4_connect 中我們終於看到了選擇埠的函式，那就是 inet_hash_connect。

2.2 選擇可用埠

我們找到 inet_hash_connect 的原始碼，我們來看看到底埠是如何選擇出來的。

這裡需要提一下在呼叫 \_\_inet_hash_connect 時傳入的兩個重要引數。

inet_sk_port_offset(sk)：這個函式是根據要連線的目的 IP 和埠等資訊生成一個隨機數。

\_\_inet_check_established：檢查是否和現有 ESTABLISH 的連線是否衝突的時候用的函式

瞭解了這兩個引數後，讓我們進入 \_\_inet_hash_connect。這個函式比較長，為了方便理解，我們先看前面這一段。

在這個函式中首先判斷了 inet_sk(sk)->inet_num，如果我們呼叫過 bind，那麼這個函式會選擇好埠並設定在 inet_num 上。這個我們後面專門分一小節介紹。這裡我們假設沒有呼叫過 bind，所以 snum 為 0。

接著呼叫 inet_get_local_port_range，這個函式讀取的是 net.ipv4.ip_local_port_range 這個核心引數。 來讀取管理員配置的可用的埠範圍。

接下來進入到了 for 迴圈中。其中offset 是我們前面說的，透過 inet_sk_port_offset(sk) 計算出的隨機數。那這段迴圈的作用就是從某個隨機數開始，把整個可用埠範圍來遍歷一遍。直到找到可用的埠後停止。

那麼我們接著來看，如何來確定一個埠是否可以使用呢？

首先判斷的是 inet_is_reserved_local_port，這個很簡單就是判斷要選擇的埠是否在 net.ipv4.ip_local_reserved_ports 中，在的話就不能用。

整個系統中會維護一個所有使用過的埠的雜湊表，它就是 hinfo->bhash。接下來的程式碼就會在這裡進行查詢。 如果在雜湊表中沒有找到，那麼說明這個埠是可用的。至此埠就算是找到了。

遍歷完所有埠都沒找到合適的，就返回 -EADDRNOTAVAIL，你在使用者程式上看到的就是 Cannot assign requested address 這個錯誤。怎麼樣，是不是很眼熟，你見過它的對吧，哈哈！

以後當你再遇到 Cannot assign requested address 錯誤，你應該想到去查一下 net.ipv4.ip_local_port_range 中設定的可用埠的範圍是不是太小了。

2.3 埠被使用過怎麼辦

回顧剛才的 \_\_inet_hash_connect， 為了描述簡單我們之前跳過了已經在 bhash 中存在時候的判斷。 這是由於其一這個過程比較長，其二這段邏輯很有價值，所以飛哥單獨拉一小節出來。

port 已經在 bhash 中如果已經存在，就表示有其它的連線使用過該埠了。 請注意，如果 check_established 返回 0，該埠仍然可以接著使用！ 。

這裡可能會讓很多同學困惑了，一個埠怎麼可以被用多次呢？

回憶下四元組的概念，兩對兒四元組中只要任意一個元素不同，都算是兩條不同的連線。以下的兩條 TCP 連線完全可以同時存在（假設 192.168.1.101 是客戶端，192.168.1.100 是服務端）

連線1：192.168.1.101 5000 192.168.1.100 8090

連線2：192.168.1.101 5000 192.168.1.100 8091

check_established 作用就是檢測現有的 TCP 連線中是否四元組和要建立的連線四元素完全一致。如果不完全一致，那麼該埠仍然可用！！！

這個 check_established 是由呼叫方傳入的，實際上使用的是 \_\_inet_check_established。我們來看它的原始碼。

該函式首先找到 inet_ehash_bucket，這個和 bhash 類似，只不過是所有 ESTABLISH 狀態的 socket 組成的雜湊表。然後遍歷這個雜湊表，使用 INET_MATCH 來判斷是否可用。

這裡 INET_MATCH 原始碼如下：

在 INET_MATCH 中將 \_\_saddr、\_\_daddr、\_\_ports 都進行了比較。當然除了 ip 和埠，INET_MATCH還比較了其它一些東東，所以 TCP 連線還有五元組、七元組之類的說法。為了統一，咱們還沿用四元組的說法。

如果 MATCH，就是說就四元組完全一致的連線，所以這個埠不可用。也返回 -EADDRNOTAVAIL。

如果不 MATCH，哪怕四元組中有一個元素不一樣，例如伺服器的埠號不一樣，那麼就 return 0，表示該埠仍然可用於建立新連線。

三、bind 時埠如何選擇

在 2.2 小節中，我們看到 connect 選擇埠之前先判斷了 inet_sk(sk)->inet_num 有沒有值。如果有的話就直接用這個，而會跳過埠選擇過程。

那麼這個值是從哪兒來的呢？不賣關子，它就是在對 socket 使用 bind 時設定的。

不只是伺服器端，哪怕是對於客戶端，也可以對 socket 使用 bind 來繫結 IP 或者埠。如果使用了 bind，那麼在 bind 的時候就會確定好埠，並設定到 inet_num 變數中。

bind 的時候，如果傳了埠，那麼 bind 就會嘗試使用該埠。如果埠號傳的是 0 ，那麼 bind 有一套獨立的選擇埠號的邏輯。

根據第一節中的 socket 核心物件，能找到 sk->sk_prot->get_port 實際呼叫的是 inet_csk_get_port。該函式來嘗試確定埠號，如果嘗試失敗，返回 EADDRINUSE。你的應用程式將會顯示一條錯誤資訊 “Address already in use”。

我們簡單看一下如果使用者沒有傳入埠（傳入的為 0），bind 是怎麼選擇埠的。

這段邏輯和 connect 很像，透過 net_random 來從 net.ipv4.ip_local_port_range 指定的埠範圍內一個隨機位置開始遍歷。也會跳開 ip_local_reserved_ports 保留埠配置。 透過 inet_csk(sk)->icsk_af_ops->bind_conflict 進行衝突檢測。

inet_csk_bind_conflict 這個函式整體比較複雜，不過我們只需要瞭解一點就好，該函式和 connect 中埠選擇邏輯不同的是，並不會到 ESTABLISH 的雜湊表進行可用檢測，只在 bind 狀態的 socket 裡查。所以 預設情況下，只要埠用過一次就不會再次使用 。

四、結論

客戶端建立連線前需要確定一個埠，該埠會在兩個位置進行確定。

第一個位置，也是最主要的確定時機是 connect 系統呼叫執行過程。在 connect 的時候，會隨機地從 ip_local_port_range 選擇一個位置開始迴圈判斷。找到可用埠後，發出 syn 握手包。如果埠查詢失敗，會報錯 “Cannot assign requested address”。這個時候你應該首先想到去檢查一下伺服器上的 net.ipv4.ip_local_port_range 引數，是不是可以再放的多一些。

如果你因為某種原因不希望某些埠被使用到，那麼就把它們寫到 ip_local_reserved_ports 這個核心引數中就行了，核心在選擇的時候會跳過這些埠。

另外注意即使是一個埠是可以被用於多條 TCP 連線的。所以一臺客戶端機最大能建立的連線數並不是 65535。只要 server 足夠多，單機發出百萬條連線沒有任何問題。我給大夥兒貼一下我實驗時候在客戶機上實驗時的實際截圖，來實際看一下一個埠號確實是被用在了多條連線上了。

截圖中左邊的 192 是客戶端，右邊的 119 是伺服器的 ip。可以看到客戶端的 10000 這個埠號是用在了多條連線上了的。

第二個位置，如果在 connect 之前使用了 bind，將會使得 connect 時的埠選擇方式無效。轉而使用 bind 時確定的埠。bind 時如果傳入了埠號，會嘗試首先使用該埠號，如果傳入了 0 ，也會自動選擇一個。但預設情況下一個埠只會被使用一次。所以對於客戶端角色的 socket，不建議使用 bind ！

最後我再想多說一句，上面的選擇埠的都是從 ip_local_port_range 範圍中的某一個隨機位置開始迴圈的。如果可用埠很充足，則能快一點找到可用埠，那迴圈很快就能退出。假設實際中 ip_local_port_range 中的埠快被用光了，這時候核心就大機率得把迴圈多執行很多輪才能找到， 這會導致 connect 系統呼叫的 CPU 開銷的上漲。

所以，最好不要等到埠不夠用了才加大 ip_local_port_range 的範圍，而是事先就應該保持一個充足的範圍。
