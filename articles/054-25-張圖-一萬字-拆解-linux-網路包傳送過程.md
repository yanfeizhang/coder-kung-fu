## 一、Linux 網路傳送過程總覽

飛哥覺得看 Linux 原始碼最重要的是得有整體上的把握，而不是一開始就陷入各種細節。

我這裡先給大家準備了一個總的流程圖，簡單闡述下 `send` 傳送了的資料是如何一步一步被髮送到網路卡的。

在這幅圖中，我們看到使用者資料被複製到核心態 (Kernel Mode)，然後經過協定堆疊處理後進入到了 RingBuffer 中。隨後網路卡驅動真正將資料傳送了出去。當傳送完成的時候，是透過硬中斷 (Hardware Interrupt) 來通知 CPU，然後清理 RingBuffer。

因為文章後面要進入原始碼，所以我們再從原始碼的角度給出一個流程圖。

雖然資料這時已經傳送完畢，但是其實還有一件重要的事情沒有做，那就是釋放快取 (Cache) 佇列等記憶體。

那核心是如何知道什麼時候才能釋放記憶體的呢，當然是等網路傳送完畢之後。網路卡在傳送完畢的時候，會給 CPU 傳送一個硬中斷來通知 CPU。更完整的流程看圖：

注意，我們今天的主題雖然是傳送資料，但是硬中斷最終觸發的軟中斷 (Softirq) 卻是   `NET_RX_SOFTIRQ`，而並不是 `NET_TX_SOFTIRQ`！！！（T 是 transmit 的縮寫，R 表示 receive）

意不意外，驚不驚喜？？？

所以這就是開篇問題 1 的一部分的原因（注意，這只是一部分原因）。

> 問 1：在伺服器上檢視 /  `proc/softirqs`，為什麼 `NET_RX` 要比 `NET_TX` 大的多的多？

傳輸完成最終會觸發 `NET_RX`，而不是 `NET_TX`。 所以自然你觀測 / `proc/softirqs` 也就能看到 `NET_RX` 更多了。

好，現在你已經對核心是怎麼傳送網路封包的有一個全域性上的把握了。不要得意，我們需要了解的細節才是更有價值的地方，讓我們繼續！！

## 二、網路卡啟動準備

現在的伺服器上的網路卡一般都是支援多佇列的。每一個佇列上都是由一個 RingBuffer 表示的，開啟了多佇列以後的的網路卡就會對應有多個 RingBuffer。

網路卡在啟動時最重要的任務之一就是分配和初始化 RingBuffer，理解了 RingBuffer 將會非常有助於後面我們掌握髮送。因為今天的主題是傳送，所以就以傳輸佇列為例，我們來看下網路卡啟動時分配 RingBuffer 的實際過程。

在網路卡啟動的時候，會呼叫到 \_\_igb_open 函式，RingBuffer 就是在這裡分配的。

```
//file: drivers/net/ethernet/intel/igb/igb_main.c
static int __igb_open(struct net_device *netdev, bool resuming)
{
    struct igb_adapter *adapter = netdev_priv(netdev);

    //分配傳輸描述符陣列
    err = igb_setup_all_tx_resources(adapter);

    //分配接收描述符陣列
    err = igb_setup_all_rx_resources(adapter);

    //開啟全部佇列
    netif_tx_start_all_queues(netdev);
}
```

在上面 \_\_igb_open 函式呼叫   `igb_setup_all_tx_resources` 分配所有的傳輸 RingBuffer, 呼叫 `igb_setup_all_rx_resources` 建立所有的接收 RingBuffer。

```
//file: drivers/net/ethernet/intel/igb/igb_main.c
static int igb_setup_all_tx_resources(struct igb_adapter *adapter)
{
    //有幾個佇列就構造幾個 RingBuffer
    for (i = 0; i < adapter->num_tx_queues; i++) {
        igb_setup_tx_resources(adapter->tx_ring[i]);
    }
}
```

真正的 RingBuffer 構造過程是在 `igb_setup_tx_resources` 中完成的。

```
//file: drivers/net/ethernet/intel/igb/igb_main.c
int igb_setup_tx_resources(struct igb_ring *tx_ring)
{
    //1.申請 igb_tx_buffer 陣列記憶體
    size = sizeof(struct igb_tx_buffer) * tx_ring->count;
    tx_ring->tx_buffer_info = vzalloc(size);

    //2.申請 e1000_adv_tx_desc DMA 陣列記憶體
    tx_ring->size = tx_ring->count * sizeof(union e1000_adv_tx_desc);
    tx_ring->size = ALIGN(tx_ring->size, 4096);
    tx_ring->desc = dma_alloc_coherent(dev, tx_ring->size,
                       &tx_ring->dma, GFP_KERNEL);

    //3.初始化佇列成員
    tx_ring->next_to_use = 0;
    tx_ring->next_to_clean = 0;
}
```

從上述原始碼可以看到，實際上一個 RingBuffer 的內部不僅僅是一個環形佇列陣列，而是有兩個。

1. `igb_tx_buffer` 陣列：這個陣列是核心使用的，透過 vzalloc 申請的。
2. `e1000_adv_tx_desc` 陣列：這個陣列是網路卡硬體使用的，硬體是可以透過 DMA 直接存取這塊記憶體，透過 `dma_alloc_coherent` 分配。

這個時候它們之間還沒有什麼聯絡。將來在傳送的時候，這兩個環形陣列中相同位置的指標將都將指向同一個 `skb`。這樣，核心和硬體就能共同存取同樣的資料了，核心往 `skb` 裡寫資料，網路卡硬體負責傳送。

最後呼叫 `netif_tx_start_all_queues` 開啟佇列。另外，對於硬中斷的處理函式 `igb_msix_ring` 其實也是在 \_\_igb_open 中註冊的。

## 四、傳送資料真正開始

## 4.1 `send` 系統呼叫 (System Call) 實作

`send` 系統呼叫的原始碼位於檔案 `net/socket.c` 中。在這個系統呼叫裡，內部其實真正使用的是 sendto 系統呼叫。整個呼叫鏈條雖然不短，但其實主要只幹了兩件簡單的事情，

- 第一是在核心中把真正的   `socket` 找出來，在這個物件裡記錄著各種協定堆疊的函式位址。
- 第二是構造一個 struct msghdr 物件，把使用者傳入的資料，例如 buffer 位址、資料長度什麼的，統統都裝進去.

剩下的事情就交給下一層，協定堆疊裡的函式 `inet_sendmsg` 了，其中 `inet_sendmsg` 函式的位址是透過 `socket` 核心物件裡的 ops 成員找到的。大致流程如圖。

有了上面的瞭解，我們再看起原始碼就要容易許多了。原始碼如下：

```
//file: net/socket.c
SYSCALL_DEFINE4(send, int, fd, void __user *, buff, size_t, len,
        unsigned int, flags)
{
    return sys_sendto(fd, buff, len, flags, NULL, 0);
}

SYSCALL_DEFINE6(......)
{
//1.根據 fd 查詢到 socket
sock = sockfd_lookup_light(fd, &err, &fput_needed);

//2.構造 msghdr
struct msghdr msg;
struct iovec iov;

iov.iov_base = buff;
iov.iov_len = len;
msg.msg_iovlen = 1;

msg.msg_iov = &iov;
msg.msg_flags = flags;
......

//3.傳送資料
sock_sendmsg(sock, &msg, len);
}
```

從原始碼可以看到，我們在使用者態 (User Mode) 使用的   `send` 函式和 sendto 函式其實都是 sendto 系統呼叫實作的。`send` 只是為了方便，封裝出來的一個更易於呼叫的方式而已。

在 sendto 系統呼叫裡，首先根據使用者傳進來的   `socket` 控制程式碼號來查詢真正的 `socket` 核心物件。接著把使用者請求的 buff、len、flag 等參數都統統打包到一個 struct msghdr 物件中。

接著呼叫了 `sock_sendmsg`=> \_\_sock_sendmsg ==> \_\_sock_sendmsg_nosec。在\_\_sock_sendmsg_nosec 中，呼叫將會由系統呼叫進入到協定堆疊，我們來看它的原始碼。

```
//file: net/socket.c
static inline int __sock_sendmsg_nosec(...)
{
    ......
    return sock->ops->sendmsg(iocb, sock, msg, size);
}
```

透過第三節裡的   `socket` 核心物件結構圖，我們可以看到，這裡呼叫的是 `sock->ops->sendmsg` 實際執行的是 `inet_sendmsg`。這個函式是 `AF_INET` 協定族提供的通用傳送函式。

## 4.2 傳輸層處理

## 1）傳輸層複製

在進入到協定堆疊 `inet_sendmsg` 以後，核心接著會找到 `socket` 上的具體協定傳送函式。對於 TCP 協定來說，那就是 `tcp_sendmsg`（同樣也是透過   `socket` 核心物件找到的）。

在這個函式中，核心會申請一個核心態的 `skb` 記憶體，將使用者待傳送的資料複製進去。注意這個時候不一定會真正開始傳送，如果沒有達到傳送條件的話很可能這次呼叫直接就回傳了。大概過程如圖：

我們來看 `inet_sendmsg` 函式的原始碼。

```
//file: net/ipv4/af_inet.c
int inet_sendmsg(......)
{
    ......
    return sk->sk_prot->sendmsg(iocb, sk, msg, size);
}
```

在這個函式中會呼叫到具體協定的傳送函式。同樣參考第三節裡的   `socket` 核心物件結構圖，我們看到對於 TCP 協定下的 `socket` 來說，來說 sk-> `sk_prot->sendmsg` 指向的是 `tcp_sendmsg`（對於 UPD 來說是 `udp_sendmsg`）。

`tcp_sendmsg` 這個函式比較長，我們分多次來看它。 先看這一段

```
//file: net/ipv4/tcp.c
int tcp_sendmsg(...)
{
    while(...){
        while(...){
            //取得傳送佇列
            skb = tcp_write_queue_tail(sk);

            //申請skb 並複製
            ......
        }
    }

```

```
//file: include/net/tcp.h
static inline struct sk_buff *tcp_write_queue_tail(const struct sock *sk)
{
    return skb_peek_tail(&sk->sk_write_queue);
}
```

理解對   `socket` 呼叫 `tcp_write_queue_tail` 是理解傳送的前提。如上所示，這個函式是在取得 `socket` 傳送佇列中的最後一個 `skb`。 `skb` 是 struct `sk_buff` 物件的簡稱，使用者的傳送佇列就是該物件組成的一個連結串列。

我們再接著看 `tcp_sendmsg` 的其他部分。

```
這個函式比較長，不過其實邏輯並不複雜。其中 msg->msg_iov 儲存的是使用者態記憶體的要傳送的資料的 buffer。接下來在核心態申請核心記憶體，例如 skb，並把使用者記憶體裡的資料複製到核心態記憶體中。這就會涉及到一次或者幾次記憶體複製的開銷。
```

至於核心什麼時候真正把 `skb` 傳送出去。在 `tcp_sendmsg` 中會進行一些判斷。

```
//file: net/ipv4/tcp.c
int tcp_sendmsg(...)
{
    while(...){
        while(...){
            //申請核心記憶體並進行複製

            //傳送判斷
            if (forced_push(tp)) {
                tcp_mark_push(tp, skb);
                __tcp_push_pending_frames(sk, mss_now, TCP_NAGLE_PUSH);

        }

```

條件都不滿足的話，這次的使用者要傳送的資料只是複製到核心就算完事了！

## 2）傳輸層傳送

假設現在核心傳送條件已經滿足了，我們再來跟蹤一下實際的傳送過程。 對於上小節函式中，當滿足真正傳送條件的時候，無論呼叫的是 \_\_tcp_push_pending_frames 還是 `tcp_push_one` 最終都實際會執行到 `tcp_write_xmit`。

所以我們直接從 `tcp_write_xmit` 看起，這個函式處理了傳輸層的擁塞控制、滑動視窗 (Sliding Window) 相關的工作。滿足視窗要求的時候，設定一下 TCP 頭然後將 `skb` 傳到更低的網路層進行處理。

我們來看下 `tcp_write_xmit` 的原始碼。

```
//file: net/ipv4/tcp_output.c
static bool tcp_write_xmit(struct sock *sk, unsigned int mss_now, int nonagle,
               int push_one, gfp_t gfp)
{
    //迴圈取得待傳送 skb
    while ((skb = tcp_send_head(sk)))
    {
        //滑動視窗相關
        cwnd_quota = tcp_cwnd_test(tp, skb);
        tcp_snd_wnd_test(tp, skb, mss_now);
        tcp_mss_split_point(...);
        tso_fragment(sk, skb, ...);
        ......

        //真正開啟傳送
        tcp_transmit_skb(sk, skb, 1, gfp);
    }
}
```

可以看到我們之前在網路協定裡學的滑動視窗、擁塞控制就是在這個函式中完成的，這部分就不過多展開了，感興趣同學自己找這段原始碼來讀。我們今天只看傳送主過程，那就走到了 `tcp_transmit_skb`。

```
//file: net/ipv4/tcp_output.c
static int tcp_transmit_skb(struct sock *sk, struct sk_buff *skb, int clone_it,
                gfp_t gfp_mask)
{
    //1.克隆新 skb 出來
    if (likely(clone_it)) {
        skb = skb_clone(skb, gfp_mask);
        ......
    }

    //2.封裝 TCP 頭
    th = tcp_hdr(skb);
    th->source        = inet->inet_sport;
    th->dest        = inet->inet_dport;
    th->window        = ...;
    th->urg            = ...;
    ......

    //3.呼叫網路層傳送介面
    err = icsk->icsk_af_ops->queue_xmit(skb, &inet->cork.fl);
}
```

第一件事是先克隆一個新的 `skb`，這裡重點說下為什麼要複製一個 `skb` 出來呢？

是因為 `skb` 後續在呼叫網路層，最後到達網路卡傳送完成的時候，這個 `skb` 會被釋放掉。而我們知道 TCP 協定是支援丟失重傳的，在收到對方的 ACK 之前，這個 `skb` 不能被刪除。所以核心的做法就是每次呼叫網路卡傳送的時候，實際上傳遞出去的是 `skb` 的一個複製。等收到 ACK 再真正刪除。

第二件事是修改 `skb` 中的 TCP header，根據實際情況把 TCP 頭設定好。這裡要介紹一個小技巧，`skb` 內部其實包含了網路協定中所有的 header。在設定 TCP 頭的時候，只是把指標指向 `skb` 的合適位置。後面再設定 IP 頭的時候，在把指標挪一挪就行，避免頻繁的記憶體申請和複製，效率很高。

`tcp_transmit_skb` 是傳送資料位於傳輸層的最後一步，接下來就可以進入到網路層進行下一層的操作了。呼叫了網路層提供的傳送介面 `icsk->icsk_af_ops->queue_xmit`()。

在下面的這個原始碼中，我們的知道了  `queue_xmit` 其實指向的是 `ip_queue_xmit` 函式。

```
//file: net/ipv4/tcp_ipv4.c
const struct inet_connection_sock_af_ops ipv4_specific = {
    .queue_xmit       = ip_queue_xmit,
    .send_check       = tcp_v4_send_check,
    ...
}
```

自此，傳輸層的工作也就都完成了。 資料離開了傳輸層，接下來將會進入到核心在網路層的實作裡。

## 4.3 網路層傳送處理

Linux 核心網路層的傳送的實作位於   `net/ipv4/ip_output.c` 這個檔案。傳輸層呼叫到的 `ip_queue_xmit` 也在這裡。（從檔名上也能看出來進入到 IP 層了，原始檔名已經從 `tcp_xxx` 變成了 `ip_xxx`。）

在網路層裡主要處理路由項查詢、IP 頭設定、netfilter 過濾、`skb` 切分（大於 MTU 的話）等幾項工作，處理完這些工作後會交給更下層的鄰居子系統來處理。

我們來看網路層入口函式 `ip_queue_xmit` 的原始碼：

```
{
    //大於 mtu 的話就要進行分片了
    if (skb->len > ip_skb_dst_mtu(skb) && !skb_is_gso(skb))
        return ip_fragment(skb, ip_finish_output2);
    else
        return ip_finish_output2(skb);
}
```

在   `ip_finish_output` 中我們看到，如果資料大於 MTU 的話，是會執行分片的。

> 實際 MTU 大小確定依賴 MTU 發現，乙太網幀為 1500 位元組。之前 QQ 團隊在早期的時候，會盡量控制自己資料封包尺寸小於 MTU，透過這種方式來最佳化網路效能。因為分片會帶來兩個問題：1、需要進行額外的切分處理，有額外效能開銷。2、只要一個分片丟失，整個包都得重傳。所以避免分片既杜絕了分片開銷，也大大降低了重傳率。

在 `ip_finish_output2` 中，終於傳送過程會進入到下一層，鄰居子系統中。

## 4.4 鄰居子系統

鄰居子系統是位於網路層和資料鏈路層中間的一個系統，其作用是對網路層提供一個封裝，讓網路層不必關心下層的位址資訊，讓下層來決定傳送到哪個 MAC 位址。

而且這個鄰居子系統並不位於協定堆疊   `net/ipv4`/ 目錄內，而是位於 `net/core/neighbour.c`。因為無論是對於 IPv4 還是 IPv6 ，都需要使用該模組。

在鄰居子系統裡主要是查詢或者建立鄰居項，在創造鄰居項的時候，有可能會發出實際的 arp 請求。然後封裝一下 MAC 頭，將傳送過程再傳遞到更下層的網路裝置子系統。大致流程如圖。

理解了大致流程，我們再回頭看原始碼。在上面小節 `ip_finish_output2` 原始碼中呼叫了 \_\_ipv4_neigh_lookup_noref。它是在 arp 快取中進行查詢，其第二個參數傳入的是路由下一跳 IP 資訊。

```
//file: include/net/arp.h
extern struct neigh_table arp_tbl;
static inline struct neighbour *__ipv4_neigh_lookup_noref(
    struct net_device *dev, u32 key)
{
    struct neigh_hash_table *nht = rcu_dereference_bh(arp_tbl.nht);

    //計算 hash 值，加速查詢
    hash_val = arp_hashfn(......);
    for (n = rcu_dereference_bh(nht->hash_buckets[hash_val]);
         n != NULL;
         n = rcu_dereference_bh(n->next)) {
        if (n->dev == dev && *(u32 *)n->primary_key == key)
            return n;
    }
}
```

如果查詢不到，則呼叫 \_\_neigh_create 建立一個鄰居。


```
//file: net/sched/sch_generic.c
void __qdisc_run(struct Qdisc *q)
{
    int quota = weight_p;

    //迴圈從佇列取出一個 skb 併傳送
    while (qdisc_restart(q)) {

        // 如果發生下面情況之一，則延後處理：
        // 1. quota 用盡
        // 2. 其他程序需要 CPU
        if (--quota <= 0 || need_resched()) {
            //將觸發一次 NET_TX_SOFTIRQ 型別 softirq
            __netif_schedule(q);
            break;
        }
    }
}
```

在上述程式碼中，我們看到 while 迴圈不斷地從佇列中取出 `skb` 並進行傳送。注意，這個時候其實都佔用的是使用者程序的系統態時間 (sy)。 只有當 quota 用盡或者其他程序需要 CPU 的時候才觸發軟中斷進行傳送。

所以這就是為什麼一般伺服器上檢視 `/proc/softirqs`，一般   `NET_RX` 都要比 `NET_TX` 大的多的第二個原因。對於讀來說，都是要經過 `NET_RX` 軟中斷，而對於傳送來說，只有系統態配額用盡才讓軟中斷上。

## 4.6 軟中斷排程

在 4.5 我們看到了如果系統態 CPU 傳送網路封包不夠用的時候，會呼叫 \_\_netif_schedule 觸發一個軟中斷。該函式會進入到 \_\_netif_reschedule，由它來實際發出   `NET_TX_SOFTIRQ` 型別軟中斷。

軟中斷是由核心執行緒 (Thread) 來執行的，該執行緒會進入到 `net_tx_action` 函式，在該函式中能取得到傳送佇列，並也最終呼叫到驅動程式裡的入口函式 `dev_hard_start_xmit`。

```
//file: net/core/dev.c
static inline void __netif_reschedule(struct Qdisc *q)
{
    sd = &__get_cpu_var(softnet_data);
    q->next_sched = NULL;
    *sd->output_queue_tailp = q;
    sd->output_queue_tailp = &q->next_sched;

    ......
    raise_softirq_irqoff(NET_TX_SOFTIRQ);
}
```

在該函式里在軟中斷能存取到的   `softnet_data` 裡設定了要傳送的資料佇列，新增到了 `output_queue` 裡了。緊接著觸發了 `NET_TX_SOFTIRQ` 型別的軟中斷。（T 代表 transmit 傳輸）

軟中斷的入口程式碼我這裡也不詳細扒了，感興趣的同學參考 [《圖解 Linux 網路封包接收過程》](https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg) 一文中的 3.2 小節 - ksoftirqd 核心執行緒處理軟中斷。

我們直接從 `NET_TX_SOFTIRQ` softirq 註冊的回呼函式 `net_tx_action` 講起。使用者態程序觸發完軟中斷之後，會有一個軟中斷核心執行緒會執行到 `net_tx_action`。

牢記，這以後傳送資料消耗的 CPU 就都顯示在 si 這裡了，不會消耗使用者程序的系統時間了。

```
//file: net/core/dev.c
static void net_tx_action(struct softirq_action *h)
{
    //透過 softnet_data 取得傳送佇列
    struct softnet_data *sd = &__get_cpu_var(softnet_data);

    // 如果 output queue 上有 qdisc
    if (sd->output_queue) {

        // 將 head 指向第一個 qdisc
        head = sd->output_queue;

        //遍歷 qdsics 列表
        while (head) {
            struct Qdisc *q = head;
            head = head->next_sched;

            //傳送資料
            qdisc_run(q);
        }
    }
}

軟中斷這裡會取得   softnet_data。前面我們看到程序核心態在呼叫 \_\_netif_reschedule 的時候把傳送佇列寫到 softnet_data 的 output_queue 裡了。 軟中斷迴圈遍歷 sd-> output_queue 傳送資料幀。
```

## 4.7 igb 網路卡驅動傳送

我們前面看到，無論是對於使用者程序的核心態，還是對於軟中斷上下文，都會呼叫到網路裝置子系統中的 `dev_hard_start_xmit` 函式。在這個函式中，會呼叫到驅動裡的傳送函式 `igb_xmit_frame`。

## 最後

用一張圖總結一下整個傳送過程

瞭解了整個傳送過程以後，我們回頭再來回顧開篇提到的幾個問題。

1. 我們在監控核心傳送資料消耗的 CPU 時，是應該看 sy 還是 si ？

在網路封包的傳送過程中，使用者程序完成了絕大部分的工作，甚至連呼叫驅動的事情都幹了。 只有當核心態程序被切走前才會發起軟中斷。 傳送過程中，絕大部分（90%）以上的開銷都是在使用者程序核心態消耗掉的。

只有一少部分情況下才會觸發軟中斷，由軟中斷 ksoftirqd 核心程序來傳送。

所以，在監控網路 IO 對伺服器造成的 CPU 開銷的時候，不能僅僅只看 si，而是應該把 si、sy 都考慮進來。

2. 在伺服器上檢視 `/proc/softirqs`，為什麼   `NET_RX` 要比 `NET_TX` 大的多的多？

之前我認為   `NET_RX` 是讀取，`NET_TX` 是傳輸。對於一個既收取使用者請求，又給使用者回傳的 Server 來說。 這兩塊的數字應該差不多才對，至少不會有數量級的差異。但事實上，飛哥手頭的一臺伺服器是這樣的：

經過今天的原始碼分析，發現這個問題的原因有兩個。

第一個原因是當資料傳送完成以後，透過硬中斷的方式來通知驅動傳送完畢。但是硬中斷無論是有資料接收，還是對於傳送完畢，觸發的軟中斷都是   `NET_RX_SOFTIRQ`，而並不是 `NET_TX_SOFTIRQ`。

第二個原因是對於讀來說，都是要經過   `NET_RX` 軟中斷的，都走 ksoftirqd 核心程序。而對於傳送來說，絕大部分工作都是在使用者程序核心態處理了，只有系統態配額用盡才會發出 `NET_TX`，讓軟中斷上。

綜上兩個原因，那麼在機器上檢視   `NET_RX` 比 `NET_TX` 大的多就不難理解了。

3. 傳送網路資料的時候都涉及到哪些記憶體複製操作？

這裡的記憶體複製，我們只特指待傳送資料的記憶體複製。

第一次複製操作是核心申請完 `skb` 之後，這時候會將使用者傳遞進來的 buffer 裡的資料內容都複製到 `skb` 中。如果要傳送的資料量比較大的話，這個複製操作開銷還是不小的。

第二次複製操作是從傳輸層進入網路層的時候，每一個 `skb` 都會被克隆一個新的副本出來。網路層以及下面的驅動、軟中斷等元件在傳送完成的時候會將這個副本刪除。傳輸層儲存著原始的 `skb`，在當網路對方沒有 ack 的時候，還可以重新傳送，以實作 TCP 中要求的可靠傳輸。

第三次複製不是必須的，只有當 IP 層發現 `skb` 大於 MTU 時才需要進行。會再申請額外的 `skb`，並將原來的 `skb` 複製為多個小的 `skb`。

> 這裡插入個題外話，大家在網路效能最佳化中經常聽到的零複製，我覺得這有點點誇張的成分。TCP 為了保證可靠性，第二次的複製根本就沒法省。如果包再大於 MTU 的話，分片時的複製同樣也避免不了。
