一、Linux 網路傳送過程總覽

二、網絡卡啟動準備

現在的伺服器上的網絡卡一般都是支援多佇列的。每一個佇列上都是由一個 RingBuffer 表示的，開啟了多佇列以後的的網絡卡就會對應有多個 RingBuffer。

網絡卡在啟動時最重要的任務之一就是分配和初始化 RingBuffer，理解了 RingBuffer 將會非常有助於後面我們掌握髮送。因為今天的主題是傳送，所以就以傳輸佇列為例，我們來看下網絡卡啟動時分配 RingBuffer 的實際過程。

在網絡卡啟動的時候，會呼叫到 \_\_igb_open 函式，RingBuffer 就是在這裡分配的。

在上面 \_\_igb_open 函式呼叫 igb_setup_all_tx_resources 分配所有的傳輸 RingBuffer, 呼叫 igb_setup_all_rx_resources 建立所有的接收 RingBuffer。

真正的 RingBuffer 構造過程是在 igb_setup_tx_resources 中完成的。

從上述原始碼可以看到，實際上一個 RingBuffer 的內部不僅僅是一個環形佇列陣列，而是有兩個。

1）igb_tx_buffer 陣列：這個陣列是核心使用的，透過 vzalloc 申請的。 2）e1000_adv_tx_desc 陣列：這個陣列是網絡卡硬體使用的，硬體是可以透過 DMA 直接訪問這塊記憶體，透過 dma_alloc_coherent 分配。

這個時候它們之間還沒有啥聯絡。將來在傳送的時候，這兩個環形陣列中相同位置的指標將都將指向同一個 skb。這樣，核心和硬體就能共同訪問同樣的資料了，核心往 skb 裡寫資料，網絡卡硬體負責傳送。

最後呼叫 netif_tx_start_all_queues 開啟佇列。另外，對於硬中斷的處理函式 igb_msix_ring 其實也是在 \_\_igb_open 中註冊的。

四、傳送資料真正開始

4.2 傳輸層處理

所以我們直接從 tcp_write_xmit 看起，這個函式處理了傳輸層的擁塞控制、滑動視窗相關的工作。滿足視窗要求的時候，設定一下 TCP 頭然後將 skb 傳到更低的網路層進行處理。

我們來看下 tcp_write_xmit 的原始碼。

可以看到我們之前在網路協議裡學的滑動視窗、擁塞控制就是在這個函式中完成的，這部分就不過多展開了，感興趣同學自己找這段原始碼來讀。我們今天只看傳送主過程，那就走到了 tcp_transmit_skb。

第一件事是先克隆一個新的 skb，這裡重點說下為什麼要複製一個 skb 出來呢？

是因為 skb 後續在呼叫網路層，最後到達網絡卡傳送完成的時候，這個 skb 會被釋放掉。而我們知道 TCP 協議是支援丟失重傳的，在收到對方的 ACK 之前，這個 skb 不能被刪除。所以核心的做法就是每次呼叫網絡卡傳送的時候，實際上傳遞出去的是 skb 的一個複製。等收到 ACK 再真正刪除。

第二件事是修改 skb 中的 TCP header，根據實際情況把 TCP 頭設定好。這裡要介紹一個小技巧，skb 內部其實包含了網路協議中所有的 header。在設定 TCP 頭的時候，只是把指標指向 skb 的合適位置。後面再設定 IP 頭的時候，在把指標挪一挪就行，避免頻繁的記憶體申請和複製，效率很高。

tcp_transmit_skb 是傳送資料位於傳輸層的最後一步，接下來就可以進入到網路層進行下一層的操作了。呼叫了網路層提供的傳送介面icsk->icsk_af_ops->queue_xmit()。

在下面的這個原始碼中，我們的知道了 queue_xmit 其實指向的是 ip_queue_xmit 函式。

自此，傳輸層的工作也就都完成了。 資料離開了傳輸層，接下來將會進入到核心在網路層的實現裡。

4.4 鄰居子系統

鄰居子系統是位於網路層和資料鏈路層中間的一個系統，其作用是對網路層提供一個封裝，讓網路層不必關心下層的地址資訊，讓下層來決定傳送到哪個 MAC 地址。

而且這個鄰居子系統並不位於協議棧 net/ipv4/ 目錄內，而是位於 net/core/neighbour.c。因為無論是對於 IPv4 還是 IPv6 ，都需要使用該模組。

在鄰居子系統裡主要是查詢或者建立鄰居項，在創造鄰居項的時候，有可能會發出實際的 arp 請求。然後封裝一下 MAC 頭，將傳送過程再傳遞到更下層的網路裝置子系統。大致流程如圖。

如果查詢不到，則呼叫 \_\_neigh_create 建立一個鄰居。

有了鄰居項以後，此時仍然還不具備傳送 IP 報文的能力，因為目的 MAC 地址還未獲取。 呼叫 dst_neigh_output 繼續傳遞 skb。

4.5 網路裝置子系統

鄰居子系統透過 dev_queue_xmit 進入到網路裝置子系統中來。

開篇第二節網絡卡啟動準備裡我們說過，網絡卡是有多個傳送佇列的（尤其是現在的網絡卡）。上面對 netdev_pick_tx 函式的呼叫就是選擇一個佇列進行傳送。

netdev_pick_tx 傳送佇列的選擇受 XPS 等配置的影響，而且還有快取，也是一套小複雜的邏輯。這裡我們只關注兩個邏輯，首先會獲取使用者的 XPS 配置，否則就自動計算了。程式碼見 netdev_pick_tx => \_\_netdev_pick_tx。

然後獲取與此佇列關聯的 qdisc。在 linux 上透過 tc 命令可以看到 qdisc 型別，例如對於我的某臺多佇列網絡卡機器上是 mq disc。

大部分的裝置都有佇列（迴環裝置和隧道裝置除外），所以現在我們進入到 \_\_dev_xmit_skb。

所以這就是為什麼一般伺服器上檢視 /proc/softirqs，一般 NET_RX 都要比 NET_TX 大的多的第二個原因 。對於讀來說，都是要經過 NET_RX 軟中斷，而對於傳送來說，只有系統態配額用盡才讓軟中斷上。

4.6 軟中斷排程

在 4.5 咱們看到了如果系統態 CPU 傳送網路包不夠用的時候，會呼叫 \_\_netif_schedule 觸發一個軟中斷。該函式會進入到 \_\_netif_reschedule，由它來實際發出 NET_TX_SOFTIRQ 型別軟中斷。

軟中斷是由核心執行緒來執行的，該執行緒會進入到 net_tx_action 函式，在該函式中能獲取到傳送佇列，並也最終呼叫到驅動程式裡的入口函式 dev_hard_start_xmit。

在該函式里在軟中斷能訪問到的 softnet_data 裡設定了要傳送的資料佇列，新增到了 output_queue 裡了。緊接著觸發了 NET_TX_SOFTIRQ 型別的軟中斷。（T 代表 transmit 傳輸）

軟中斷的入口程式碼我這裡也不詳細扒了，感興趣的同學參考 《圖解Linux網路包接收過程》 一文中的 3.2 小節 - ksoftirqd核心執行緒處理軟中斷。

我們直接從 NET_TX_SOFTIRQ softirq 註冊的回撥函式 net_tx_action講起。使用者態程序觸發完軟中斷之後，會有一個軟中斷核心執行緒會執行到 net_tx_action。

牢記，這以後傳送資料消耗的 CPU 就都顯示在 si 這裡了，不會消耗使用者程序的系統時間了 。

軟中斷這裡會獲取 softnet_data。前面我們看到程序核心態在呼叫 \_\_netif_reschedule 的時候把傳送佇列寫到 softnet_data 的 output_queue 裡了。 軟中斷迴圈遍歷 sd->output_queue 傳送資料幀。

來看 qdisc_run，它和程序使用者態一樣，也會呼叫到 \_\_qdisc_run。

然後一樣就是進入 qdisc_restart => sch_direct_xmit，直到驅動程式函式 dev_hard_start_xmit。

最後

用一張圖總結一下整個傳送過程

瞭解了整個傳送過程以後，我們回頭再來回顧開篇提到的幾個問題。

1.我們在監控核心傳送資料消耗的 CPU 時，是應該看 sy 還是 si ？

在網路包的傳送過程中，使用者程序（在核心態）完成了絕大部分的工作，甚至連呼叫驅動的事情都幹了。 只有當核心態程序被切走前才會發起軟中斷。 傳送過程中，絕大部分（90%）以上的開銷都是在使用者程序核心態消耗掉的。

只有一少部分情況下才會觸發軟中斷（NET_TX 型別），由軟中斷 ksoftirqd 核心程序來傳送。

所以，在監控網路 IO 對伺服器造成的 CPU 開銷的時候，不能僅僅只看 si，而是應該把 si、sy 都考慮進來。

2. 在伺服器上檢視 /proc/softirqs，為什麼 NET_RX 要比 NET_TX 大的多的多？

之前我認為 NET_RX 是讀取，NET_TX 是傳輸。對於一個既收取使用者請求，又給使用者返回的 Server 來說。 這兩塊的數字應該差不多才對，至少不會有數量級的差異。但事實上，飛哥手頭的一臺伺服器是這樣的：

經過今天的原始碼分析，發現這個問題的原因有兩個。

第一個原因是當資料傳送完成以後，透過硬中斷的方式來通知驅動傳送完畢。但是硬中斷無論是有資料接收，還是對於傳送完畢，觸發的軟中斷都是 NET_RX_SOFTIRQ，而並不是 NET_TX_SOFTIRQ。

第二個原因是對於讀來說，都是要經過 NET_RX 軟中斷的，都走 ksoftirqd 核心程序。而對於傳送來說，絕大部分工作都是在使用者程序核心態處理了，只有系統態配額用盡才會發出 NET_TX，讓軟中斷上。

綜上兩個原因，那麼在機器上檢視 NET_RX 比 NET_TX 大的多就不難理解了。

3.傳送網路資料的時候都涉及到哪些記憶體複製操作？

這裡的記憶體複製，我們只特指待傳送資料的記憶體複製。

第一次複製操作是核心申請完 skb 之後，這時候會將使用者傳遞進來的 buffer 裡的資料內容都複製到 skb 中。如果要傳送的資料量比較大的話，這個複製操作開銷還是不小的。

第二次複製操作是從傳輸層進入網路層的時候，每一個 skb 都會被克隆一個新的副本出來。網路層以及下面的驅動、軟中斷等元件在傳送完成的時候會將這個副本刪除。傳輸層儲存著原始的 skb，在當網路對方沒有 ack 的時候，還可以重新傳送，以實現 TCP 中要求的可靠傳輸。

第三次複製不是必須的，只有當 IP 層發現 skb 大於 MTU 時才需要進行。會再申請額外的 skb，並將原來的 skb 複製為多個小的 skb。
