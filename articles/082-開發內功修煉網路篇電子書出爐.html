飛哥的開發內功修煉技術號更新文章有一年多了，以前的文章都是單獨介紹一個技術點，沒給大家一個整體的視角。所以有的讀者讀到個別文章的時候難免就會有困惑。

比如我曾經寫過的 說出來你可能不信，核心這傢伙在記憶體的使用上給自己開了個小灶！ 。有的讀者就納悶了，你研究核心使用記憶體這麼深，工作中有啥用麼。

今天我就來說一下我的創作整體思路。我在選題的時候，並不是想到啥就寫啥的，而且很早就有一個規劃。拿網路篇來說，可以用一個短句來概括這個規劃，那就是 理解網路效能 。在確定了研究目標以後，我對任務進行了拆解，把效能拆分為 三個角度：CPU 開銷、記憶體開銷、時間開銷 。

具體到某個角度比如 CPU，那我需要給自己解釋清楚網路包是怎麼從網絡卡到核心中的，核心又是透過哪些方式通知程序的。只有理解清楚了這些才能真正把握網路對 CPU 的消耗。

對於記憶體角度也是一樣，只有理解了核心是如何使用記憶體，甚至需要哪些核心物件都搞清楚，也才能真正理解一條 TCP 連線的記憶體開銷。

飛哥把之前網路篇相關的所有文章都做了個彙總，也新增了部分新內容比如效能最佳化建議和前沿技術展望等，整理出了一本電子書。我給它起了個名字叫 《理解了實現再談網路效能》 。在這本電子書裡，你將能更清晰看到我的整體思路，也將能更深入地把握網路效能開銷。

今天在這裡我把這本《理解了實現再談網路效能》獻給大家， 在文末介紹電子書的獲取方式。

修煉技術內功有啥好處

先容許我多扯一點。我在我的技術群裡看到有的同學說他去面試，遇到面試官說：“你是來面 PHP 的，懂 IO 多路複用這玩意兒有啥用！”。我只能說這個面試官一定自己的技術級別也不高，只懂得 CURD 之類的技術。如果是高階別的開發連 IO 多路複用是啥都不懂，以後專案中網路遇到瓶頸怎麼最佳化，遇到高併發怎麼樣選擇更優秀的技術方案。

我覺得目前大多數的業界的技術學習都太偏向於各種花拳繡腿了，太缺乏對內功的重視，上面的面試官就是一個典型的例子。

高效能的 PHP 非同步網路通訊引擎 swoole 的作者韓天峰說過，很多程式設計師職業規劃的文章，上來就是 Linux、PHP、MySQL、Nginx、Redis、Memcache、jQuery 這些，然後就直接上手搭環境、做專案，中級就是學習各種 PHP 框架和類庫，高階階段就是 MySQL 最佳化、PHP 核心與擴充套件、架構設計這些了。這些文章都存在一個嚴重的缺陷，不重視基礎。就好比練武功，只求速成，不修煉內功和心法，只練各種招式，這樣練出來的高手能高到哪裡去？

事實上，碼農圈裡的牛人比如韓天峰，比如 PHP7 作者鳥哥，他們都具備非常非常紮實的基礎，他們之所以牛，並不是他們掌握的花拳繡腿的功夫多，而是內功非常非常深厚。舉個小例子，鳥哥在 PHP7 中把 HashTable 結構體從 72 位元組壓縮到了 56 位元組，表面看起來不大的最佳化，實際上是數倍的效能提升。因為 CPU 在向記憶體要資料的時候是以 Cache Line 為單位進行的，一個 Cache Line 是 64 位元組。56 位元組可以一次請求搞定，而原來的 72 位元組則需要兩次。另外就是 L1/L2/L3 的命中率也會提升很多，這個對效能的幫助更大。顯然鳥哥深諳 CPU 的工作原理。

內功它不幫助你掌握最新的開發語言，也不教會你時髦的框架，也不會帶你走進火熱的人工智慧。但是我相信它是你成為大牛的必經之路。我簡單列一下鍛鍊內功的好處：

1） 內功方面的技術生命週期長 。Linux 作業系統 1991 年就釋出了，現在還是發展的如日中天。對於作者 Linus，我覺得他也有年齡焦慮。但他可能焦慮的找不到合適的接班人。反觀應用層的一些技術尤其是很多的框架，生命週期能超過十年我就已經覺得他很牛叉了。如果你的精力全部押寶在這些生命週期很短的技術上，你說能不焦慮嗎！所以我覺得戒掉浮躁，踏踏實實練好內功是你對抗中年焦慮的解藥之一。

2） 內功深厚的人理解新技術非常快 。不用說業界的各位大牛，就拿我自己來舉兩個小例子。我其實還沒怎麼去翻過 kafka 的原始碼。但是當我研究完了核心是如何讀取檔案的、核心處理網路包的整體過程後，就秒懂了 kafka 在網路這塊為啥效能表現很突出了。另外一個是當我理解了 epoll 的內部實現以後，回頭再看 Golang 的 net 包，才切切實實看懂了地球上絕頂精妙的對網路 IO 的封裝。所以 Linux 核心你真的弄懂了的話，再看應用層的各種新技術就猶如帶了透視鏡一般，直接看到骨骼。

3） 核心提供了優秀系統設計的例項 。Linux 作為一個千錘百煉的系統，其中蘊含了大量的世界頂級的設計和實現方案。平時我們在自己的業務開發中，在編碼之前也需要先進行設計。比如我在剛工作的時候負責的一個資料採集任務排程，其中的實現就是部分參考了作業系統程序排程方案。再比如如何在管理海量的連線，epoll 內部的紅黑樹 + 就緒佇列的組合可以提供給你一個很好的參考。這種例子還有很多很多，總之如果能將 Linux 的某些優秀實現，搬到你的系統中會極大提升你的專案的實現水平。

4） 對效能的把握更到位 。如果不具備紮實的內功對效能問題很難理解到本質。一般工作幾年的同學憑經驗能知道 A 快 B 慢，但為啥 A 快，還是不清楚！如果理解底層是怎麼運作的，你對效能的把握會更到位、工作中做效能最佳化才不底虛、做技術方案選型的時候也更得心應手！

時髦的東西終究會過時，但紮實的內功能力將會伴隨你的一生。 只有具備了深厚的內功底蘊，你才能在你的發展道路上走的更穩、走的更遠。

內功修煉網路篇誕生記

我曾經聽到過有的人說，學習網路就是在學習各種協議，這種說法其實誤導了很多的人。提到計算機網路的知識點，你肯定也首先想到的是 OSI 七層模型、IP、TCP、UDP，HTTP。關於 TCP 再多一點你也會想到三次握手、四次揮手、滑動視窗、流量控制。關於 HTTP 協議就是報文格式、 GET/POST，狀態碼、Cookie/Session 等等。

這些東西確實很有用，但是我的這些知識卻不能幫我清除我在工作實踐中的如下幾個疑惑。

1）有一次我們運維找過來，說某某幾臺線上機器上出現了 3 萬多個 TIME_WAIT，不行了得趕緊處理哈。後來他幫我們開啟了 tcp_tw_reuse 和 tcp_tw_recycle，先把問題處理掉了。 但是我的思考卻並沒有停止， 一條 TIME_WAIT 到底會有哪些開銷 。埠占用導致新連線無法建立？還是會過多消耗機器上的記憶體？ 3 萬條 TIME_WAIT 究竟該算是 warning 還是 error？

2）另外一次是當時公司還沒有建立 redis 平臺之前，我們業務自己維護了一組 redis server 。為了節約握手開銷，我們的業務程序對 redis 開啟了長連線。這樣一個 redis 例項上最終就出現了 6000 條的連線。雖然每條連線上大部分時間都是空閒的，但是我卻在思考 一條空閒的連線究竟會有哪些開銷 ？這 6000 條連線會不會把伺服器搞壞？ 當然最終觀測的結果是沒啥問題，但是對於細節原理我仍然吃的不是很準。

3）另外一次也是我們業務要把短連線最佳化成長連線。但是這次涉及到了要訪問公司的 Mysql 平臺。當時我們公司的 Mysql 需要為每一個 ip 申請一個併發數。因為我們當時使用的是 php-fpm，沒有連線池的概念。所以我們有多少個 fpm 程序，就得申請多大的併發數，我們當時申請了 200 個。 然後工程部的同學就過來 PK 了，你們這單機 200 個併發不行，太高了。雖然我最終給他舉了上面 redis 的例子，最終他同意了。雖然勉強說服了他，但是我仍然吃不準空閒的 tcp 連線到底開銷在哪兒？

經過以上各種實踐問題的磨鍊，我發現了問題的關鍵所在。那就是 我們大家之前對於計算機網路的知識太多都聚集於協議層面了，太過於偏向理論。而對於網路在機器是如何被實現的，開銷如何，卻理解太少太少了。 網路是如何使用 cpu 的，如何使用記憶體的，這些知識感覺在整個業界說很匱乏也不為過。

舉個小例子，按理說現在整個業界都在講高併發，那一臺伺服器到底能支援多少條 TCP 連線，這算是高併發裡很基礎的問題了吧。但是當我產生以上疑問以後，在網上、在各種經典書裡，都根本搜不到能讓我滿意的答案。很多文章都是含含糊糊講了半天 ，討論了半天的 CxxxK。但看完還是不知道最多能支援多少，更別說具體點的細節了，比如一條 TCP 到底需要消耗多大記憶體。

所以，飛哥下定決心，要在實現層面把計算機網路扒個底兒朝天，把網路的 cpu 開銷，記憶體開銷要徹底搞搞清楚！

開發內功修煉網路篇系列文章就是出於這個背景產生的，進而也誕生出了今天的《理解了實現再談網路效能》！
