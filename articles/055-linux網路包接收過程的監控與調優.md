# Linux網路包接收過程的監控與調優

> 原文標題：Linux网络包接收过程的监控与调优

> 原文連結：http://kfngxl.cn/index.php/archives/178/

---

上一篇文章中《圖解Linux網路包接收過程》，我們梳理了在Linux系統下一個資料包被接收的整個過程。Linux核心對網路包的接收過程大致可以分為接收到RingBuffer、硬中斷處理、ksoftirqd軟中斷處理幾個過程。其中在ksoftirqd軟中斷處理中，把資料包從RingBuffer中摘下來，送到協議棧的處理，再之後送到使用者程序socket的接收佇列中。

理解了Linux工作原理之後，還有更重要的兩件事情。第一是動手監控，會實際檢視網路包接收的整體情況。第二是調優，當你的伺服器有問題的時候，你能找到瓶頸所在，並會利用核心開放的引數進行調節。

先說幾個工具

在正式內容開始之前，我們先來了解幾個Linux下監控網絡卡時可用的工具。

ethtool

首先第一個工具就是我們在上文中提到的 ethtool ，它用來檢視和設定網絡卡引數。這個工具其實本身只是提供幾個通用介面，真正的實現是都是在網絡卡驅動中的。正因為該工具是由驅動直接實現的，所以個人覺得它最重要。

該命令比較複雜，我們選幾個今天能用到的說

-i 顯示網絡卡驅動的資訊，如驅動的名稱、版本等

-S 檢視網絡卡收發包的統計情況

-g/-G 檢視或者修改RingBuffer的大小

-l/-L 檢視或者修改網絡卡佇列數

-c/-C 檢視或者修改硬中斷合併策略

實際檢視一下網絡卡驅動：

這裡看到我的機器上網絡卡驅動程式是ixgbe。有了驅動名稱，就可以在原始碼中找到對應的程式碼了。對於 ixgbe 來說，其驅動的原始碼位於 drivers/net/ethernet/intel/ixgbe 目錄下。 ixgbe_ethtool.c 下都是實現的供ethtool使用的相關函式，如果ethtool哪裡有搞不明白的，就可以透過這種方式查詢到原始碼來讀。另外我們前文《圖解Linux網路包接收過程》裡提到的NAPI收包時的poll回撥函式，啟動網絡卡時的open函式都是在這裡實現的。

ifconfig

網路管理工具ifconfig不只是可以為網絡卡配置ip，啟動或者禁用網絡卡，也包含了一些網絡卡的統計資訊。

RX packets：接收的總包數

RX bytes：接收的位元組數

RX errors：表示總的收包的錯誤數量

RX dropped：資料包已經進入了 Ring Buffer，但是由於其它原因導致的丟包

RX overruns：表示了 fifo 的 overruns，這是由於 Ring Buffer不足導致的丟包

偽檔案系統/proc

Linux 核心提供了 /proc 偽檔案系統，透過/proc可以檢視核心內部資料結構、改變核心設定。我們先跑一下題，看一下這個偽檔案系統裡都有啥：

/proc/sys 目錄可以檢視或修改核心引數

/proc/cpuinfo 可以檢視CPU資訊

/proc/meminfo 可以檢視記憶體資訊

/proc/interrupts 統計所有的硬中斷

/proc/softirqs 統計的所有的軟中斷資訊

/proc/slabinfo 統計了核心資料結構的slab記憶體使用情況

/proc/net/dev 可以看到一些網絡卡統計資料

詳細聊下偽檔案 /proc/net/dev ，透過它可以看到核心中對網絡卡的一些相關統計。包含了以下資訊：

bytes: 傳送或接收的資料的總位元組數

packets: 介面傳送或接收的資料包總數

errs: 由裝置驅動程式檢測到的傳送或接收錯誤的總數

drop: 裝置驅動程式丟棄的資料包總數

fifo: FIFO緩衝區錯誤的數量

frame: The number of packet framing errors.（分組幀錯誤的數量）

colls: 介面上檢測到的衝突數

所以，偽檔案 /proc/net/dev 也可以作為我們檢視網絡卡工作統計資料的工具之一。

偽檔案系統sysfs

sysfs和/proc類似，也是一個偽檔案系統，但是比proc更新，結構更清晰。 其中的 /sys/class/net/eth0/statistics/ 也包含了網絡卡的統計資訊。

好了，簡單瞭解過這幾個工具以後，讓我們正式開始今天的行程。

RingBuffer監控與調優

前面我們看到，當網線中的資料幀到達網絡卡後，第一站就是RingBuffer（網絡卡透過DMA機制將資料幀送到RingBuffer中）。因此我們第一個要監控和調優的就是網絡卡的RingBuffer，我們使用 ethtool 來來檢視一下Ringbuffer。

這裡看到我手頭的網絡卡設定RingBuffer最大允許設定到4096，目前的實際設定是512。

在Linux的整個網路棧中，RingBuffer起到一個任務的收發中轉站的角色。對於接收過程來講，網絡卡負責往RingBuffer中寫入收到的資料幀，ksoftirqd核心執行緒負責從中取走處理。只要ksoftirqd執行緒工作的足夠快，RingBuffer這個中轉站就不會出現問題。但是我們設想一下，假如某一時刻，瞬間來了特別多的包，而ksoftirqd處理不過來了，會發生什麼？這時RingBuffer可能瞬間就被填滿了，後面再來的包網絡卡直接就會丟棄，不做任何處理！

那我們怎麼樣能看一下，我們的伺服器上是否有因為這個原因導致的丟包呢？ 前面我們介紹的四個工具都可以檢視這個丟包統計，拿 ethtool 來舉例：

rx_fifo_errors如果不為0的話（在 ifconfig 中體現為 overruns 指標增長），就表示有包因為RingBuffer裝不下而被丟棄了。那麼怎麼解決這個問題呢？很自然首先我們想到的是，加大RingBuffer這個“中轉倉庫”的大小。透過ethtool就可以修改。

這樣網絡卡會被分配更大一點的”中轉站“，可以解決偶發的瞬時的丟包。不過這種方法有個小副作用，那就是排隊的包過多會增加處理網路包的延時。所以另外一種解決思考更好，。那就是讓核心處理網路包的速度更快一些，而不是讓網路包傻傻地在RingBuffer中排隊。怎麼加快核心消費RingBuffer中任務的速度呢，彆著急，我們繼續往下看...

smp_affinity 裡是CPU的親和性的繫結，8是二進位制的1000,第4位為1，代表的就是第4個CPU核心-CPU3。

2）對於收包來過程來講，硬中斷的總次數表示的是Linux收包總數嗎？ 不是，硬體中斷次數不代表總的網路包數。第一網絡卡可以設定中斷合併，多個網路幀可以只發起一次中斷。第二NAPI 執行的時候會關閉硬中斷，透過poll來收包。

多佇列網絡卡調優

現在的主流網絡卡基本上都是支援多佇列的，我們可以透過將不同的佇列分給不同的CPU核心來處理，從而加快Linux核心處理網路包的速度。這是最為有用的一個最佳化手段。

每一個佇列都有一箇中斷號，可以獨立向某個CPU核心發起硬中斷請求，讓CPU來 poll 包。透過將接收進來的包被放到不同的記憶體佇列裡，多個CPU就可以同時分別向不同的佇列發起消費了。這個特性叫做RSS（Receive Side Scaling，接收端擴充套件）。透過 ethtool 工具可以檢視網絡卡的佇列情況。

上述結果表示當前網絡卡支援的最大佇列數是63，當前開啟的佇列數是8。對於這個配置來講，最多同時可以有8個核心來參與網路收包。如果你想提高核心收包的能力，直接簡單加大佇列數就可以了，這比加大RingBuffer更為有用。因為加大RingBuffer只是給個更大的空間讓網路幀能繼續排隊，而加大佇列數則能讓包更早地被核心處理。 ethtool 修改佇列數量方法如下：

我們前文說過，硬中斷髮生在哪一個核上，它發出的軟中斷就由哪個核來處理。所有透過加大網絡卡佇列數，這樣硬中斷工作、軟中斷工作都會有更多的核心參與進來。

一般處理到這裡，網路包的接收就沒有大問題了。但如果你有更高的追求，或者是說你並沒有更多的CPU核心可以參與進來了，那怎麼辦？放心，我們也還有方法提高單核的處理網路包的接收速度。

硬中斷合併

先來講一個實際中的例子，假如你是一位開發同學，和你對口的產品經理一天有10個小需求需要讓你幫忙來處理。她對你有兩種中斷方式：

第一種：產品經理想到一個需求，就過來找你，和你描述需求細節，然後讓你幫你來改

第二種：產品經理想到需求後，不來打擾你，等攢夠5個來找你一次，你集中處理

我們現在不考慮及時性，只考慮你的工作整體效率，你覺得那種方案下你的工作效率會高呢？或者換句話說，你更喜歡哪一種工作狀態呢？很明顯，只要你是一個正常的開發，都會覺得第二種方案更好。對人腦來講，頻繁的中斷會打亂你的計劃，你腦子裡剛才剛想到一半技術方案可能也就廢了。當產品經理走了以後，你再想撿起來剛被中斷之的工作的時候，很可能得花點時間回憶一會兒才能繼續工作。

對於CPU來講也是一樣，CPU要做一件新的事情之前，要載入該程序的地址空間，load程序程式碼，讀取程序資料，各級別cache要慢慢熱身。因此如果能適當降低中斷的頻率，多攢幾個包一起發出中斷，對提升CPU的工作效率是有幫助的。所以，網絡卡允許我們對硬中斷進行合併。

軟中斷監控與調優

在硬中斷之後，再接下來的處理過程就是ksoftirqd核心執行緒中處理的軟中斷了。之前我們說過，軟中斷和它對應的硬中斷是在同一個核心上處理的。 因此，前面硬中斷分散到多核上處理的時候，軟中斷的最佳化其實也就跟著做了，也會被多核處理。不過軟中斷也還有自己的可最佳化選項。

軟中斷budget調整

不知道你有沒有聽說過番茄工作法，它的大致意思就是你要有一整段的不被打擾的時間，集中精力處理某一項作業。這一整段時間時長被建議是25分鐘。 對於我們的Linux的處理軟中斷的ksoftirqd來說，它也和番茄工作法思路類似。一旦它被硬中斷觸發開始了工作，它會集中精力處理一波兒網路包（絕不只是1個），然後再去做別的事情。

我們說的處理一波兒是多少呢，策略略複雜。我們只說其中一個比較容易理解的，那就是 net.core.netdev_budget 核心引數。

這個的意思說的是，ksoftirqd一次最多處理300個包，處理夠了就會把CPU主動讓出來，以便Linux上其它的任務可以得到處理。 那麼假如說，我們現在就是想提高核心處理網路包的效率。那就可以讓ksoftirqd程序多幹一會兒網路包的接收，再讓出CPU。至於怎麼提高，直接修改不這個引數的值就好了。

如果要保證重啟仍然生效，需要將這個配置寫到/etc/sysctl.conf

軟中斷GRO合併

GRO和硬中斷合併的思想很類似，不過階段不同。硬中斷合併是在中斷髮起之前，而GRO已經到了軟中斷上下文中了。

如果應用中是大檔案的傳輸，大部分包都是一段資料，不用GRO的話，會每次都將一個小包傳送到協議棧（IP接收函式、TCP接收）函式中進行處理。開啟GRO的話，Linux就會智慧進行包的合併，之後將一個大包傳給協議處理函式。這樣CPU的效率也是就提高了。
