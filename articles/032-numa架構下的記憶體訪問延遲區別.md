# NUMA架構下的記憶體訪問延遲區別！

> 原文標題：NUMA架构下的内存访问延迟区别！

> 原文連結：http://kfngxl.cn/index.php/archives/560/

---

大家好，我是飛哥！
現在的伺服器物理機CPU一般都是多個CPU，核數也是十幾甚至幾十核。記憶體幾十GB甚至是上百G，也是由許多的記憶體條組成的。那麼我這裡思考一下，這麼多的CPU和記憶體它們之間是怎麼互相連線的？同一個CPU核訪問不同的記憶體條延時一樣嗎？
在《記憶體隨機訪問也比順序慢，帶你深入理解記憶體IO過程》中我們瞭解了記憶體訪問時晶片內部的執行過程，在《實際測試記憶體在順序IO和隨機IO時的訪問延時差異》中我們又進行了實際的程式碼測試。不過這兩文中我們都把精力聚焦在記憶體內部機制，而回避了上面的問題，那就是CPU和記憶體的連線方式，也就是匯流排架構。

## 回顧CPU與記憶體的簡單連線：FSB時代

我們先來回顧下在歷史上CPU、記憶體數量比較少的年代裡的匯流排方案-FSB。FSB的全稱是Front Side Bus，因此也叫前端匯流排。CPU透過FSB匯流排連線到北橋晶片，然後再連線到記憶體。記憶體控制器是整合在北橋裡的，Cpu和記憶體之間的通訊全部都要透過這一條FSB匯流排來進行。

在這個年代裡，當時提高計算機系統整體效能的方式就是不斷地提高CPU、FSB匯流排、記憶體條的資料傳輸頻率。

## 如今多CPU多記憶體條複雜互聯：NUMA時代

當CPU的主頻提升到了3GHz每秒以後，硬體製造商們發現單個CPU的已經到了物理極限了。所以就改變了效能改進的方法，改成為向多核、甚至是多CPU的方向來發展。在這種情況下，如果仍然採用FSB匯流排，會導致所有的CPU和記憶體通訊都經過匯流排，這樣匯流排就成為了瓶頸，無法充分發揮多核的優勢與效能。所以CPU製造商們把記憶體控制器從北橋搬到了CPU內部，這樣CPU便可以直接和自己的記憶體進行通訊了。那麼，如果CPU想要訪問不和自己直連的記憶體條怎麼辦呢？所以就誕生了新的匯流排型別，它就叫QPI匯流排。

圖中CPU1如果想要訪問記憶體3的話，就需要經過QPS匯流排才可以。

## 動手檢視Linux下NUMA架構

我們先透過dmidecode命令檢視一下記憶體插槽，單條大小等資訊。大家可以試著在linux上執行以下該命令。輸出結果很長，大家可以有空仔細研究。我這裡不全部介紹，這裡只挑選一些和記憶體相關的：

```
# dmidecode|grep -P -A5 "Memory\s+Device"|grep Size

        Size: 8192 MB

        Size: 8192 MB
        Size: No Module Installed
        Size: 8192 MB
        Size: 8192 MB
        Size: 8192 MB
        Size: No Module Installed
        Size: 8192 MB
        Size: No Module Installed
        Size: 8192 MB
```

可以看出，我當前使用的機器上共有16個記憶體插槽，共插了8條8G的記憶體。所以總共是64GB。如我們前面所述，在NUMA架構裡，每一個物理CPU都有不同的記憶體組，透過`numactl`命令可以檢視這個分組情況。

```
# numactl --hardware
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 4 5 12 13 14 15 16 17
node 0 size: 32756 MB
node 0 free: 19642 MB
node 1 cpus: 6 7 8 9 10 11 18 19 20 21 22 23
node 1 size: 32768 MB
node 1 free: 18652 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

透過上述命令可以看到，每一組CPU核分配了32GB（4條）的記憶體。`node distance`是一個二維矩陣，描述node訪問所有記憶體條的延時情況。`node 0`裡的CPU訪問`node 0`裡的記憶體相對距離是`10`,因為這時訪問的記憶體都是和該CPU直連的。而`node 0`如果想訪問`node 1`節點下的記憶體的話，就需要走QPI匯流排了，這時該相對距離就變成了`21`。

所以、在NUMA架構下，CPU訪問自己同一個node裡的記憶體要比其它記憶體要快！

## 動手測試NUMA架構記憶體延遲差異

`numactl`命令有`--cpubind`和`--membind`的選項，透過它們我們可以指定我們要用的node節點。還沿用《用程式碼讓你來實際感受記憶體的在不同情況下的訪問延時差異》裡的測試程式碼

1、讓記憶體和CPU處於同一個node

```
# numactl --cpubind=0 --membind=0 ./main

andom   2.40    2.40    2.40    2.40    4.80    4.80    19.20   28.80   52.80
```

## 結論

透過上面的各個小節我們可以看到，現代的伺服器裡，CPU和記憶體條都有多個，它們之前目前主要採用的是複雜的NUMA架構進行互聯，NUMA把伺服器裡的CPU和記憶體分組劃分成了不同的node。從上述實驗結果來看，拿8M陣列，迴圈步長為64的case來說，同node耗時3.15納秒，跨node為3.96納秒。所以屬於同一個node裡的CPU和記憶體之間訪問速度會比較快。而如果跨node的話，則需要經過QPI匯流排，總體來說，速度會略慢一些。
