前面我們在 《Linux程序是如何建立出來的？》 中介紹了程序的建立過程。事實上程序的 pid 名稱空間、pid 也都是在這個過程中申請的。我今天就來帶大家深入理解一下 docker 核心之一 pid 名稱空間的工作原理。

一、Linux 的預設 pid 名稱空間

前面的文章 《Linux程序是如何建立出來的？》 中我們提到了程序的名稱空間成員 nsproxy。

Linux 在啟動的時候會有一套預設的名稱空間，定義在 kernel/nsproxy.c 檔案下。

其中預設的 pid 名稱空間是 init_pid_ns，它定義在 kernel/pid.c 下。

在 pid 名稱空間裡我覺得最需要關注的是兩個欄位。一個是 level 表示當前 pid 名稱空間的層級。另一個是 pidmap，這是一個 bitmap，一個 bit 如果為 1，就表示當前序號的 pid 已經分配出去了。

另外預設名稱空間的 level 初始化是 0。這是一個表示樹的層次結構的節點。如果有多個名稱空間建立出來，它們之間會組成一棵樹。level 表示樹在第幾層。根節點的 level 是 0.

INIT_TASK 0號程序，也叫 idle 程序，它固定使用這個預設的 init_nsproxy。

所有程序都是一個派生一個的方式生成出來的。如果不指定名稱空間，所有程序使用的都是使用預設的名稱空間。

二、Linux 新 pid 名稱空間建立

在這裡，我們假設我們建立程序時指定了 CLONE_NEWPID 要建立一個獨立的 pid 名稱空間出來。

在 《Linux程序是如何建立出來的？》 一文中我們已經瞭解了程序的建立過程。整個建立過程的核心是在於 copy_process 函式。

在這個函式中會申請和複製程序的地址空間、開啟檔案列表、檔案目錄等關鍵資訊，另外就是 pid 名稱空間的建立也是在這裡完成的 。

2.1 建立程序時構造新名稱空間

在上面的 copy_process 程式碼中我們看到對 copy_namespaces 函式的呼叫。名稱空間就是在這個函式中操作的。

如果在建立程序時候沒有傳入 CLONE_NEWNS 等幾個 flag，還是會複用之前的預設名稱空間。這幾個 flag 的含義如下。

CLONE_NEWPID: 是否建立新的程序編號名稱空間，以便與宿主機的程序 PID 進行隔離

CLONE_NEWNS: 是否建立新的掛載點（檔案系統）名稱空間，以便隔離檔案系統和掛載點

CLONE_NEWNET: 是否建立新的網路名稱空間，以便隔離網絡卡、IP、埠、路由表等網路資源

CLONE_NEWUTS: 是否建立新的主機名與域名名稱空間，以便在網路中獨立標識自己

CLONE_NEWIPC: 是否建立新的 IPC 名稱空間，以便隔離訊號量、訊息佇列和共享記憶體

CLONE_NEWUSER: 用來隔離使用者和使用者組的。

因為我們本節開頭假設傳入了 CLONE_NEWPID 標記。所以會進入到 create_new_namespaces 中來申請新的名稱空間。

create_new_namespaces 中會呼叫 copy_pid_ns 來完成實際的建立，真正的建立過程是在 create_pid_namespace 中完成的。

在 create_pid_namespace 真正申請了新的 pid 名稱空間，為它的 pidmap 申請了記憶體（在 create_pid_cachep 中申請的），也進行了初始化。

另外還有一點比較重要的是新名稱空間和舊名稱空間透過 parent、level 等欄位組成了一棵樹。其中 parent 指向了上一級名稱空間，自己的 level 用來表示層次，設定成了上一級 level + 1。

2.2 申請程序id

建立完名稱空間後，在 copy_process 中接下來接著就是呼叫 alloc_pid 來分配 pid（Docker 容器就是這麼幹的）。

注意傳入的引數是 p->nsproxy->pid_ns。前面程序建立了新的 pid namespace，這個時候該名稱空間就是 level 為 1 的新 pid_ns。我們繼續來看 alloc_pid 具體 pid 的過程。

在上面的程式碼中要注意兩個細節。

我們平時說的 pid 在核心中並不是一個簡單的整數型別，而是一個小結構體來表示的（struct pid）。

申請 pid 並不是申請了一個，而是使用了一個 for 迴圈申請多個出來

之所以要申請多個，是因為對於容器裡的程序來說，並不是在自己當前的名稱空間申請就完事了，還要到其父名稱空間中也申請一個。我們把 for 迴圈的工作工程用下圖表示一下。

首先到當前層次的名稱空間申請一個 pid 出來，然後順著名稱空間的父節點，每一層也都要申請一個，並都記錄到 pid->numbers 陣列中。

這裡多說一下，如果 pid 申請失敗的話，會報 -ENOMEM 錯誤，在使用者層看起來就是“fork:無法分配記憶體”，實際是由 pid 不足引起的。這個問題我在 《明明還有大量記憶體，為啥報錯“無法分配記憶體”？》 提到過。

三、容器程序 pid 檢視

pid 已經申請好了，那在容器中是如何檢視當前層次的程序號的呢？比如我們在容器中看到的 demo-ie 程序的 id 就是 1。

核心提供了個函式用來檢視程序在當前某個名稱空間的命名號。

其中在容器中檢視程序 pid 使用的是 pid_vnr，pid_vnr 呼叫 pid_nr_ns 來檢視程序在特定名稱空間裡的程序號。

函式 pid_nr_ns 接收連個引數

第一個引數是程序裡記錄的 pid 物件（儲存有在各個層次申請到的 pid 號）

第二個引數是指定的 pid 名稱空間（透過 task_active_pid_ns(current)獲取）。

當具備這兩個引數後，就可以根據 pid 名稱空間裡記錄的層次 level 取得容器程序的當前 pid 了

在 pid_nr_ns 中透過判斷 level 就把容器 pid 整數值查出來了。
