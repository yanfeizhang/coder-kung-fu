# 剖析CPU效能火焰圖生成的內部原理

> 原文標題：剖析CPU性能火焰图生成的内部原理

> 原文連結：http://kfngxl.cn/index.php/archives/655/

大家好，我是飛哥！

在進行CPU效能最佳化的時候，我們經常先需要分析出來我們的應用程式中的CPU資源在哪些函式中使用的比較多，這樣才能高效地最佳化。一個非常好的分析工具就是《效能之巔》作者 Brendan Gregg 發明的火焰圖。

在這張火焰圖中，一個函式佔據的寬度越寬，表明該函式消耗的 CPU 佔比越高。但對於位於火焰圖下方的函式來說，它們雖然開銷比較大，但都是因為其子函式執行消耗的。所以一般都是看最上方的寬度較長的函式，這是導致整個系統 CPU 比較高的熱點，把它最佳化掉可以提升程式執行效能。

我們今天就來介紹下火焰圖的是怎麼做出來的，以及它的工作原理。

之所以選擇我提供一個 demo 程式碼來生成，是因為這個足夠簡單和清晰，方便大家理解。在上面這個火焰圖中，可以看出 main 函式呼叫了 funcA、funcB、funcC，其中 funcA 又呼叫了 funcD、funcE，然後這些函式的開銷又都不是自己花掉的，而是因為自己呼叫的一個 CPU 密集型的函式 caculate。整個系統的呼叫棧的耗時統計就十分清晰的展現在眼前了。

如果要對這個專案進行效能最佳化。在上方的火焰圖中看雖然funcA、funcB、funcC、funcD、funcE這幾個函式的耗時都挺長，但它們的耗時並不是自己用掉的。而且都花在執行子函式里了。我們真正應該關注的是火焰圖最上方 caculate 這種又長又平的函式。因為它才是真正花掉 CPU 時間的程式碼。其它專案中也一樣，拿到火焰圖後，從最上方開始，把耗時比較長的函式找出來，最佳化掉。

另外就是在實際的專案中，可能函式會非常的多，並不像上面這麼簡單，很多函式名可能都被摺疊起來了。這個也好辦，svg 格式的圖片是支援互動的，你可以點選其中的某個函式，然後就可以展開了只詳細地看這個函式以及其子函式的火焰圖了。

怎麼樣，火焰圖使用起來是不是還挺簡單的。接下來的小節中我們再來講講火焰圖生成全過程的內部原理。理解了這個，你才能講火焰圖用的得心應手。

二、perf取樣

2.1 perf 介紹

在生成火焰圖的第一步中，就是需要對你要觀察的程序或伺服器進行取樣。取樣可用的工具有好幾個，我們這裡用的是 perf record。

上面的命令中 -g 指的是取樣的時候要記錄呼叫棧的資訊。 ./main 是啟動 main 程式，並只取樣這一個程序。這只是個最簡單的用法，其實 perf record 的功能非常的豐富。

它可以指定採集事件。當前系統支援的事件列表可以用過 perf list 來檢視。預設情況下采集的是 Hardware event 下的 cycles 這一事件。假如我們想取樣 cache-misses 事件，我們可以透過 -e 引數指定。

還可以指定取樣的方式。該命令支援兩種取樣方式，時間頻率取樣，事件次數發生取樣。-F 引數指定的是每秒鐘取樣多少次。-c引數指定的是每發生多少次取樣一次。

還可以指定要記錄的CPU核

還可以採集核心的呼叫棧

在使用 perf record 執行後，會將取樣到的資料都生成到 perf.data 檔案中。在上面的實驗中，雖然我們只採集了幾秒，但是生成的檔案還挺大的，有 800 多 KB。我們透過 perf script 命令可以解析檢視一下該檔案的內容。大概有 5 萬多行。其中的內容就是取樣 cycles 事件時的呼叫棧資訊。

除了 perf script 外，還可以使用 perf report 來檢視和渲染結果。

我們來看下它的幾個關鍵執行過程。在 perf_event_open 呼叫的 perf_event_alloc 指定了取樣處理回撥函式為，比如perf_event_output_backward、perf_event_output_forward等

當 perf_event_open 建立事件物件，並開啟後，硬體上發生的事件就可以出發執行了。核心註冊相應的硬體中斷處理函式是 perf_event_nmi_handler。

這樣 CPU 硬體會根據 perf_event_open 呼叫時指定的週期發起中斷，呼叫 perf_event_nmi_handler 通知核心進行取樣處理

該終端處理函式的函式呼叫鏈經過 x86_pmu_handle_irq 到達 perf_event_overflow。其中 perf_event_overflow 是一個關鍵的取樣函式。無論是硬體事件取樣，還是軟體事件取樣都會呼叫到它。它會呼叫 perf_event_open 時註冊的 overflow_handler。我們假設 overflow_handler 為 perf_event_output_forward

總結

火焰圖是一個非常好的用於分析熱點函式的工具，只要你關注效能最佳化，就應該學會使用它來分析你的程式。我們今天的文章不光是介紹了火焰圖是如何生成的，而且還介紹了其底層的工作原理。火焰圖的生成主要分兩步，一是取樣，而是渲染。

在取樣這一步，主要依賴的是核心提供的 perf_event_open 系統呼叫。該系統呼叫在內部給CPU指定了中斷處理函式。然後CPU會定時發起中斷，核心在每次中斷中，都會對當前CPU在執行的函式進行取樣。具體過程是訪問該程序的 IP 暫存器的值（也就是下一條指令的地址）。透過分析該程序的可執行檔案，是可以得知每次取樣的 IP 值處於哪個函式內部。最終核心和硬體一起協同合作，會定時將當前正在執行的函式，以及甚至是函式完整的呼叫鏈路都給記錄下來。

在渲染這一步，Brendan Gregg 提供的指令碼會出 perf 工具輸出的 perf_data 檔案進行預處理，然後基於預處理後的資料渲染成 svg 圖片。函式執行的次數越多，在 svg 圖片中的寬度就越寬。我們就可以非常直觀地看出哪些函式消耗的 CPU 多了。

最後再補充說一句是，我們的火焰圖只是一個取樣的渲染結果。假如我們取樣了 100 次，有 30次都是發現函式 A 在執行。那麼火焰圖就認為函式 A 消耗掉了 30% 的CPU週期。顯然這種取樣的方式並不一定完全代表真實情況，但只要取樣頻率不是太低，基本也夠用了。
