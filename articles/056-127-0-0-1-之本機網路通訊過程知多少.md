二、本機傳送過程

在第一節中，我們看到了跨機時整個網路傳送過程（嫌第一節流程圖不過癮，想繼續看原始碼瞭解細節的同學可以參考 拆解 Linux 網路包傳送過程 ） 。

在本機網路 IO 的過程中，流程會有一些差別。為了突出重點，將不再介紹整體流程，而是隻介紹和跨機邏輯不同的地方。有差異的地方總共有兩個，分別是 路由 和 驅動程式 。

2.1 網路層路由

傳送資料會進入協議棧到網路層的時候，網路層入口函式是 ip_queue_xmit。在網路層裡會進行路由選擇，路由選擇完畢後，再設定一些 IP 頭、進行一些 netfilter 的過濾後，將包交給鄰居子系統。

對於本機網路 IO 來說，特殊之處在於在 local 路由表中就能找到路由項，對應的裝置都將使用 loopback 網絡卡，也就是我們常見的 lo。

我們來詳細看看路由網路層裡這段路由相關工作過程。從網路層入口函式 ip_queue_xmit 看起。

查詢路由項的函式是 ip_route_output_ports，它又依次呼叫到 ip_route_output_flow、\_\_ip_route_output_key、fib_lookup。呼叫過程省略掉，直接看 fib_lookup 的關鍵程式碼。

在 fib_lookup 將會對 local 和 main 兩個路由表展開查詢，並且是先查 local 後查詢 main。我們在 Linux 上使用命令名可以檢視到這兩個路由表， 這裡只看 local 路由表（因為本機網路 IO 查詢到這個表就終止了）。

從上述結果可以看出，對於目的是 127.0.0.1 的路由在 local 路由表中就能夠找到了。fib_lookup 工作完成，返回\_\_ip_route_output_key 繼續。

對於是本機的網路請求，裝置將全部都使用 net->loopback_dev,也就是 lo 虛擬網絡卡。

接下來的網路層仍然和跨機網路 IO 一樣，最終會經過 ip_finish_output，最終進入到 鄰居子系統的入口函式 dst_neigh_output 中。

在鄰居子系統函式中經過處理，進入到網路裝置子系統（入口函式是 dev_queue_xmit）。

三、本機接收過程

在跨機的網路包的接收過程中，需要經過硬中斷，然後才能觸發軟中斷。而在本機的網路 IO 過程中，由於並不真的過網絡卡，所以網絡卡實際傳輸，硬中斷就都省去了。直接從軟中斷開始，經過 process_backlog 後送進協議棧，大體過程如圖。

接下來我們再看更詳細一點的過程。 在軟中斷被觸發以後，會進入到 NET_RX_SOFTIRQ 對應的處理方法 net_rx_action 中（至於細節參見 [圖解Linux網路包接收過程 ]( https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg ) 一文中的 3.2 小節）。

我們還記得對於 igb 網絡卡來說，poll 實際呼叫的是 igb_poll 函式。那麼 loopback 網絡卡的 poll 函式是誰呢？由於poll_list 裡面是 struct softnet_data 物件，我們在 net_dev_init 中找到了蛛絲馬跡。

原來 struct softnet_data 預設的 poll 在初始化的時候設定成了 process_backlog 函式，來看看它都幹了啥。

這次先看對 skb_queue_splice_tail_init 的呼叫。原始碼就不看了，直接說它的作用是把 sd->input_pkt_queue 裡的 skb 鏈到 sd->process_queue 連結串列上去。

然後再看 \_\_skb_dequeue， \_\_skb_dequeue 是從 sd->process_queue 上取下來包來處理。這樣和前面傳送過程的結尾處就對上了。​傳送過程是把包放到了 input_pkt_queue 佇列裡，接收過程是在從這個佇列裡取出 skb。

最後呼叫 \_\_netif_receive_skb 將 skb(資料) 送往協議棧。在此之後的呼叫過程就和跨機網路 IO 又一致了。

送往協議棧的呼叫鏈是 \_\_netif_receive_skb => \_\_netif_receive_skb_core => deliver_skb 後 將資料包送入到 ip_rcv 中（詳情參見[圖解Linux網路包接收過程 ]( https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg ) 一文中的 3.3 小節）。

網路再往後依次是傳輸層，最後喚醒使用者程序，這裡就不多展開了。

1）127.0.0.1 本機網路 IO 需要經過網絡卡嗎？ 透過本文的敘述，我們確定地得出結論， 不需要經過網絡卡 。即使了把網絡卡拔了本機網路是否還可以正常使用的。

2）資料包在核心中是個什麼走向，和外網傳送相比流程上有啥差別？ 總的來說，本機網路 IO 和跨機 IO 比較起來，確實是節約了一些開銷。傳送資料不需要進 RingBuffer 的驅動佇列，直接把 skb 傳給接收協議棧（經過軟中斷）。但是在核心其它元件上，可是一點都沒少，系統呼叫、協議棧（傳輸層、網路層等）、網路裝置子系統、鄰居子系統整個走了一個遍。連“驅動”程式都走了（雖然對於迴環裝置來說只是一個純軟體的虛擬出來的東東）。所以即使是本機網路 IO，也別誤以為沒啥開銷。

一、相關原始碼分析

第一： 所有 local 路由表項核心都會標識為 RTN_LOCAL

前面文章裡可以看到選用哪個裝置是在網路層里路由選擇的時候決定的，函式是 \_\_ip_route_output_key。

這裡會查詢到 local 路由表。

很多人在看到這個路由表的時候就被它給迷惑了，以為上面 10.162. . 真的會被路由到 eth0。 而其實核心在初始化 local 路由表的時候，把 local 路由表裡所有的路由項都設定成了 RTN_LOCAL。這個過程是在設定本機 ip 的時候，呼叫 fib_inetaddr_event 函式完成設定的。

第二： 所有 RTN_LOCAL 型別的路由表都會選擇到 loopback 虛擬裝置

來看網路層的這段原始碼。

所以即使本機 IP，不用 127.0.0.1，核心在路由項查詢的時候仍然會使用 net->loopback_dev。也就是 lo 虛擬網絡卡。

總結

我覺得有相當大一部分人都會認為訪問本機 Server 的話，用 127.0.0.1 更快。原因是直覺上認為訪問 IP 就會經過網絡卡。

其實核心知道本機上所有的 IP，只要發現目的地址是本機 IP 就可以全走 loopback 迴環裝置了。 本機其它 IP 和 127.0.0.1 一樣，也是不用過物理網絡卡的，所以訪問它們效能開銷基本一樣！
