當資料封包到達另外一臺機器的時候，Linux 資料封包的接收過程開始了。

當網路卡收到資料以後，向 CPU 發起一箇中斷，以通知 CPU 有資料到達。當 CPU 收到中斷請求後，會去呼叫網路驅動註冊的中斷處理函式，觸發軟中斷 (Softirq)。ksoftirqd 檢測到有軟中斷請求到達，開始輪詢接收封包，收到後交由各級協定堆疊處理。當協定堆疊處理完並把資料放到接收佇列的之後，喚醒使用者程序 (Process)。

## 二、本機傳送過程

在第一節中，我們看到了跨機時整個網路傳送過程（嫌第一節流程圖不過癮，想繼續看原始碼瞭解細節的同學可以參考 [拆解 Linux 網路封包傳送過程](https://mp.weixin.qq.com/s/wThfD9th9e_-YGHJJ3HXNQ)） 。

在本機網路 IO 的過程中，流程會有一些差別。為了突出重點，將不再介紹整體流程，而是隻介紹和跨機邏輯不同的地方。有差異的地方總共有兩個，分別是路由和驅動程式。

## 2.1 網路層路由

傳送資料會進入協定堆疊到網路層的時候，網路層入口函式是   `ip_queue_xmit`。在網路層裡會進行路由選擇，路由選擇完畢後，再設定一些 IP 頭、進行一些 netfilter 的過濾後，將封包交給鄰居子系統。

對於本機網路 IO 來說，特殊之處在於在 local 路由表中就能找到路由項，對應的裝置都將使用 loopback 網路卡，也就是我們常見的 lo。

我們來詳細看看路由網路層裡這段路由相關工作過程。從網路層入口函式 `ip_queue_xmit` 看起。

```
//file: net/ipv4/ip_output.c
int ip_queue_xmit(struct sk_buff *skb, struct flowi *fl)
{
    //檢查 socket 中是否有快取的路由表
    rt = (struct rtable *)__sk_dst_check(sk, 0);
    if (rt == NULL) {
        //沒有快取則展開查詢
        //則查詢路由項， 並快取到 socket 中
        rt = ip_route_output_ports(...);
        sk_setup_caps(sk, &rt->dst);
 }
```

查詢路由項的函式是   `ip_route_output_ports`，它又依次呼叫到 `ip_route_output_flow`、\_\_ip_route_output_key、 `fib_lookup`。呼叫過程省略掉，直接看 `fib_lookup` 的關鍵程式碼。

```
//file:include/net/ip_fib.h
static inline int fib_lookup(struct net *net, const struct flowi4 *flp,
                 struct fib_result *res)
{
    struct fib_table *table;

    table = fib_get_table(net, RT_TABLE_LOCAL);
    if (!fib_table_lookup(table, flp, res, FIB_LOOKUP_NOREF))
        return 0;

    table = fib_get_table(net, RT_TABLE_MAIN);
    if (!fib_table_lookup(table, flp, res, FIB_LOOKUP_NOREF))
        return 0;
    return -ENETUNREACH;
}
```

在 `fib_lookup` 將會對 local 和 main 兩個路由表展開查詢，並且是先查 local 後查詢 main。我們在 Linux 上使用命令名可以檢視到這兩個路由表， 這裡只看 local 路由表（因為本機網路 IO 查詢到這個表就終止了）。

```
#ip route list table local
local 10.143.x.y dev eth0 proto kernel scope host src 10.143.x.y
local 127.0.0.1 dev lo proto kernel scope host src 127.0.0.1
```

從上述結果可以看出，對於目的是 127.0.0.1 的路由在 local 路由表中就能夠找到了。`fib_lookup` 工作完成，回傳\_\_ip_route_output_key 繼續。

```
//file: net/ipv4/route.c
struct rtable *__ip_route_output_key(struct net *net, struct flowi4 *fl4)
{
    if (fib_lookup(net, fl4, &res)) {
    }
    if (res.type == RTN_LOCAL) {
        dev_out = net->loopback_dev;
        ...
    }

    rth = __mkroute_output(&res, fl4, orig_oif, dev_out, flags);
    return rth;
}

對於是本機的網路請求，裝置將全部都使用 net->loopback_dev,也就是 lo 虛擬網路卡。
```

接下來的網路層仍然和跨機網路 IO 一樣，最終會經過   `ip_finish_output`，最終進入到鄰居子系統的入口函式 `dst_neigh_output` 中。

> 本機網路 IO 需要進行 IP 分片嗎？因為和正常的網路層處理過程一樣會經過   `ip_finish_output` 函式。在這個函式中，如果 `skb` 大於 MTU 的話，仍然會進行分片。只不過 lo 的 MTU 比 Ethernet 要大很多。透過 ifconfig 命令就可以查到，普通網路卡一般為 1500，而 lo 虛擬介面能有 65535。

在鄰居子系統函式中經過處理，進入到網路裝置子系統（入口函式是 `dev_queue_xmit`）。

## 2.3 「驅動」程式

對於真實的 igb 網路卡來說，它的驅動程式碼都在   `drivers/net/ethernet/intel/igb/igb_main.c` 檔案裡。順著這個路子，我找到了 loopback 裝置的「驅動」程式碼位置：`drivers/net/loopback.c`。
在 `drivers/net/loopback.c`

```
//file:drivers/net/loopback.c

    .ndo_init      = loopback_dev_init,
    .ndo_start_xmit= loopback_xmit,
    .ndo_get_stats64 = loopback_get_stats64,
};
```

所以對   `dev_hard_start_xmit` 呼叫實際上執行的是 loopback 「驅動」 裡的 `loopback_xmit`。為什麼我把「驅動」加個引號呢，因為 loopback 是一個純軟體性質的虛擬介面，並沒有真正意義上的驅動，它的工作流程大致如圖。

我們再來看詳細的程式碼。

```
//file:drivers/net/loopback.c
static netdev_tx_t loopback_xmit(struct sk_buff *skb,
                 struct net_device *dev)
{
    //剝離掉和原 socket 的聯絡
    skb_orphan(skb);

    //呼叫netif_rx
    if (likely(netif_rx(skb) == NET_RX_SUCCESS)) {
    }
}
```

在   `skb_orphan` 中先是把 `skb` 上的 `socket` 指標去掉了（剝離了出來）。

> 注意，在本機網路 IO 傳送的過程中，傳輸層下面的 `skb` 就不需要釋放了，直接給接收方傳過去就行了。總算是省了一點點開銷。不過可惜傳輸層的 `skb` 同樣節約不了，還是得頻繁地申請和釋放。

接著呼叫   `netif_rx`，在該方法中中最終會執行到 `enqueue_to_backlog` 中（netif_rx-> netif_rx_internal-> `enqueue_to_backlog`）。

```

                  unsigned int *qtail)
{
    sd = &per_cpu(softnet_data, cpu);

    ...
    __skb_queue_tail(&sd->input_pkt_queue, skb);

    ...
    ____napi_schedule(sd, &sd->backlog);

在   enqueue_to_backlog 把要傳送的 skb 插入 softnet_data-> input_pkt_queue 佇列中並呼叫 ____napi_schedule 來觸發軟中斷。
```

```

                     struct napi_struct *napi)
{
    list_add_tail(&napi->poll_list, &sd->poll_list);
    __raise_softirq_irqoff(NET_RX_SOFTIRQ);
}
```

只有觸發完軟中斷，傳送過程就算是完成了。

## 三、本機接收過程

在跨機的網路封包的接收過程中，需要經過硬中斷，然後才能觸發軟中斷。而在本機的網路 IO 過程中，由於並不真的過網路卡，所以網路卡實際傳輸，硬中斷就都省去了。直接從軟中斷開始，經過   `process_backlog` 後送進協定堆疊，大體過程如圖。

接下來我們再看更詳細一點的過程。
在軟中斷被觸發以後，會進入到 `NET_RX_SOFTIRQ` 對應的處理方法 `net_rx_action` 中（至於細節參見 [圖解 Linux 網路封包接收過程
](https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg) 一文中的 3.2 小節）。

```
//file: net/core/dev.c
static void net_rx_action(struct softirq_action *h){
    while (!list_empty(&sd->poll_list)) {
        work = n->poll(n, weight);
    }
}
```

我們還記得對於 igb 網路卡來說，  `poll` 實際呼叫的是 `igb_poll` 函式。那麼 loopback 網路卡的 `poll` 函式是誰呢？由於 `poll_list` 裡面是 struct  `softnet_data` 物件，我們在 `net_dev_init` 中找到了蛛絲馬跡。

```
//file:net/core/dev.c
static int __init net_dev_init(void)
{
    for_each_possible_cpu(i) {
        sd->backlog.poll = process_backlog;
    }
}
```

原來 struct  `softnet_data` 預設的  `poll` 在初始化的時候設定成了 `process_backlog` 函式，來看看它都做了什麼。

```
//file: net/core/dev.c
static int process_backlog(struct napi_struct *napi, int quota)
{
    while(){
        while ((skb = __skb_dequeue(&sd->process_queue))) {
            __netif_receive_skb(skb);
        }

        //skb_queue_splice_tail_init() 函式用於將連結串列 a 連線到連結串列 b 上，
        //形成一個新的連結串列 b，並將原來 a 的頭變成空連結串列。
        qlen = skb_queue_len(&sd->input_pkt_queue);
        if (qlen)
            skb_queue_splice_tail_init(&sd->input_pkt_queue,
                           &sd->process_queue);

    }
}

這次先看對   skb_queue_splice_tail_init 的呼叫。原始碼就不看了，直接說它的作用是把 sd->input_pkt_queue 裡的 skb 鏈到 sd->process_queue 連結串列上去。

然後再看 \_\_skb_dequeue， \_\_skb_dequeue 是從 sd->process_queue 上取下來包來處理。這樣和前面傳送過程的結尾處就對上了。傳送過程是把封包放到了 input_pkt_queue 佇列裡，接收過程是在從這個佇列裡取出 skb。
```

最後呼叫 \_\_netif_receive_skb 將 `skb`(資料) 送往協定堆疊。在此之後的呼叫過程就和跨機網路 IO 又一致了。

送往協定堆疊的呼叫鏈是 \_\_netif_receive_skb => \_\_netif_receive_skb_core =>`deliver_skb` 後將資料封包送入到 `ip_rcv` 中（詳情參見[圖解 Linux 網路封包接收過程
](https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg) 一文中的 3.3 小節）。

網路再往後依次是傳輸層，最後喚醒使用者程序，這裡就不多展開了。

## 一、相關原始碼分析

第一：所有 local 路由表項核心都會標識為 `RTN_LOCAL`

前面文章裡可以看到選用哪個裝置是在網路層里路由選擇的時候決定的，函式是 \_\_ip_route_output_key。

```

{
    if (fib_lookup(net, fl4, &res)) {
    }
    if (res.type == RTN_LOCAL) {
        dev_out = net->loopback_dev;
        ...
    }

    rth = __mkroute_output(&res, fl4, orig_oif, dev_out, flags);
    return rth;

```

這裡會查詢到 local 路由表。

```
# ip route list table local
local 10.162.*.* dev eth0  proto kernel  scope host  src 10.162.*.*
local 127.0.0.1 dev lo  proto kernel  scope host  src 127.0.0.1
```

很多人在看到這個路由表的時候就被它給迷惑了，以為上面 10.162..真的會被路由到 eth0。
而其實核心在初始化 local 路由表的時候，把 local 路由表裡所有的路由項都設定成了   `RTN_LOCAL`。這個過程是在設定本機 ip 的時候，呼叫 `fib_inetaddr_event` 函式完成設定的。

```
case NETDEV_UP:
fib_add_ifaddr(ifa);
break;
case NETDEV_DOWN:
fib_del_ifaddr(ifa, NULL);
```

```
//file:ipv4/fib_frontend.c

{
    fib_magic(RTM_NEWROUTE, RTN_LOCAL, addr, 32, prim);
}
```


## 二、實踐驗證

為了穩妥起見，飛哥再擷取封包確認一下。開啟兩個控制檯視窗，一個對 lo 裝置進行擷取封包。因為區域網內會有大量的網路請求，為了方便過濾，這裡使用一個特殊的埠號 8888。如果這個埠號在你的機器上佔用了，那需要再換一個。

```
#tcpdump -i eth0 port 8888
```

另外一個視窗使用 telnet 對本機 IP 埠發出幾條網路請求。

```
#telnet 10.162.*.* 8888
Trying 10.162.*.*...
telnet: connect to address 10.162.*.*: Connection refused
```

這時候切回第一個控制檯，發現什麼反應都沒有。說明包根本就沒有過 eth0 這個裝置。

再把裝置換成 lo 再抓。當 telnet 發出網路請求以後，在 `tcpdump` 所在的視窗下看到了封包擷取結果。

```
# tcpdump -i lo port 8888
tcpdump: verbose output suppressed, use -v or -vv for full protocol decode
listening on lo, link-type EN10MB (Ethernet), capture size 65535 bytes
08:22:31.956702 IP 10.162.*.*.62705 > 10.162.*.*.ddi-tcp-1: Flags [S], seq 678725385, win 43690, options [mss 65495,nop,wscale 8], length 0
08:22:31.956720 IP 10.162.*.*.ddi-tcp-1 > 10.162.*.*.62705: Flags [R.], seq 0, ack 678725386, win 0, length 0
```

## 總結

我覺得有相當大一部分人都會認為存取本機 Server 的話，用 127.0.0.1 更快。原因是直覺上認為存取 IP 就會經過網路卡。

其實核心知道本機上所有的 IP，只要發現目的位址是本機 IP 就可以全走 loopback 迴環裝置了。本機其他 IP 和 127.0.0.1 一樣，也是不用過實體網路卡的，所以存取它們效能開銷基本一樣！
