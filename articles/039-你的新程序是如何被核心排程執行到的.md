一、CPU 核的執行佇列

程序建立完後需要被新增到執行佇列中，那我們就來看看這個執行佇列究竟是長啥樣子的。

關於執行佇列，我們得先從 CPU 的物理結構講起。現代主流的伺服器都是多 CPU 架構，每顆 CPU 又會包含多個物理核，每個物理核又可以超執行緒出多個邏輯核來供作業系統管理和使用。

拿某臺線上的伺服器 32 核的伺服器來舉例，該伺服器實際上是有 2 顆 CPU，每顆 CPU 包含了 8 個物理核心。這樣總共包含的是 16 個物理核。

因為該伺服器每個物理核心又可以當成兩個超執行緒來用，所以透過 top 命令可以看到有 32 “核”，這裡看到的核其實是邏輯核。

為了讓每個 CPU 核(邏輯核)都能更好地參與程序任務處理，不需要考慮和其他處理器競爭的問題，也能充分利用本地硬體 Cache 來對訪問加速。Linux 核心會為每個 CPU 核都分配一個執行佇列，也就是 struct rq 核心物件。

核心定義是透過 DEFINE_PER_CPU 來定義 Per CPU 變數的。其中執行佇列使用的是 DEFINE_PER_CPU_SHARED_ALIGNED 宏。

DEFINE_PER_CPU_SHARED_ALIGNED 宏接收兩個引數，第一引數可以理解為是陣列型別，第二個引數可以理解為陣列名。

這個宏執行後的效果是初始化出來一個 runqueues 陣列，在該陣列中為每一個 CPU 核都配置了一個執行佇列（struct rq）物件。

那麼這個執行佇列 struct rq 又是如何實現的呢？Linux 作業系統程序排程有多種多樣的需求。例如有的需要按優先順序來實時排程，只要高優先順序的程序一就緒，就需要立即搶佔 CPU 資源。有的不需要搶佔這麼頻繁，對實時性要求沒那麼高，但需要程序公平地被分配 CPU 資源就可以了。

為了滿足各種複雜的排程策略，核心在 struct rq 中實現了不同的排程類（Scheduling Class）。不同的排程需求的程序放在不同的排程類中。

2.1 實時排程器

在實時類排程需求中，一般核心執行緒如 migration 一般對實時性的要求比較高，這類程序需要及時排程分配 CPU。

在這種排程演算法中，優先順序是最主要考慮的因素。高優先順序的程序可以搶佔低優先順序程序 CPU 資源來執行。同一個優先順序的程序按照先到先服務（SCHED_FIFO）或者時間片輪轉（SCHED_RR）。

這種排程方式實現起來比較簡單，只需要定義一些優先順序，併為每個優先順序各分配一個連結串列當佇列即可，也叫多優先順序佇列。

2.2 完全公平排程器

Linux 主要是用來執行使用者程序的。對於絕大部分的使用者程序來說，對實時性的要求沒那麼高。如果因為優先順序的問題頻繁地發生搶佔，進而導致過多的程序上下文切換的開銷，對系統整體的效能是有不利的影響的。

所以使用者程序採用的是不同的排程演算法。Linux 2.6.23 之後採用了完全公平排程器（Completely Fair Scheduler，CFS）作為對使用者程序的排程演算法。 CFS 排程器的核心思想是強調讓每個程序儘量公平地分配到 CPU 時間即可，而不是實時搶佔。 。

舉個例子，假設一個 CPU 上有兩個任務需要執行，那麼每個任務都將分配 50% 的 CPU 時間，以保障公平性。假如有 N 個任務，CPU 儘可能分配給每個程序 1/N 的處理時間。

公平排程演算法在實現上引入了一個虛擬時間的概念。一旦程序執行虛擬時間就會增加。儘量讓虛擬時間最小的程序執行，誰小了就要多執行，誰大了就要少獲得 CPU。最後儘量保證所有程序的虛擬時間相等，動態地達到公平分配 CPU 的目的。

但是在資料結構的組織上，有一個小小的難點要解決。那就是當所有程式執行起來後，每一個程序的虛擬時間是不斷地在變化的。如何動態管理這些虛擬時間不斷在變化的程序，快速把虛擬時間最少的程序找出來。

在 CFS 排程器中採用的解決辦法是使用的是紅黑樹來管理任務。紅黑樹把程序按虛擬執行時間從小到大排序。越靠樹的左側，程序的執行虛擬時間越小。越靠樹的右側，程序的執行虛擬時間就越大。這樣每當想挑選可執行程序時，直接從樹的最左側選擇節點就可以了。

另外完全公平排程器實現上考慮到的兩個細節這裡我和大家提一下。

第一個就是照顧效能開銷 。

前面我們說過，程序上下文切換會導致額外的 CPU 浪費。假如被選中的程序剛執行沒多久，它的虛擬時間時間就比另一個程序小了。這時候難道要馬上換另一個程序處理麼？出於減少頻繁切換程序所帶來的成本考慮，顯然並不應該這樣。

所以，Linux 會保證選擇到的程序一個最短的執行時間，這個時間由 sched_min_granularity_ns 這個核心引數來控制。

上面是飛哥阿里雲伺服器的預設配置。這表示程序至少會執行 10 ms。當然了，如果程序因為等待網路、磁碟等資源時主動放棄那另算。

第二個就是權重考量 。

在實踐中可能確實有程序需要多分配一點執行時間。Linux 採用的做法在是上述絕對公平演算法基礎上再為程序引入一個權重。

透過給每個程序設定一定的權重，各個程序按權重的比例公平地來分配 CPU 時間。如果程序的權重高，那就按比例多獲得一點 CPU，權重低獲得的比例就低。

這個權重就是 Linux 程序的 nice 值，也就是我們平時 top 命令結果中看到的 ni 這一列。nice 範圍為 -20（最高權重）到 19（最低權重）。

現在有很多人都把 nice 理解成了優先順序，這是不太恰當的。優先順序強調的是搶佔，高優先順序比低優先順序有優先獲得 CPU 的權利。而使用者程序中的 nice 值強調的是獲取到 CPU 執行時間的比例，理解成權重更合適。

四、新程序加入排程

同在 《Linux程序是如何建立出來的？》 一文中我們講到，程序在 copy_process 建立完畢後，透過呼叫 wake_up_new_task 將新程序加入到就緒佇列中，等待排程器排程。

今天我們可以來展開看看 wake_up_new_task 執行時具體都發生了什麼。新程序是如何加入到 CPU 執行佇列 （struct rq）中的，我們來展開詳細看看。

wake_up_new_task 主要做了兩件事，一是選擇一個合適 CPU，二是將程序新增到所選的 CPU 的任務佇列中。

4.1 選擇合適的 CPU 執行佇列

前面我們講到，每個 CPU 核都有一個對應的執行佇列 runqueue (struct rq)。所以新程序在加入排程前的第一件事就是選擇一個合適的執行佇列。然後使用該任務佇列中，並等待排程。

要稍微注意的是，在 set_task_cpu(p, select_task_rq(p, SD_BALANCE_FORK, 0)) 這一行程式碼中包含對兩個函式的呼叫。

select_task_rq 是選擇一個合適的 CPU（執行佇列）

set_task_cpu 是使用選擇好的 CPU

在講選擇執行佇列之前，我們先簡單回顧一下 CPU 裡的快取。

CPU 同一個物理核上的兩個邏輯核是共享一組 L1 和 L2 快取的。整顆物理 CPU 上所有的核心共享同一組 L3。每一級 Cache 的訪問耗時都差別非常大，L1 大約是 1 ns 多一些，L2 大約是 2 ns 多，L3 大約 4 - 8 ns。而記憶體耗時在最壞的隨機 IO 情況下可以達到 30 多 ns。

儲存延遲測試參見 《實際測試記憶體在順序IO和隨機IO時的訪問延時差異》 ，想了解你的 CPU 上 cache 的情況請參見 《CPU cache 的檢視》

瞭解了 CPU 的物理結構以及各級快取的效能差異，你就大概能弄明白選擇 CPU 的核心目的了。 CPU 排程是在快取效能和空閒核心兩個點之間做權衡 。 同等條件下會盡量優先考慮快取命中率，選擇同 L1/L2 的核，其次會選擇同一個物理 CPU 上的（共享 L3），最壞情況下去選擇另外一個物理 CPU 上的核心。

選擇執行佇列 select_task_rq 這個函式有點複雜。但是理解了上面這個邏輯後，相信你理解起來就會容易很多。

在本文的第三節中我們提到了 fork 出來的新程序的 sched_class 使用的是公平排程器 fair_sched_class，回憶一下這個結構體的定義。

所以上面的 p->sched_class->select_task_rq 這一句實際是進入到了 fair_sched_class 的 select_task_rq_fair 方法裡，透過公平排程器實現的選擇任務佇列的來選擇的。

為了方便你理解，我把 select_task_rq_fair 原始碼精簡處理後，只留下了關鍵邏輯。這個函式一開始就獲得了當前 CPU（建立新程序的程序所使用的 CPU）和上一次執行的 CPU（新程序暫時還沒有）。接下來就是兩個關鍵邏輯：一是快速路徑選擇，二是慢速路徑選擇。

在快速路徑選擇中，主要的策略就是考慮共享 cache 且 idle 的 CPU。優先選擇任務上一次執行的CPU，其次是喚醒任務的 CPU。總之就是儘量考慮 cache 效能。

如果快速路徑沒選到，那就進入慢速路徑。首選選出負載最小的組（find_idlest_group），然後再從該組中選出最空閒的 CPU（find_idlest_cpu）。

當進入到慢速路徑以後，會導致程序下一次執行的時候跑的別的核、甚至是別的物理 CPU 上，這樣以前跑熱的 L1、L2、L3 就都失效了。使用者程序過多地發生這種漂移會對效能造成影響。當然核心在極力地避免。如果你想強行幹掉漂移，可以試試 taskset 命令。

至於 set_task_cpu 的邏輯比較簡單，主要就是把選到的 CPU 設定到新建立出來的程序 task_struct 上。

五、排程時機

前面我們講述的過程全部是新程序建立發生的事情，新程序還沒有真正被排程。觸發排程器開始選擇程序並上 CPU 開始執行的時機有很多。我們就以咱們前面文章講過的同步阻塞時機為例。

在 圖解 | 深入理解高效能網路開發路上的絆腳石 - 同步阻塞網路 IO 一文中我們提到過，在同步阻塞網路程式設計模型下，如果 socket 上沒有收到資料，或者收到不足夠多，則呼叫 sk_wait_data 把當前程序阻塞掉，讓出 CPU 並排程執行佇列中的其它程序進行。

我們現在假設就有某一個程序發生了這樣的阻塞。sk_wait_data 依次會呼叫 sk_wait_event、schedule_timeout，然後到達排程的核心函式 schedule。 我們來看看它的核心實現 \_\_schedule。

六、總結

好了，我們把今天的文章的內容總結一下。

一個程序從 fork 建立出來到最後真正能獲得 CPU 並進行執行，中間有很多的核心邏輯需要處理，我把它分成了這麼幾個步驟供你更容易地理解。

第一，每個 CPU 核都有一個執行佇列。為了支援不同的排程需求，執行佇列是由實時排程器、完全公平調取器等多種排程器組成。 第一，是程序在 fork 的時候會選擇自己的調取器，使用者程序一般都是用完全公平排程器（fair_sched_class）。 第二，程序建立完前會綜合考慮快取友好性以及空閒狀況，選擇一個 CPU 執行佇列出來，並將新程序新增到該佇列中。 第三，核心有很多的時機來觸發排程。我們文中舉了同步阻塞網路 IO 放棄 CPU 時調取新程序執行的例子。在放棄 CPU 前會從當前 CPU 的執行佇列獲取一個程序出來，上下文切換後執行之。

我們再回到開篇的問題：

問題一 ：程序不主動釋放 CPU 的話，每次排程最少能執行多久？ 在完全公平排程器中，出於減少頻繁切換程序所帶來的成本考慮，一個程序一旦被分配到 CPU 就會持續執行相對較長的一段時間，避免頻繁的程序上下文切換導致的效能損耗。這段時間的最小值由 sched_min_granularity_ns 這個核心引數來控制，單位是 ns (納秒) 。例如下面這個配置的最短執行時間是 10 ms。

當然了，如果程序因為等待網路、磁碟等資源時主動放棄 CPU 那另算。

問題二 ：程序的 nice 值代表的是優先順序嗎，高優先順序是否能搶佔低優先順序的 CPU ？ 在實時任務如 migration 核心執行緒中，是按優先順序排程的。優先順序強調的是搶佔，高優先順序比低優先順序有優先獲得 CPU 的權利。

但是對於使用者程序來講，一般都採用的完全公平排程器來進行 CPU 資源的分配。在這種調取器中，其 nice 其實是一個權重的概念。權重高的程序獲得的 CPU 比例會相對高一些。但不是實時搶佔。
