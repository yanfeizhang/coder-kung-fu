在根據 TCP 的服務開發中，三次握手的主要流程圖如下。

伺服器中的核心邏輯是建立   `socket`, 繫結埠，`listen` 監聽，最後 `accept` 接收用戶端的請求。

//伺服器端核心程式碼
```
int main(int argc, char const *argv[])
{
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    bind(fd, ...);
    listen(fd, 128);
    accept(fd, ...);
```

用戶端的核心邏輯是建立   `socket`，然後呼叫 `connect` 連線 server。

//用戶端核心程式碼
```
int main(){
    fd = socket(AF_INET,SOCK_STREAM, 0);
    connect(fd, ...);
    ...
}
```

關於   `socket` 物件的建立和 `bind` 這裡就先不講，我們直接從和三次握手過程關係最大的 `listen` 講起！

另外本文中核心原始碼會比較多。如果你能理解的了更好，如果覺得不好理解，那直接重點看本文中的加粗字型部分以及最後一節的結論即可。

## 一、伺服器的 `listen`

平時我們都知道，伺服器在開始提供服務之前都需要先   `listen` 一下。但 `listen` 內部究竟做了什麼，我們平時很少去琢磨。

今天就讓我們詳細來看看，直接上一段 `listen` 時執行到的核心核心程式碼。

```
//file: net/core/request_sock.c
int reqsk_queue_alloc(struct request_sock_queue *queue,
              unsigned int nr_table_entries)
{
    size_t lopt_size = sizeof(struct listen_sock);
    struct listen_sock *lopt;

    //計算半連線佇列的長度
    nr_table_entries = min_t(u32, nr_table_entries, sysctl_max_syn_backlog);
    nr_table_entries = ......

    //為半連線佇列申請記憶體
    lopt_size += nr_table_entries * sizeof(struct request_sock *);
    if (lopt_size > PAGE_SIZE)
        lopt = vzalloc(lopt_size);
    else
        lopt = kzalloc(lopt_size, GFP_KERNEL);

    //全連線佇列頭初始化
    queue->rskq_accept_head = NULL;

    //半連線佇列設定
    lopt->nr_table_entries = nr_table_entries;
    queue->listen_opt = lopt;
    ......
}
```

在這段程式碼裡，核心計算半連線佇列 (Connection Queue) 的長度。計算出來了實際大小以後，開始申請用於管理半連線佇列物件的記憶體 (Memory)。最後將半連線佇列掛到了接收佇列 queue 上。

另外 queue->  `rskq_accept_head` 代表的是全連線佇列，它是一個連結串列的形式。在 `listen` 這裡因為還沒有連線，所以將全連線佇列頭 `queue->rskq_accept_head` 設定成 NULL。

當全連線佇列和半連線佇列中有元素的時候，他們在核心中的結構圖大致如下。

所以，在伺服器 `listen` 的時候，主要是進行了全/半連線佇列的長度限制計算，以及相關的記憶體申請和初始化。如果想了解更多的 `listen` 內部操作細節可以看前文 [《為什麼伺服器端程式都需要先 `listen` 一下？》](https://mp.weixin.qq.com/s/hv2tmtVpxhVxr6X-RNWBsQ)

## 二、用戶端   `connect`

用戶端透過呼叫 `connect` 來發起連線。在 `connect` 系統呼叫 (System Call) 中會進入到核心原始碼的 `tcp_v4_connect`。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_connect(struct sock *sk, struct sockaddr *uaddr, int addr_len)
{
    //設定 socket 狀態為 TCP_SYN_SENT
    tcp_set_state(sk, TCP_SYN_SENT);

    //動態選擇一個埠
    err = inet_hash_connect(&tcp_death_row, sk);

    //函式用來根據 sk 中的資訊，構建一個完成的 syn 報文，並將它傳送出去。
    err = tcp_connect(sk);
}
```

在這裡將完成把   `socket` 狀態設定為 `TCP_SYN_SENT`。 再透過 `inet_hash_connect` 來動態地選擇一個可用的埠後（埠選擇詳細過程參考前文 [《TCP 連線中用戶端的埠號是如何確定的？》](https://mp.weixin.qq.com/s/C-Eeoeh9GHxugF4J30fz1A)），進入到 `tcp_connect` 中。

```
//file:net/ipv4/tcp_output.c
int tcp_connect(struct sock *sk)
{
    tcp_connect_init(sk);

    //申請 skb 並構造為一個 SYN 封包
    ......

    //新增到傳送佇列 sk_write_queue 上
    tcp_connect_queue_skb(sk, buff);

    //實際發出 syn
    err = tp->fastopen_req ? tcp_send_syn_data(sk, buff) :
          tcp_transmit_skb(sk, buff, 1, sk->sk_allocation);

    //啟動重傳定時器
    inet_csk_reset_xmit_timer(sk, ICSK_TIME_RETRANS,
                  inet_csk(sk)->icsk_rto, TCP_RTO_MAX);
}
```

在   `tcp_connect` 申請和構造 SYN 封包，然後將其發出。

注意了，當傳送完畢以後，會啟動一個重傳定時器。`tcp_connect_init` 函式將首次超時時間設定成了 1 s (我手頭的版本是 3.10，在一些老版本是是 3 s)。

```

{
    //初始化為 TCP_TIMEOUT_INIT
    inet_csk(sk)->icsk_rto = TCP_TIMEOUT_INIT;
    ......
}
```

`TCP_TIMEOUT_INIT` 在 `include/net/tcp.h` 下被定義成了 1 秒。

```

```

在一些老版本下，例如 `linux/v2.6.30` 下這個初始值是 3 秒。

```
//file: include/net/tcp.h
#define TCP_TIMEOUT_INIT ((unsigned)(3*HZ))
```

總結一下用戶端   `connect` 做的事情，主要是三件。

- 1. 選擇可用的本地埠
- 2. 發出 SYN 握手請求
- 3. 啟動重傳定時器

## 三、伺服器響應 SYN

在伺服器端，所有的 TCP 封包（包括用戶端發來的握手請求）都經過網路卡 (Network Card)、軟中斷 (Softirq)，最後進入到 `tcp_v4_rcv`。 在該函式中根據網路封包（`skb`）TCP 頭資訊中的目的 IP 資訊查到當前在 `listen` 的 `socket`。然後繼續進入 `tcp_v4_do_rcv` 處理握手過程。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_do_rcv(struct sock *sk, struct sk_buff *skb)
{
    ...
    //伺服器收到第一步握手 SYN 或者第三步 ACK 都會走到這裡
    if (sk->sk_state == TCP_LISTEN) {
        struct sock *nsk = tcp_v4_hnd_req(sk, skb);
    }

    if (tcp_rcv_state_process(sk, skb, tcp_hdr(skb), skb->len)) {
        rsk = sk;
        goto reset;
    }
}
```

在   `tcp_v4_do_rcv` 中判斷當前 `socket` 是 `listen` 狀態後，首先會到 `tcp_v4_hnd_req` 去檢視半連線佇列。伺服器第一次響應 SYN 的時候，半連線佇列裡必然是空空如也，所以相當於什麼也沒幹就回傳了。

```
//file:net/ipv4/tcp_ipv4.c
static struct sock *tcp_v4_hnd_req(struct sock *sk, struct sk_buff *skb)
{
    // 查詢 listen socket 的半連線佇列
    struct request_sock *req = inet_csk_search_req(sk, &prev, th->source,
                               iph->saddr, iph->daddr);
    ...
    return sk;
}
```

在   `tcp_rcv_state_process` 里根據不同的 `socket` 狀態進行不同的處理。

```
//file:net/ipv4/tcp_input.c
int tcp_rcv_state_process(struct sock *sk, struct sk_buff *skb,
              const struct tcphdr *th, unsigned int len)
{
    switch (sk->sk_state) {
        //第一次握手
        case TCP_LISTEN:
            if (th->syn) { //判斷是 SYN 握手封包
                ...
                if (icsk->icsk_af_ops->conn_request(sk, skb) < 0)
                    return 1;
    ......

```

其中   `conn_request` 是一個函式指標，指向 `tcp_v4_conn_request`。伺服器響應 SYN 的主要處理邏輯都在這個 `tcp_v4_conn_request` 裡。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_conn_request(struct sock *sk, struct sk_buff *skb)
{
    //看看半連線佇列是否滿了
    if (inet_csk_reqsk_queue_is_full(sk) && !isn) {
        want_cookie = tcp_syn_flood_action(sk, skb, "TCP");
        if (!want_cookie)
            goto drop;
    }

    //在全連線佇列滿的情況下，如果有 young_ack，那麼直接丟
    if (sk_acceptq_is_full(sk) && inet_csk_reqsk_queue_young(sk) > 1) {
        NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENOVERFLOWS);
        goto drop;
    }

    ...

    //分配 request_sock 核心物件
    req = inet_reqsk_alloc(&tcp_request_sock_ops);

    //構造 syn+ack 包
    skb_synack = tcp_make_synack(sk, dst, req,
        fastopen_cookie_present(&valid_foc) ? &valid_foc : NULL);

    if (likely(!do_fastopen)) {
        //傳送 syn + ack 響應
        err = ip_build_and_send_pkt(skb_synack, sk, ireq->loc_addr,
             ireq->rmt_addr, ireq->opt);

        //新增到半連線佇列，並開啟計時器
        inet_csk_reqsk_queue_hash_add(sk, req, TCP_TIMEOUT_INIT);
    }else if (tcp_v4_conn_req_fastopen(sk, skb, skb_synack, req))
}
```

在這裡首先判斷半連線佇列是否滿了，如果滿了的話進入   `tcp_syn_flood_action` 去判斷是否開啟了 `tcp_syncookies` 核心參數 (Kernel Parameter)。如果佇列滿，且未開啟 `tcp_syncookies`，那麼該握手封包將直接被丟棄！！

接著還要判斷全連線佇列是否滿。因為全連線佇列滿也會導致握手異常的，那乾脆就在第一次握手的時候也判斷了。如果全連線佇列滿了，且有 `young_ack` 的話，那麼同樣也是直接丟棄。

>  `young_ack` 是半連線佇列裡保持著的一個計數器。記錄的是剛有 SYN 到達，沒有被 `SYN_ACK` 重傳定時器重傳過 `SYN_ACK`，同時也沒有完成過三次握手的 sock 數量

接下來是構造 synack 包，然後透過 `ip_build_and_send_pkt` 把它傳送出去。

最後把當前握手資訊新增到半連線佇列，並開啟計時器。計時器的作用是如果某個時間之內還收不到用戶端的第三次握手的話，伺服器會重傳 synack 包。

總結一下，其實伺服器響應 ack 洋洋灑灑這麼多程式碼，主要也是三件事。

- 1. 發出 SYN ACK
- 2. 進入半連線佇列
- 3. 啟動定時器

## 五、伺服器響應 ACK

伺服器響應 ack 的時候同樣會進入到 `tcp_v4_do_rcv`

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_do_rcv(struct sock *sk, struct sk_buff *skb)
{
    ...
    if (sk->sk_state == TCP_LISTEN) {
        struct sock *nsk = tcp_v4_hnd_req(sk, skb);
    }

    if (tcp_rcv_state_process(sk, skb, tcp_hdr(skb), skb->len)) {
        rsk = sk;
        goto reset;
    }
}
```

不過由於這已經是第三次握手了，半連線佇列裡會存在上次第一次握手時留下的半連線資訊。所以 `tcp_v4_hnd_req` 的執行邏輯會不太一樣。

```
//file:net/ipv4/tcp_ipv4.c
static struct sock *tcp_v4_hnd_req(struct sock *sk, struct sk_buff *skb)
{
    ...
    struct request_sock *req = inet_csk_search_req(sk, &prev, th->source,
                               iph->saddr, iph->daddr);
    if (req)
        return tcp_check_req(sk, skb, req, prev, false);
    ...
}
```

`inet_csk_search_req` 負責在半連線佇列裡進行查詢，找到以後回傳一個半連線 `request_sock` 物件。然後進入到 `tcp_check_req` 中。

```
//file：net/ipv4/tcp_minisocks.c
struct sock *tcp_check_req(struct sock *sk, struct sk_buff *skb,
               struct request_sock *req,
               struct request_sock **prev,
               bool fastopen)
{
    ...
    //建立子 socket
    child = inet_csk(sk)->icsk_af_ops->syn_recv_sock(sk, skb, req, NULL);
    ...

    //清理半連線佇列
    inet_csk_reqsk_queue_unlink(sk, req, prev);
    inet_csk_reqsk_queue_removed(sk, req);

    //新增全連線佇列
    inet_csk_reqsk_queue_add(sk, req, child);
    return child;
}
```

## 5.1 建立子   `socket`

icsk_af_ops-> `syn_recv_sock` 對應的是 `tcp_v4_syn_recv_sock` 函式。

static inline void reqsk_queue_unlink(struct request_sock_queue *queue, struct request_sock *req,
    struct request_sock **prev_req)
{
    write_lock(&queue->syn_wait_lock);
    *prev_req = req->dl_next; /* 改變了指標的值，相當於刪除了req指向的執行個體 */
    write_unlock(&queue->syn_wait_lock);

## 5.3 新增全連線佇列

接著新增到全連線佇列裡邊來。

```
//file: include/net/request_sock.h
static inline void reqsk_queue_add(struct request_sock_queue *queue,
                   struct request_sock *req,
                   struct sock *parent,
                   struct sock *child)
{
    req->sk = child;
    sk_acceptq_added(parent);

    if (queue->rskq_accept_head == NULL)
        queue->rskq_accept_head = req;
    else
        queue->rskq_accept_tail->dl_next = req;

    queue->rskq_accept_tail = req;
    req->dl_next = NULL;
}
```

伺服器響應第三次握手所做的工作也可以大致歸納成三件

- 1. 建立新 sock
- 2. 從半連線佇列刪除
- 3. 加入全連線佇列

## 六、伺服器   `accept`

估計大家看原始碼看到這裡快吐了都， 最後 `accept` 一步我們就長話短說。

```
//file: net/ipv4/inet_connection_sock.c
struct sock *inet_csk_accept(struct sock *sk, int flags, int *err)
{
    //從全連線佇列中取得
    struct request_sock_queue *queue = &icsk->icsk_accept_queue;
    req = reqsk_queue_remove(queue);

    newsk = req->sk;
    return newsk;
}
```

`reqsk_queue_remove` 這個操作很簡單，就是從全連線佇列的連結串列裡取得出一個頭元素回傳就行了。

```
//file:include/net/request_sock.h
static inline struct request_sock *reqsk_queue_remove(struct request_sock_queue *queue)
{
    struct request_sock *req = queue->rskq_accept_head;

    WARN_ON(req == NULL);

    queue->rskq_accept_head = req->dl_next;
    if (queue->rskq_accept_head == NULL)
        queue->rskq_accept_tail = NULL;

    return req;
}
```

所以，`accept` 的重點工作就是從已經建立好的全連線佇列中取出一個回傳給使用者程序 (Process)。
