# 聊聊 TCP 連線耗時的那些事兒

> 原文標題：聊聊TCP连接耗时的那些事儿

> 原文連結：https://mp.weixin.qq.com/s/wXyerOFoibRsaBmbl224gw

---

在網際網路 (Network) 後端日常開發介面的時候中，不管你使用的是 C、Java、PHP 還是 Golang，都避免不了需要呼叫 mysql、redis 等元件來取得資料，可能還需要執行一些 rpc 遠端呼叫，或者再呼叫一些其他 restful api。 在這些呼叫的底層，基本都是在使用 TCP 協定進行傳輸。這是因為在傳輸層協定中，TCP 協定具備可靠的連線，錯誤重傳，擁塞控制等優點，所以目前應用比 UDP 更廣泛一些。
相信你也一定聽聞過 TCP 也存在一些缺點，那就是老生常談的開銷要略大。但是各路技術部落格裡都在單單說開銷大、或者開銷小，而少見不給出具體的量化分析。不客氣一點，這都是營養不大的廢話。經過日常工作的思考之後，我更想弄明白的是，開銷到底多大。一條 TCP 連線的建立需要耗時延遲多少，是多少毫秒，還是多少微秒？能不能有一個哪怕是粗略的量化估計？當然影響 TCP 耗時的因素有很多，例如網路丟包等等。我今天只分享我在工作實踐中遇到的比較高發的各種情況。

## 正常 TCP 連線建立過程

要想釐清 TCP 連線的建立耗時，我們需要詳細瞭解連線的建立過程。在前文《圖解 Linux 網路封包 (Network Packet) 接收過程》中我們介紹了資料封包在接收端是怎麼被接收的。資料封包從傳送方出來，經過網路到達接收方的網路卡 (Network Card)。在接收方網路卡將資料封包 DMA 到 RingBuffer 後，核心經過硬中斷 (Hardware Interrupt)、軟中斷 (Softirq) 等機制來處理（如果傳送的是使用者資料的話，最後會傳送到   `socket` 的接收佇列中，並喚醒使用者程序 (Process)）。

在軟中斷中，當一個包被核心從 RingBuffer 中摘下來的時候，在核心中是用 struct `sk_buff` 結構體來表示的 (參見核心程式碼 `include/linux/skbuff.h`)。其中的 data 成員是接收到的資料，在協定堆疊逐層被處理的時候，透過修改指標指向 data 的不同位置，來找到每一層協定關心的資料。

透過設定不同的標記為，將 TCP 封包分成 SYNC、FIN、ACK、RST 等型別。用戶端透過  `connect` 系統呼叫 (System Call) 命令核心發出 SYNC、ACK 等包來實作和伺服器 TCP 連線的建立。在伺服器端，可能會接收許許多多的連線請求，核心還需要藉助一些輔助資料結構-半連線佇列 (Connection Queue) 和全連線佇列。我們來看一下整個連線過程：

在這個連線過程中，我們來簡單分析一下每一步的耗時

- 用戶端發出 SYNC 包：用戶端一般是透過  `connect` 系統呼叫來發出 SYN 的，這裡牽涉到本機的系統呼叫和軟中斷的 CPU 耗時開銷
- SYN 傳到伺服器：SYN 從用戶端網路卡被髮出，開始「跨過山和大海，也穿過人山人海~~~」，這是一次長途遠距離的網路傳輸
- 伺服器處理 SYN 封包：核心透過軟中斷來接收封包，然後放到半連線佇列中，然後再發出  `SYN/ACK` 響應。又是 CPU 耗時開銷
- `SYC/ACK` 傳到用戶端：`SYC/ACK` 從伺服器端被髮出後，同樣跨過很多山、可能很多大海來到用戶端。又一次長途網路跋涉
- 用戶端處理  `SYN/ACK`：用戶端核心接收封包並處理 SYN 後，經過幾 us 的 CPU 處理，接著發出 ACK。同樣是軟中斷處理開銷
- ACK 傳到伺服器：和 SYN 封包，一樣，再經過幾乎同樣遠的路，傳輸一遍。 又一次長途網路跋涉
- 伺服器端收到 ACK：伺服器端核心收到並處理 ACK，然後把對應的連線從半連線佇列中取出來，然後放到全連線佇列中。一次軟中斷 CPU 開銷
- 伺服器端使用者程序喚醒：正在被 accpet 系統呼叫阻塞的使用者程序被喚醒，然後從全連線佇列中取出來已經建立好的連線。一次上下文切換 (Context Switch) 的 CPU 開銷

以上幾步操作，可以簡單劃分為兩類：

- 第一類是核心消耗 CPU 進行接收、傳送或者是處理，包括系統呼叫、軟中斷和上下文切換。它們的耗時基本都是幾個 us 左右。具體的分析過程可以參見《一次系統呼叫開銷到底有多大？》、《軟中斷會吃掉你多少 CPU？》、《程序/執行緒 (Thread) 切換會用掉你多少 CPU？》這三篇文章。
- 第二類是網路傳輸，當包被從一臺機器上發出以後，中間要經過各式各樣的網線、各種交換機路由器。所以網路傳輸的耗時相比本機的 CPU 處理，就要高的多了。根據網路遠近一般在幾 ms\~到幾百 ms 不等。。

1ms 就等於 1000us，因此網路傳輸耗時比雙端的 CPU 開銷要高 1000 倍左右，甚至更高可能還到 100000 倍。所以，在正常的 TCP 連線的建立過程中，一般可以考慮網路延遲即可。一個 RTT 指的是包從一臺伺服器到另外一臺伺服器的一個來回的延遲時間。所以從全域性來看，TCP 連線建立的網路耗時大約需要三次傳輸，再加上少許的雙方 CPU 開銷，總共大約比 1.5 倍 RTT 大一點點。不過從用戶端視角來看，只要 ACK 包發出了，核心就認為連線是建立成功了。所以如果在用戶端打點統計 TCP 連線建立耗時的話，只需要兩次傳輸耗時-既 1 個 RTT 多一點的時間。（對於伺服器端視角來看同理，從 SYN 封包收到開始算，到收到 ACK，中間也是一次 RTT 耗時）

## TCP 連結建立時的異常情況

上一節可以看到在用戶端視角，在正常情況下一次 TCP 連線總的耗時也就就大約是一次網路 RTT 的耗時。如果所有的事情都這麼簡單，我想我的這次分享也就沒有必要了。事情不一定總是這麼美好，總會有意外發生。在某些情況下，可能會導致連線時的網路傳輸耗時上漲、CPU 處理開銷增加、甚至是連線失敗。現在我們說一下我線上上遇到過的各種溝溝坎坎。

1. 用戶端  `connect` 系統呼叫耗時失控

正常一個系統呼叫的耗時也就是幾個 us（微秒）左右。但是在《追蹤將伺服器 CPU 耗光的兇手!》一文中筆者的一臺伺服器當時遇到一個狀況，某次運維同學轉達過來說該服務 CPU 不夠用了，需要擴容。當時的伺服器監控如下圖：

該服務之前一直每秒抗 2000 左右的 qps，CPU 的 idel 一直有 70%+。怎麼突然就 CPU 一下就不夠用了呢。而且更奇怪的是 CPU 被打到谷底的那一段時間，負載卻並不高（伺服器為 4 核機器，負載 3-4 是比較正常的）。 後來經過排查以後發現當 TCP 用戶端  `TIME_WAIT` 有 30000 左右，導致可用埠不是特別充足的時候，`connect` 系統呼叫的 CPU 開銷直接上漲了 100 多倍，每次耗時達到了 2500us（微秒），達到了毫秒級別。

當遇到這種問題的時候，雖然 TCP 連線建立耗時只增加了 2ms 左右，整體 TCP 連線耗時看起來還可接受。但是這裡的問題在於這 2ms 多都是在消耗 CPU 的週期，所以問題不小。
解決起來也非常簡單，辦法很多：修改核心參數 (Kernel Parameter)  net.ipv4.ip_local_port_range 多預留一些埠號、改用長連線都可以。

2. 半/全連線佇列滿

如果連線建立的過程中，任意一個佇列滿了，那麼用戶端傳送過來的 syn 或者 ack 就會被丟棄。用戶端等待很長一段時間無果後，然後會發出 TCP Retransmission 重傳。拿半連線佇列舉例：

要知道的是上面 TCP 握手超時重傳的時間是秒級別的。也就是說一旦 server 端的連線佇列導致連線建立不成功，那麼光建立連線就至少需要秒級以上。而正常的在同機房的情況下只是不到 1 毫秒的事情，整整高了 1000 倍左右。尤其是對於給使用者提供實時服務的程式來說，使用者體驗將會受到較大影響。如果連重傳也沒有握手成功的話，很可能等不及二次重試，這個使用者存取直接就超時了。

還有另外一個更壞的情況是，它還有可能會影響其他的使用者。假如你使用的是程序/執行緒池這種模型提供服務，例如  php-fpm。我們知道 fpm 程序是阻塞的，當它響應一個使用者請求的時候，該程序是沒有辦法再響應其他請求的。假如你開了 100 個程序/執行緒，而某一段時間內有 50 個程序/執行緒卡在和 redis 或者 mysql 伺服器的握手連線上了（注意：這個時候你的伺服器是 TCP 連線的用戶端一方）。這一段時間內相當於你可以用的正常工作的程序/執行緒只有 50 個了。而這個 50 個 worker 可能根本處理不過來，這時候你的服務可能就會產生擁堵。再持續稍微時間長一點的話，可能就產生雪崩了，整個服務都有可能會受影響。

既然後果有可能這麼嚴重，那麼我們如何檢視我們手頭的服務是否有因為半/全連線佇列滿的情況發生呢？在用戶端，可以擷取封包檢視是否有 SYN 的 TCP Retransmission。如果有偶發的 TCP Retransmission，那就說明對應的伺服器端連線佇列可能有問題了。

在伺服器端的話，檢視起來就更方便一些了。 netstat-s 可檢視到當前系統半連線佇列滿導致的丟包統計，但該數字記錄的是總丟封包數。你需要再借助 `watch` 命令動態監控。如果下面的數字在你監控的過程中變了，那說明當前伺服器有因為半連線佇列滿而產生的丟包。你可能需要加大你的半連線佇列的長度了。

```
$ watch 'netstat -s | grep LISTEN'
    8 SYNs to LISTEN sockets ignored
```

對於全連線佇列來說呢，檢視方法也類似。

```
$ watch 'netstat -s  | grep overflowed'
    160 times the listen queue of a socket overflowed
```

如果你的服務因為佇列滿產生丟包，其中一個做法就是加大半/全連線佇列的長度。 半連線佇列長度 Linux 核心 (Linux Kernel) 中，主要受 `tcp_max_syn_backlog` 影響加大它到一個合適的值就可以。

```
# cat /proc/sys/net/ipv4/tcp_max_syn_backlog
1024
# echo "2048" > /proc/sys/net/ipv4/tcp_max_syn_backlog
```

全連線佇列長度是應用程式呼叫   `listen` 時傳入的 backlog 以及核心參數 net.core.somaxconn 二者之中較小的那個。你可能需要同時調整你的應用程式和該核心參數。

```
# cat /proc/sys/net/core/somaxconn
128
# echo "256" > /proc/sys/net/core/somaxconn
```

改完之後我們可以透過 ss 命令輸出的 Send-Q 確認最終生效長度：

```
$ ss -nlt
Recv-Q Send-Q Local Address:Port Address:Port
0      128    *:80               *:*
```

>Recv-Q 告訴了我們當前該程序的全連線佇列使用長度情況。如果   Recv-Q 已經逼近了 Send-Q,那麼可能不需要等到丟包也應該準備加大你的全連線佇列了。

如果加大佇列後仍然有非常偶發的佇列溢位的話，我們可以暫且容忍。如果仍然有較長時間處理不過來怎麼辦？另外一個做法就是直接報錯，不要讓用戶端超時等待。例如將 Redis、Mysql 等後端介面的核心參數 `tcp_abort_on_overflow` 為 1。如果佇列滿了，直接發 reset 給 client。告訴後端程序/執行緒不要痴情地傻等。這時候 client 會收到錯誤「connection reset by peer」。犧牲一個使用者的存取請求，要比讓整個服務都崩潰還是要強的。

## TCP 連線耗時實測

我寫了一段非常簡單的程式碼，用來在用戶端統計每建立一個 TCP 連線需要消耗多長時間。

```
<?php
$ip = {伺服器ip};
$port = {伺服器埠};
$count = 50000;
function buildConnect($ip,$port,$num){
    for($i=0;$i<$num;$i++){
        $socket = socket_create(AF_INET,SOCK_STREAM,SOL_TCP);
        if($socket ==false) {
            echo "$ip $port socket_create() 失敗的原因是:".socket_strerror(socket_last_error($socket))."\n";
            sleep(5);
            continue;
        }

        if(false == socket_connect($socket, $ip, $port)){
            echo "$ip $port socket_connect() 失敗的原因是:".socket_strerror(socket_last_error($socket))."\n";
            sleep(5);
            continue;
        }
        socket_close($socket);
    }
}

$t1 = microtime(true);
buildConnect($ip, $port, $count);
echo (($t2-$t1)*1000).'ms';
```

在測試之前，我們需要本機 linux 可用的埠數充足，如果不夠 50000 個，最好調整充足。

```
# echo "5000   65000" /proc/sys/net/ipv4/ip_local_port_range
```

1. 正常情況
注意：無論是用戶端還是伺服器端都不要選擇有線上服務在跑的機器，否則你的測試可能會影響正常使用者存取

首先我的用戶端位於河北懷來的 IDC 機房內，伺服器選擇的是公司廣東機房的某臺機器。執行 ping 命令得到的延遲大約是 37ms，使用上述指令碼建立 50000 次連線後，得到的連線平均耗時也是 37ms。這是因為前面我們說過的，對於用戶端來看，第三次的握手只要包傳送出去，就認為是握手成功了，所以只需要一次 RTT、兩次傳輸耗時。雖然這中間還會有用戶端和伺服器端的系統呼叫開銷、軟中斷開銷，但由於它們的開銷正常情況下只有幾個 us(微秒)，所以對總的連線建立延遲影響不大。

接下來我換了一臺目標伺服器，該伺服器所在機房位於北京。離懷來有一些距離，但是和廣東比起來可要近多了。這一次 ping 出來的 RTT 是 1.6\~1.7ms 左右，在用戶端統計建立 50000 次連線後算出每條連線耗時是 1.64ms。

再做一次實驗，這次選中實驗的伺服器和用戶端直接位於同一個機房內，ping 延遲在 0.2ms\~0.3ms 左右。跑了以上指令碼以後，實驗結果是 50000 TCP 連線總共消耗了 11605ms，平均每次需要 0.23ms。

> 線上架構提示：這裡看到同機房延遲只有零點幾 ms，但是跨個距離不遠的機房，光 TCP 握手耗時就漲了 4 倍。如果再要是跨地區到廣東，那就是百倍的耗時差距了。線上部署時，理想的方案是將自己服務依賴的各種 mysql、redis 等服務和自己部署在同一個地區、同一個機房（再變態一點，甚至可以是甚至是同一個機架）。因為這樣包括 TCP 連結建立什麼的各種網路封包傳輸都要快很多。要儘可能避免長途跨地區機房的呼叫情況出現。

2. 連線佇列溢位

測試完了跨地區、跨機房和跨機器。這次為了快，直接和本機建立連線結果會怎麼樣呢？
Ping 本機 ip 或 127.0.0.1 的延遲大概是 0.02ms，本機 ip 比其他機器 RTT 肯定要短。我覺得肯定連線會非常快，嗯實驗一下。連續建立 5W TCP 連線，總時間消耗 27154ms，平均每次需要 0.54ms 左右。嗯！？怎麼比跨機器還長很多？
有了前面的理論基礎，我們應該想到了，由於本機 RTT 太短，所以瞬間連線建立請求量很大，就會導致全連線佇列或者半連線佇列被打滿的情況。一旦發生佇列滿，當時撞上的那個連線請求就得需要 3 秒+的連線建立延遲。所以上面的實驗結果中，平均耗時看起來比 RTT 高很多。

在實驗的過程中，我使用 `tcpdump` 擷取封包看到了下面的一幕。原來有少部分握手耗時 3s+，原因是半連線佇列滿了導致用戶端等待超時後進行了 SYN 的重傳。

我們又重新改成每 500 個連線，sleep 1 秒。嗯好，終於沒有卡的了（或者也可以加大連線佇列長度）。結論是本機 50000 次 TCP 連線在用戶端統計總耗時 102399 ms，減去 sleep 的 100 秒後，平均每個 TCP 連線消耗 0.048ms。比 ping 延遲略高一些。這是因為當 RTT 變的足夠小的時候，核心 CPU 耗時開銷就會顯現出來了，另外 TCP 連線要比 ping 的 icmp 協定更復雜一些，所以比 ping 延遲略高 0.02ms 左右比較正常。

## 結論

TCP 連線建立異常情況下，可能需要好幾秒，一個壞處就是會影響使用者體驗，甚至導致當前使用者存取超時都有可能。另外一個壞處是可能會誘發雪崩。所以當你的伺服器使用短連線的方式存取資料的時候，一定要學會要監控你的伺服器的連線建立是否有異常狀態發生。如果有，學會最佳化掉它。當然你也可以採用本機記憶體 (Memory) 快取 (Cache)，或者使用連線池來保持長連線，透過這兩種方式直接避免掉 TCP 握手揮手的各種開銷也可以。

再說正常情況下，TCP 建立的延遲大約就是兩臺機器之間的一個 RTT 耗時，這是避免不了的。但是你可以控制兩臺機器之間的實體距離來降低這個 RTT，例如把你要存取的 redis 儘可能地部署的離後端介面機器近一點，這樣 RTT 也能從幾十 ms 削減到最低可能零點幾 ms。

最後我們再思考一下，如果我們把伺服器部署在北京，給紐約的使用者存取可行嗎？
前面的我們同機房也好，跨機房也好，電訊號傳輸的耗時基本可以忽略（因為實體距離很近），網路延遲基本上是轉發裝置佔用的耗時。但是如果是跨越了半個地球的話，電訊號的傳輸耗時我們可得算一算了。
北京到紐約的球面距離大概是 15000 公里，那麼拋開裝置轉發延遲，僅僅光速傳播一個來回（RTT 是 Rround trip time，要跑兩次），需要時間 = 15,000,000 *2 / 光速 = 100ms。實際的延遲可能比這個還要大一些，一般都得 200ms 以上。建立在這個延遲上，要想提供使用者能存取的秒級服務就很困難了。所以對於海外使用者，最好都要在當地建機房或者購買海外的伺服器。
