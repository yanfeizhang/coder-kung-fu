# 機械硬碟 (Hard Disk Drive, HDD) 隨機 IO 慢的超乎你的想像

大家都知道硬碟的隨機 IO 很慢，但是比順序 IO 慢多少呢，不知道你是否有過數字上的直接對比。今天我來實際壓測對比一下磁碟 (Disk) 在順序 IO 和隨機 IO 不同場景下的效能資料表現。透過今天的實驗資料，你將能深刻理解資料庫事務中為什麼要用日誌的方式來實作，為什麼索引中要用節點更大的 B+樹。

對於任何儲存系統，效能指標無非就是頻寬、延遲或 IOPS。我的測試機器的硬碟設定是一個由 7 塊 300G 萬轉機械磁碟組成的 RAID5，壓測工具使用的 fio，壓測過程中，我們固定幾個參數：

- IO 引擎我們選擇 libaio
- 為了避免作業系統 (Operating System) 管理的 PageCache 記憶體 (Memory) 對測試結果的干擾，使用 direct 參數繞開
- 開啟   `unified_rw_reporting`，讓結果中分別顯示讀和寫
- 為了保證測試相對準確，我們執行時間設定為 300s
- 由於伺服器敏感性，壓測物件沒有選擇裸裝置，用的檔案，會有一點檔案系統 (File System) 額外開銷
- 測試檔案尺寸定義為 100G，我的 RAID 卡快取 (Cache) 是 1G，目的就是讓它的命中率別太高
- 排程策略我們選擇最最常用的 noop
- 開啟 `refill_buffers`，每次 `I/O` 提交後都重新產生測試檔案資料片段，保證隨機性
- 按照 RAID 使用設定建議，關閉掉磁碟自帶快取

然後再對另外的參數進行動態調整，然後進行多次對比測試

- 讀寫模式上，使用順序讀和隨機讀進行分別驗證
- 磁碟 IO 單位我們使用扇區的整數倍，512 1K 2K ...
- RAID 卡預讀策略，分別設定 NORA（不開啟預讀）和 RA（開啟預讀）來獨立測試

順序讀取測試

我們先來看一下順序讀取情況下，在該磁碟陣列的頻寬表現，見圖 1：

?

可以看到，當 IO size 比較小的時候，即使是順序發起連續 IO 請求，頻寬表現也不算給力，只有不到 `20MB/s`。隨著 IO size 增加的時候，頻寬也上來了,最大能夠達到 1.2GB 多。

大家注意看下在 NORA 情況下，在 128K 增加到 256K 的時候，頻寬突然增加了很多，這是為什麼呢？秘密在於我的 RAID 陣列裡的條帶大小是 128K,當 IO size 為 256K 的時候，磁碟陣列才開始真正並行工作了。IO size 小的時候，並不能發揮多盤優勢。

Strip Size          : 128 KB

另外就是對於順序 IO 的情況，RA 預取也能起到一些作用，在 IO size 在 64k 的時候就能夠達到 1.2GB 的頻寬。

我們再來看延遲，見圖 2

我們圖中的單位是微秒-us，在《磁碟分割槽也是隱含了技術技巧的》中，我對磁碟耗時進行過理論上的估算，磁碟耗時主要在兩個地方：

- 尋道時間：3-15ms，這個耗時可以透過合理分割槽最佳化
- 旋轉延遲：萬轉磁碟這個延遲大概 0-6ms

為什麼在圖 2 實驗結果裡，延遲卻都很低，在 IO size 為 512 的時候，平均竟然只有 30us 左右？其實順序 IO 的情況下，RAID 卡快取命中率很高，其實絕大部分的讀請求並沒有穿透到讓磁碟的機械軸來工作。

我們再來看 IOPS，見圖 3

在 IO 請求 size 正好為 1 個扇區大小的時候，磁碟陣列的 IOPS 表現最高，達到了 3W 多次每秒。當 IO size 增加的時候，IOPS 在逐步下降，但這時候，其實磁碟的吞吐是在增加的。

彙總一下，磁碟陣列在順序 IO 的情況下表現還是很不錯的，原因有三個：

- 順序 IO 的情況下，RAID 卡的命中率高，尤其是設定了 RAID 預取
- 單盤本身順序 IO 也是磁碟工作最舒服的狀態，因為節約了尋道的延遲
- 當 IO 超過 RAID 條狀大小的時候，IO 會分散到多塊盤上並行處理

隨機讀取測試

我們作為開發者使用磁碟的時候，可能不一定能保證永遠都能讓它工作在最舒服的狀態，有些時候可能也必須得讓它進行隨機存取。所以我們今天也試一下我的磁碟陣列在隨機情況下的表現，對於 fio 工具來說只需要設定 rw 參數為 randread 既可。不過 IO size 我只測試到了 128 就停了，因為再大了就越像順序 IO 了。

機械硬碟即使是組成了 RAID 陣列，而且還有快取，貌似對隨機 IO 也無可奈何。在隨機 IO 的情況下，頻寬吞吐糟糕透了，在 IO size 比較小的時候，竟然只有零點幾兆每秒。

我們再來看延遲，見圖 5：

?

隨機情況下延遲基本都 5ms 左右，這就和我們前面理論上的計算結果對上了。隨機存取導致更多的請求真正穿透到了機械軸上。

再來看 IOPS，這個指標也很差，也就是 200 左右吧。這個資料和圖 5 的延遲形成了呼應，處理一次請求 5ms 左右，那麼 1 秒可不就是隻能處理 200 次左右麼。所以硬碟廠家們天天給你吹風，說他家磁碟 IOPS 能達到幾萬幾萬。但是他們從來閉口不提隨機 IO 情況下，其實真是的只有 200。

?

大家看到了我的萬轉機械硬碟組成 RAID5 陣列，在順序條件最好的情況下，頻寬可以達到 `1GB/s` 以上，平均延遲也非常低，最低只有 20 多 us。但是在隨機 IO 的情況下，機械硬碟的短板就充分暴露了，零點幾兆的頻寬，將近 5ms 的延遲，IOPS 只有 200 左右。其原因是因為

- 隨機存取直接讓 RAID 卡快取成了個擺設
- 磁碟不能並行工作，因為我的機器 RAID 寬度 Strip Size 為 128 KB
- 機械軸也得在各個磁軌之間跳來跳去。

理解了磁碟順序 IO 時候的幾十 M 甚至一個 GB 的頻寬，隨機 IO 這個真的是太可憐了。

3

結論

從上面的測試資料中我們看到了機械硬碟在順序 IO 和隨機 IO 下的巨大效能差異。在順序 IO 情況下，磁碟是最擅長的順序 IO,再加上 Raid 卡快取命中率也高。這時頻寬表現有幾十、幾百 M，最好條件下甚至能達到 1GB。IOPS 這時候能有 2-3W 左右。到了隨機 IO 的情形下，機械軸也被逼的跳來跳去尋道，RAID 卡快取也失效了。頻寬跌到了 1MB 以下，最低只有 100K，IOPS 也只有可憐巴巴的 200 左右。

如果你真正理解了以上實驗中的資料，就能理解很多工程實踐中的許多的事情。

- 複製資料夾：我們都知道，在複製一個資料夾的時候，如果這個資料夾裡面包含了許多堆碎檔案，這時候複製起來非常慢。原因就是這時候機械硬碟大機率都是在隨機 IO。怎麼提高複製速度呢？很簡單，就是把它們先打一個包。打包之後這個資料夾就變成一個大檔案了，這時候再複製的話，磁碟就是執行的最擅長的順序 IO 了，所以會快很多。
- 資料庫事務：所有的資料庫在實作事務的時候，都要保證寫資料落盤成功才能回傳。但為什麼他們幾乎都是落盤到自己的事務日誌檔案裡去就回傳成功的，而不是直接寫入到資料表檔案裡。這背後的原因還是磁碟讀寫效能問題，事務只需要保證資料落地成功就可以，至於寫到哪裡並不重要。寫到資料檔案中的話大機率就變成隨機 IO 了。如果寫到一個日誌檔案中，就是地地道道的順序 IO，效能就發揮到極致。
- Mysql 的 B+樹：在上面的資料中大家還可以看到，無論是順序 IO 還是隨機 IO，只要增加每次 IO 的單位，效能都會上漲。理解了這個，你就能真正理解為什麼 Mysql 是採用 B+樹當索引，而不是用其他的樹了（例如二叉樹）。因為 B+樹的節點更大，IO 起來會讓磁碟工作更舒服一些。

4

最後

結尾我想再分享一個 5 年前我在工程中實際效能最佳化的案例。當時接手了一個系統，要用數以百萬級的使用者 imei，到 Mysql 中去查詢使用者的另一個字串 id（clientid）資料。前開發的實作方式是傳統的分批進行 Mysql 語句查詢。這種實作下，且不說多次的網路 (Network) RTT 耗時，單說 Mysql 查詢，即使是有索引這時候也得需要進行大量的隨機 IO，因為使用者 imei 是隨機分佈的。我採用的最佳化方式也非常簡單，直接把 Mysql 使用者整張使用者表一次性透過順序 IO 的方式讀出來，load 到記憶體中。在記憶體中用 HashTable 組織好，透過 Hash 的方式進行快速查詢。最終耗時最佳化掉了 90% 以上。
