現在你可能還覺得 Node、zone、夥伴系統、slab 這些東西還有那麼一點點陌生。別怕，接下來我們結合動手觀察，把它們逐個來展開細說。（下面的討論都根據 Linux 3.10.0 版本）

## 一、NODE 劃分

在現代的伺服器上，記憶體和 CPU 都是所謂的 NUMA 架構

CPU 往往不止是一顆。透過 `dmidecode` 命令看到你主機板上插著的 CPU 的詳細資訊

記憶體也不只是一條。`dmidecode` 同樣可以檢視到伺服器上插著的所有記憶體條，也可以看到它是和哪個 CPU 直接連線的。

## 二、ZONE 劃分

每個 node 又會劃分成若干的 zone（區域）。zone 表示記憶體中的一塊範圍

- `ZONE_DMA`：位址段最低的一塊記憶體區域，ISA(Industry Standard Architecture) 裝置 DMA 存取
- `ZONE_DMA32`：該 Zone 用於支援 32-bits 位址匯流排的 DMA 裝置，只在 64-bits 系統裡才有效
- `ZONE_NORMAL`：在 X86-64 架構下，DMA 和 DMA32 之外的記憶體全部在 NORMAL 的 Zone 裡管理

> 為什麼沒有提 `ZONE_HIGHMEM` 這個 zone？ 因為這是 32 位機時代的產物。現在應該沒誰在用這種古董了吧。

在每個 zone 下，都包含了許許多多個 Page（頁面）， 在 linux 下一個 Page 的大小一般是 4 KB。

在你的機器上，你可以使用透過 zoneinfo 檢視到你機器上 zone 的劃分，也可以看到每個 zone 下所管理的頁面有多少個。

```
# cat /proc/zoneinfo
Node 0, zone      DMA
pages free     3973
managed  3973
Node 0, zone    DMA32
pages free     390390
managed  427659
Node 0, zone   Normal
pages free     15021616
managed  15990165
Node 1, zone   Normal
pages free     16012823
managed  16514393

每個頁面大小是 4K，很容易可以計算出每個 zone 的大小。例如對於上面 Node1 的 Normal， 16514393 * 4K = 66 GB。
```

## 三、根據夥伴系統管理空閒頁面

每個 zone 下面都有如此之多的頁面，Linux 使用夥伴系統對這些頁面進行高效的管理。 在核心中，表示 zone 的資料結構是 struct zone。 其下面的一個陣列 `free_area` 管理了絕大部分可用的空閒頁面。這個陣列就是夥伴系統實作的重要資料結構。

```
//file: include/linux/mmzone.h
#define MAX_ORDER 11
struct zone {
    free_area   free_area[MAX_ORDER];
    ......
}
```

`free_area` 是一個 11 個元素的陣列，在每一個陣列分別代表的是空閒可分配連續 4K、8K、16K、......、4M 記憶體連結串列。

透過 `cat/proc/pagetypeinfo`, 你可以看到當前系統裡夥伴系統裡各個尺寸的可用連續記憶體塊數量。

核心提供分配器函式 `alloc_pages` 到上面的多個連結串列中尋找可用連續頁面。

```
struct page * alloc_pages(gfp_t gfp_mask, unsigned int order)
```

`alloc_pages` 是怎麼工作的呢？我們舉個簡單的小例子。假如要申請 8K-連續兩個頁框的記憶體。為了描述方便，我們先暫時忽略 UNMOVEABLE、RELCLAIMABLE 等不同型別

> 夥伴系統中的夥伴指的是兩個記憶體塊，大小相同，位址連續，同屬於一個大塊區域。

根據夥伴系統的記憶體分配中，有可能需要將大塊記憶體拆分成兩個小夥伴。在釋放中，可能會將兩個小夥伴合併再次組成更大塊的連續記憶體。

## 四、SLAB 管理器

說到現在，不知道你注意到沒有。目前我們介紹的記憶體分配都是以頁面（4KB）為單位的。

對於各個核心執行中實際使用的物件來說，多大的物件都有。有的物件有 1K 多，但有的物件只有幾百、甚至幾十個位元組。如果都直接分配一個 4K 的頁面來儲存的話也太敗家了，所以夥伴系統並不能直接使用。

在夥伴系統之上，核心又給自己建立了一個專用的記憶體分配器， 叫 slab 或 slub。 這兩個詞老混用，為了省事，接下來我們就統一叫 slab 吧。

這個分配器最大的特點就是，一個 slab 內只分配特定大小、甚至是特定的物件。這樣當一個物件釋放記憶體後，另一個同類物件可以直接使用這塊記憶體。透過這種辦法極大地降低了碎片發生的機率。

slab 相關的核心物件定義如下：

```
//file: include/linux/slab_def.h
struct kmem_cache {
    struct kmem_cache_node **node
    ......
}
```

```
//file: mm/slab.h
struct kmem_cache_node {
    struct list_head slabs_partial;
    struct list_head slabs_full;
    struct list_head slabs_free;
    ......
}
```

每個 cache 都有滿、半滿、空三個連結串列。 每個連結串列節點都對應一個 slab，一個 slab 由 1 個或者多個記憶體頁組成。

在每一個 slab 內都儲存的是同等大小的物件。一個 cache 的組成示意圖如下：

當 cache 中記憶體不夠的時候，會呼叫根據夥伴系統的分配器（\_\_alloc_pages 函式）請求整頁連續記憶體的分配。

```
//file: mm/slab.c
static void *kmem_getpages(struct kmem_cache *cachep,
         gfp_t flags, int nodeid)
{
    ......
    flags |= cachep->allocflags;
    if (cachep->flags & SLAB_RECLAIM_ACCOUNT)
        flags |= __GFP_RECLAIMABLE;

    page = alloc_pages_exact_node(nodeid, ...);
    ......
}
```

```
//file: include/linux/gfp.h
static inline struct page *alloc_pages_exact_node(int nid,
        gfp_t gfp_mask,unsigned int order)
{
    return __alloc_pages(gfp_mask, order, node_zonelist(nid, gfp_mask));
}
```

核心中會有很多個   `kmem_cache` 存在。它們是在 linux 初始化，或者是執行的過程中分配出來的。它們有的是專用的，有的是通用的。

上圖中，我們看到 `socket_alloc` 核心物件都存在 TCP 的專用 `kmem_cache` 中。

透過檢視 `/proc/slabinfo` 我們可以檢視到所有的 kmem cache。

另外 linux 還提供了一個特別方便的命令 slabtop 來按照佔用記憶體從大往小進行排列。這個命令用來分析 slab 記憶體開銷非常的方便。

無論是 / `proc/slabinfo`，還是 slabtop 命令的輸出。裡面都包含了每個 cache 中 slab 的如下兩個關鍵資訊。

- objsize：每個物件的大小
- objperslab： 一個 slab 裡存放的物件的數量

在 `/proc/slabinfo` 還多輸出了一個 pagesperslab。 展示了一個 slab 佔用的頁面的數量，每個頁面 4K，這樣也就能算出每個 slab 佔用的記憶體大小。

最後，slab 管理器元件提供了若干介面函式，方便自己使用。舉三個例子：

- `kmem_cache_create`: 方便地建立一個根據 slab 的核心物件管理器。
- `kmem_cache_alloc`: 快速為某個物件申請記憶體
- `kmem_cache_free`: 歸還物件佔用的記憶體給 slab 管理器

在核心的原始碼中，可以大量見到 `kmem_cache` 開頭函式的使用。

## 總結

透過上面描述的幾個步驟，核心高效地把記憶體用了起來。

- 第一步：把所有的記憶體條和 CPU 劃分成 node
- 第二步：把每一個 node 劃分成 zone
- 第三步：每個 zone 下都用夥伴系統管理空閒頁面
- 第四步：核心提供 slab 分配器為自己專用

前三步是基礎模組，為應用程式分配記憶體時的請求調頁元件也能夠用到。但第四步，就算是核心的小灶了。核心根據自己的使用場景，量身打造的一套自用的高效記憶體分配管理機制。

```
# cat /proc/slabinfo | grep TCP
TCP                  288    384   1984   16    8

「可以看到 TCP cache 下每個 slab 佔用 8 個 Page，也就是 8* 4096 = 32768 位元組。
該物件的單個大小是 1984 位元組位元組，每個 slab 內放了 16 個物件。1984*16=31744」
```

「這個時候再多放一個 TCP 物件又放不下，剩下的 1K 記憶體就只好「浪費」掉了。 但是鑑於 slab 機制整體提供的高效能、以及低碎片的效果，這一點點的額外開銷還是很值得的。」
