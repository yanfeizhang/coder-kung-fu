# 說出來你可能不信，核心這傢伙在記憶體的使用上給自己開了個小灶！

> 原文標題：说出来你可能不信，内核这家伙在内存的使用上给自己开了个小灶！

> 原文連結：http://kfngxl.cn/index.php/archives/529/

---

現在你可能還覺得Node、zone、夥伴系統、slab這些東東還有那麼一點點陌生。別怕，接下來我們結合動手觀察，把它們逐個來展開細說。​（下面的討論都基於Linux 3.10.0版本）

一、NODE 劃分

在現代的伺服器上，記憶體和CPU都是所謂的NUMA架構

CPU往往不止是一顆。透過dmidecode命令看到你主機板上插著的CPU的詳細資訊

記憶體也不只是一條。dmidecode同樣可以檢視到伺服器上插著的所有記憶體條，也可以看到它是和哪個CPU直接連線的。

每一個CPU以及和他直連的記憶體條組成了一個 node（節點） 。

在你的機器上，你可以使用numactl你可以看到每個node的情況

二、ZONE 劃分

每個 node 又會劃分成若干的 zone（區域） 。zone 表示記憶體中的一塊範圍

ZONE_DMA：地址段最低的一塊記憶體區域，ISA(Industry Standard Architecture)裝置DMA訪問

ZONE_DMA32：該Zone用於支援32-bits地址匯流排的DMA裝置，只在64-bits系統裡才有效

ZONE_NORMAL：在X86-64架構下，DMA和DMA32之外的記憶體全部在NORMAL的Zone裡管理

在每個zone下，都包含了許許多多個 Page（頁面）， 在linux下一個Page的大小一般是 4 KB。

在你的機器上，你可以使用透過 zoneinfo 檢視到你機器上 zone 的劃分，也可以看到每個 zone 下所管理的頁面有多少個。

每個頁面大小是4K，很容易可以計算出每個 zone 的大小。比如對於上面 Node1 的 Normal， 16514393 * 4K = 66 GB。

三、基於夥伴系統管理空閒頁面

每個 zone 下面都有如此之多的頁面，Linux使用 夥伴系統 對這些頁面進行高效的管理。 在核心中，表示 zone 的資料結構是 struct zone 。 其下面的一個陣列 free_area 管理了絕大部分可用的空閒頁面。這個陣列就是 夥伴系統 實現的重要資料結構。

free_area是一個11個元素的陣列，在每一個陣列分別代表的是空閒可分配連續4K、8K、16K、......、4M記憶體連結串列。

透過 cat /proc/pagetypeinfo , 你可以看到當前系統裡夥伴系統裡各個尺寸的可用連續記憶體塊數量。

核心提供分配器函式 alloc_pages 到上面的多個連結串列中尋找可用連續頁面。

alloc_pages 是怎麼工作的呢？我們舉個簡單的小例子。假如要申請8K-連續兩個頁框的記憶體。為了描述方便，我們先暫時忽略UNMOVEABLE、RELCLAIMABLE等不同型別

基於夥伴系統的記憶體分配中，有可能需要將大塊記憶體拆分成兩個小夥伴。在釋放中，可能會將兩個小夥伴合併再次組成更大塊的連續記憶體。

四、SLAB管理器

說到現在，不知道你注意到沒有。目前我們介紹的記憶體分配都是 以頁面（4KB）為單位的 。

對於各個核心執行中實際使用的物件來說，多大的物件都有。有的物件有1K多，但有的物件只有幾百、甚至幾十個位元組。如果都直接分配一個 4K的頁面 來儲存的話也太敗家了，所以夥伴系統並不能直接使用。

在夥伴系統之上， 核心又給自己搞了一個專用的記憶體分配器， 叫slab或slub 。 這兩個詞老混用，為了省事，接下來我們就統一叫 slab 吧。

這個分配器最大的特點就是，一個slab內只分配特定大小、甚至是特定的物件。這樣當一個物件釋放記憶體後，另一個同類物件可以直接使用這塊記憶體。透過這種辦法極大地降低了碎片發生的機率。

slab相關的核心物件定義如下：

每個cache都有滿、半滿、空三個連結串列。 每個連結串列節點都對應一個 slab，一個 slab 由 1 個或者多個記憶體頁組成。

在每一個 slab 內都儲存的是同等大小的物件。 一個cache的組成示意圖如下：

當 cache 中記憶體不夠的時候，會呼叫基於夥伴系統的分配器（\_\_alloc_pages函式）請求整頁連續記憶體的分配。

核心中會有很多個 kmem_cache 存在。它們是在linux初始化，或者是執行的過程中分配出來的。它們有的是專用的，有的是通用的。

上圖中，我們看到 socket_alloc 核心物件都存在 TCP的專用 kmem_cache 中。

透過檢視 /proc/slabinfo 我們可以檢視到所有的 kmem cache。

另外 linux 還提供了一個特別方便的命令 slabtop 來按照佔用記憶體從大往小進行排列。這個命令用來分析 slab 記憶體開銷非常的方便。

無論是 /proc/slabinfo ，還是 slabtop 命令的輸出。裡面都包含了每個 cache 中 slab的如下兩個關鍵資訊。

objsize：每個物件的大小

objperslab： 一個 slab 裡存放的物件的數量

在 /proc/slabinfo 還多輸出了一個pagesperslab。 展示了一個slab 佔用的頁面的數量，每個頁面4K，這樣也就能算出每個 slab 佔用的記憶體大小。

最後，slab 管理器元件提供了若干介面函式，方便自己使用。舉三個例子：

kmem_cache_create : 方便地建立一個基於 slab 的核心物件管理器。

kmem_cache_alloc : 快速為某個物件申請記憶體

kmem_cache_free : 歸還物件佔用的記憶體給 slab 管理器

在核心的原始碼中，可以大量見到 kmem_cache 開頭函式的使用。

總結

透過上面描述的幾個步驟，核心高效地把記憶體用了起來。

第一步：把所有的記憶體條和 CPU 劃分成 node

第二步：把每一個 node 劃分成 zone

第三步：每個 zone 下都用夥伴系統管理空閒頁面

第四步：核心提供 slab 分配器為自己專用

前三步是基礎模組，為應用程式分配記憶體時的請求調頁元件也能夠用到。但第四步，就算是核心的小灶了。核心根據自己的使用場景，量身打造的一套自用的高效記憶體分配管理機制。

“可以看到 TCP cache下每個 slab 佔用 8 個 Page，也就是 8* 4096 = 32768 位元組。 該物件的單個大小是 1984 位元組 位元組，每個slab內放了 16 個物件。1984*16=31744”

“這個時候再多放一個 TCP 物件又放不下，剩下的 1K 記憶體就只好“浪費”掉了。 但是鑑於 slab 機制整體提供的高效能、以及低碎片的效果，這一點點的額外開銷還是很值得的。”
