# TLB 快取 (Cache) 是個什麼鬼，如何檢視 TLB miss？

> 原文標題：TLB缓存是个神马鬼，如何查看TLB miss？

> 原文連結：https://mp.weixin.qq.com/s/mssTS3NN7-w2df1vhYSuYw

介紹 TLB 之前，我們先來回顧一個作業系統 (Operating System) 裡的基本概念，虛擬記憶體 (Virtual Memory)。

## 虛擬記憶體

在使用者的視角里，每個程序 (Process) 都有自己獨立的位址空間，A 程序的 4GB 和 B 程序 4GB 是完全獨立不相關的，他們看到的都是作業系統虛擬出來的位址空間。但是呢，虛擬位址最終還是要落在實際記憶體 (Memory) 的實體位址上進行操作的。作業系統就會透過頁表 (Page Table) 的機制來實作程序的虛擬位址到實體位址的翻譯工作。其中每一頁的大小都是固定的。這一段我不想介紹的太過於詳細，對這個概念不熟悉的同學回去翻一下作業系統的教材。

頁表管理有兩個關鍵點，分別是頁面大小和頁表級數

- 1. 頁面大小
在 Linux 下，我們透過如下命令可以檢視到當前作業系統的頁大小

```
# getconf PAGE_SIZE
4096
```

可以看到當前我的 Linux 機器的頁表是 4KB 的大小。

- 2. 頁表級數頁表級數越少，虛擬位址到實體位址的對映會很快，但是需要管理的頁表項會很多，能支援的位址空間也有限。相反頁表級數越多，需要的儲存的頁表資料就會越少，而且能支援到比較大的位址空間，但是虛擬位址到實體位址的對映就會越慢。

## 32 位系統的虛擬記憶體實作：二級頁表

為了幫助大家回憶這段知識，我舉個例子。如果想支援 32 位的作業系統下的 4GB 程序虛擬位址空間，假設頁表大小為 4K，則共有 2 的 20 次方頁面。如果採用速度最快的 1 級頁表，對應則需要 2 的 20 次方個頁表項。一個頁表項假如 4 位元組，那麼一個程序就需要（1048576*4=）4M 的記憶體來存頁表項。
如果是採用 2 級頁表，如圖 1，則建立程序時只需要有一個頁目錄就可以了，佔用 (1024*4)=4KB 的記憶體。剩下的二級頁表項只有用到的時候才會再去申請。

## 64 位系統的虛擬記憶體實作：四級頁表

現在的作業系統需要支援的可是 48 位位址空間（理論上可以支援 64 位，但其實作在只支援到了 48 位，也足夠用了），而且要支援成百上千的程序，如果不採用分級頁表的方式，則建立程序時就需要為其維護一個 2 的 36 次方個頁表項（64 位 Linux 目前只使用了位址中的 48 位的，在這裡面，最後 12 位都是頁內位址，只有前 36 位才是用來尋找頁表的）， 2^36 *4Byte=32GB，這個更不能忍了。 也必須和 32 位系統一樣，進一步提高頁表的級數。

Linux 在   v2.6.11 以後，最終採用的方案是 4 級頁表，分別是：

- PGD：page Global directory(47-39), 頁全域性目錄
- PUD：Page Upper Directory(38-30)，頁上級目錄
- PMD：page middle directory(29-21)，頁中間目錄
- PTE：page table entry(20-12)，頁表項

這樣，一個 64 位的虛擬空間，初始建立的時候只需要維護一個 2^9 大小的一個頁全域性目錄就夠了，現在的頁表資料結構被擴充套件到了 8byte。這個頁全域性目錄僅僅需要 (2^9 *8=) 4K，剩下的中間頁目錄、頁表項只需要在使用的時候再分配就好了。Linux 就是透過這種方式支援起 (2^48 =) 256T 的程序位址空間的。

## 頁表帶來的問題

上面終於費勁扒了半天 Linux 虛擬記憶體的實作，我終於可以開始說我想說的重點了。
雖然建立一個支援 256T 的位址空間的程序在初始的時候只需要 4K 的頁全域性目錄，但是，這也帶來了額外的問題，頁表是存在記憶體裡的。那就是一次記憶體 IO 光是虛擬位址到實體位址的轉換就要去記憶體查 4 次頁表，再算上真正的記憶體存取，最壞情況下需要 5 次記憶體 IO 才能取得一個記憶體資料!!

## TLB 應運而生

和 CPU 的 L1、L2、L3 的快取思想一致，既然進行位址轉換需要的記憶體 IO 次數多，且耗時。那麼幹脆就在 CPU 裡把頁表儘可能地 cache 起來不就行了麼，所以就有了 TLB(Translation Lookaside Buffer)，專門用於改進虛擬位址到實體位址轉換速度的快取。其存取速度非常快，和暫存器相當，比 L1 存取還快。


有了 TLB 之後，CPU 存取某個虛擬記憶體位址的過程如下

- 1. CPU 產生一個虛擬位址
- 2. MMU 從 TLB 中取得頁表，翻譯成實體位址
- 3. MMU 把實體位址傳送給 `L1/L2/L3`/記憶體
- 4. `L1/L2/L3`/記憶體將位址對應資料回傳給 CPU

由於第 2 步是類似於暫存器的存取速度，所以如果 TLB 能命中，則虛擬位址到實體位址的時間開銷幾乎可以忽略。如果想了解 TLB 更詳細的工作機制，請參考《深入理解電腦系統-第 9 章虛擬記憶體》

## 工具

既然 TLB 快取命中很重要，那麼有什麼工具能夠檢視你的系統裡的命中率呢？ 還真有

```
# perf stat -e dTLB-loads,dTLB-load-misses,iTLB-loads,iTLB-load-misses -p $PID
 Performance counter stats for process id '21047':

           627,809 dTLB-loads
             8,566 dTLB-load-misses          #    1.36% of all dTLB cache hits
         2,001,294 iTLB-loads
             3,826 iTLB-load-misses          #    0.19% of all iTLB cache hits
```

## 擴充套件

因為 TLB 並不是很大，只有 4k，而且現在邏輯核 (Logical Core) 又造成會有兩個程序來共享。所以可能會有 cache miss 的情況出現。而且一旦 TLB miss 造成的後果可比實體位址 cache miss 後果要嚴重一些，最多可能需要進行 5 次記憶體 IO 才行。建議你先用上面的 `perf` 工具檢視一下你的程式的 TLB 的 miss 情況，如果確實不命中率很高，那麼 Linux 允許你使用大記憶體頁，很多大牛包括 PHP7 作者鳥哥也這樣建議。這樣將會大大減少頁表項的數量，所以自然也會降低 TLB cache miss 率。所要承擔的代價就是會造成一定程度的記憶體浪費。在 Linux 裡，大記憶體頁預設是不開啟的。
