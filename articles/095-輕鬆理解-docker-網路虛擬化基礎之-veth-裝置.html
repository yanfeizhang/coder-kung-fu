不得不說，網路虛擬化技術是我給自己刨的又一個大坑。雖然我自認為把原生 Linux 網路實現過程理解的還算不錯了。但在看網路虛擬化相關的技術的時候，還是覺得不是很容易。

回想下在物理機組成的網路裡，最基礎，最簡單的網路連線方式是什麼？沒錯，那就是直接用一根交叉網線把兩臺電腦的網絡卡連起來。這樣，一臺機器傳送資料，另外一臺就能收到了。

那麼，網路虛擬化實現的第一步，就是用軟體來模擬這個簡單的網路連線實現過程。實現的技術就是我們今天的主角 veth，它模擬了在物理世界裡的兩塊網絡卡，以及一條網線。透過它可以將兩個虛擬的裝置連線起來，讓他們之間相互通訊。平時工作中在 Docker 映象裡我們看到的 eth0 裝置，其實就是 veth。

事實上，這種軟體模擬硬體方式我們一點兒也不陌生，我們本機網路 IO 裡的 lo 迴環裝置也是這樣一個用軟體虛擬出來裝置。 Veth 和 lo 的一點區別就是 veth 總是成雙成對地出現。

我們今天就來深入地看看 veth 這個東東是咋工作的。

二、veth 底層建立過程

在上一小節中，我們親手建立了一對兒 veth 裝置，並透過簡單的配置就可以讓他們之間互相進行通訊了。那麼在本小節中，我們看看在核心裡，veth 到底是如何建立的。

Veth 相關原始碼位於 drivers/net/veth.c，其中初始化入口是 veth_init。

在 veth_init 中註冊了 veth_link_ops（veth 裝置的操作方法），它包含了 veth 裝置的建立、啟動和刪除等回撥函式。

我們先來看下 veth 裝置的建立函式 veth_newlink， 這是理解 veth 的關鍵之處 。

在 veth_newlink 中，我們看到它透過 register_netdevice 建立了 peer 和 dev 兩個網路虛擬裝置。接下來的 netdev_priv 函式返回的是網路裝置的 private 資料，priv->peer 就是一個指標而已。

兩個新建立出來的裝置 dev 和 peer 透過 priv->peer 指標來完成結對。其中 dev 裝置裡的 priv->peer 指標指向 peer 裝置， peer 裝置裡的 priv->peer 指向 dev。

接著我們再看下 veth 裝置的啟動過程。

其中 dev->netdev_ops = &veth_netdev_ops 這行也比較關鍵。veth_netdev_ops 是 veth 裝置的操作函式。例如傳送過程中呼叫的函式指標 ndo_start_xmit，對於 veth 裝置來說就會呼叫到 veth_xmit。這個在下一個小節裡我們會用到。

三、veth 網路通訊過程

在 《25 張圖，一萬字，拆解 Linux 網路包傳送過程》 和 《圖解Linux網路包接收過程》 兩篇文章中，我們系統介紹了 Linux 網路包的收發過程。 在 《127.0.0.1 之本機網路通訊過程知多少 ?》 中我們又詳細討論了基於迴環裝置 lo 的本機網路 IO 過程。

我們回顧一下基於迴環裝置 lo 的本機網路過程。在傳送階段裡，流程分別是 send 系統呼叫 => 協議棧 => 鄰居子系統 => 網路裝置層 => 驅動。在接收階段裡，流程分別是軟中斷 => 驅動 => 網路裝置層 => 協議棧 => 系統呼叫返回。過程圖示如下：

基於 veth 的網路 IO 過程和上面這個過程圖幾乎完全一樣。和 lo 裝置所不同的就是使用的驅動程式不一樣，馬上我們就能看到。

網路裝置層最後會透過 ops->ndo_start_xmit 來呼叫驅動進行真正的傳送。

在 《127.0.0.1 之本機網路通訊過程知多少 ?》 一文中，我們提到過對於迴環裝置 lo 來說 netdev_ops 是 loopback_ops。那麼上面傳送過程中呼叫的 ops->ndo_start_xmit 對應的就是 loopback_xmit。

回顧本文上一小節中，對於 veth 裝置來說，它在啟動的時候將 netdev_ops 設定成了 veth_netdev_ops。那 ops->ndo_start_xmit 對應的具體傳送函式就是 veth_xmit。這就是在整個傳送的過程中，唯一和 lo 裝置不同的地方所在。我們來簡單看一下這個傳送函式的程式碼。

在 veth_xmit 中主要就是獲取一下當前 veth 裝置，然後向對端把資料傳送過去就行了。傳送到對端裝置的工作是由 dev_forward_skb 函式來處理的。

先呼叫了 eth_type_trans 將 skb 的所屬裝置改為了剛剛取到的 veth 的對端裝置 rcv。

接著呼叫 netif_rx，這塊又和 lo 裝置的操作一樣了。在該方法中最終會執行到 enqueue_to_backlog 中（netif_rx -> netif_rx_internal -> enqueue_to_backlog）。在這裡將要傳送的 skb 插入 softnet_data->input_pkt_queue 佇列中並呼叫 ____napi_schedule 來觸發軟中斷，見下面的程式碼。

當資料傳送完喚起軟中斷後，veth 對端的裝置開始接收。 和傳送過程不同的是，所有的虛擬裝置的收包 poll 函式都是一樣的，都是在裝置層被初始化成了 process_backlog。

所以 veth 裝置的接收過程和 lo 裝置完全一樣。想再看看這塊過程的同學就請參考 《127.0.0.1 之本機網路通訊過程知多少 ?》 一文中的第三節吧。大致流程是 net_rx_action 執行到 deliver_skb，然後送到協議棧中。

總結

由於大部分的同學在日常工作中一般不會接觸到 veth，所以在看到 Docker 相關的技術文中提到這個技術時總會以為它是多麼的高深。

其實從實現上來看，虛擬裝置 veth 和我們日常接觸的 lo 裝置非常非常的像。連基於 veth 的本機網路 IO 通訊圖其實都是我直接從 127.0.0.1 的那篇文章裡複製過來的。只要你看過飛哥的 127.0.0.1 之本機網路通訊過程知多少 ?！ 這篇，理解起來 veth 簡直不要太容易。

只不過和 lo 裝置相比，veth 是為了虛擬化技術而生的，所以它多了個結對的概念。在建立函式 veth_newlink 中，一次性就建立了兩個網路裝置出來，並把對方分別設定成了各自的 peer。在傳送資料的過程中，找到傳送裝置的 peer，然後發起軟中斷讓對方收取就算完事了。
