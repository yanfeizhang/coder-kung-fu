# 聊聊跨程序共享記憶體的內部工作原理

> 原文標題：聊聊跨进程共享内存的内部工作原理

> 原文連結：http://kfngxl.cn/index.php/archives/547/

---

大家好，我是飛哥！

在 Linux 系統的程序虛擬記憶體中，一個重要的特性就是不同程序的地址空間是隔離的。A 程序的地址 0x4000 和 B 程序的 0x4000 之間沒有任何關係。這樣確確實實是讓各個程序的執行時互相之間的影響降到了最低。某個程序有 bug 也只能自己崩潰，不會影響其它程序的執行。

但是有的時候我們是想要跨程序傳遞一些資料的。因為程序虛擬記憶體地址是隔離的。所以目前業界最常用的做法是讓程序之間透過 127.0.0.1 或者是 Unix Domain Socket 等本機網路手段進行資料的傳輸。這個方案在傳輸的資料量較小的時候工作是很不錯的。

但如果程序間想共享的資料特別大，比如說幾個 GB，那如果使用網路 IO 方案的話，就會涉及到大量的記憶體複製的開銷，導致比較低的程式效能。這是可以採用程序間共享記憶體的方法來在通訊時避免記憶體複製。

那麼問題來了，不同程序之間的虛擬地址是隔離的，共享記憶體又是如何突破這個限制的呢？我們今天就來深入地瞭解下共享記憶體的內部工作原理。

一、共享記憶體的使用方式

共享記憶體傳送方程序的開發基本過程是呼叫 memfd_create 建立一個記憶體檔案。然後透過 mmap 系統呼叫為這個記憶體檔案申請一塊 共享記憶體 。然後這個記憶體檔案就可以寫入資料了。最後把這個檔案的控制代碼透過 Unix Domain Socket 的方式給接收方程序傳送過去。

共享記憶體接收方的工作過程是先用 Unix Domain Socket 連線上伺服器，然後使用 recvmsg 就可以收到傳送方傳送過來的檔案控制代碼。

這樣這兩個程序都各自有一個檔案控制代碼，在底層上是指向同一個記憶體檔案的。這樣就實現了傳送方和接收方之間的記憶體檔案共享了。

但我們上面介紹的是開發基本過程。按照我們開發內功修煉公眾號的風格，這還不算完，我們是要把它最底層的原理真正的弄通透才算的。所以接下來我們再深入地分析 memfd_create、 mmap、以及 Unix Domain socket sendmsg 和 recvmsg 的底層工作原理，來看看它們是如何配合來實現跨程序共享記憶體的。

程序的虛擬記憶體地址空間在核心底層中就是由這樣一個個的 vma 來組成的。每一個 vma 都宣告的是程序虛擬地址中的某一段地址範圍已經分配出去了。在 mmap_region 函式中申請了 vma，並在核心中將其管理了起來。

這裡注意我們在申請共享記憶體的時候，給 vma 是帶了 VM_SHARED 標記的。帶了這個標記的 vma和普通的虛擬記憶體不一樣。 後面在發生缺頁中斷申請實體記憶體的時候，在不同的程序間是可以對應到同一塊實體記憶體的。所以可以實現程序間的共享。

所以真正讓程序之間可以共享記憶體的是這個帶 VM_SHARED 的 vma。

五、總結

共享記憶體傳送方程序的開發過程基本分 memfd_create 建立記憶體檔案、mmap 申請共享記憶體、Unix Domain Socket 傳送檔案控制代碼三步。

第一步，memfd_create 系統呼叫的主要邏輯有兩個，一是呼叫 get_unused_fd_flags 申請一個沒使用過的檔案控制代碼，二是呼叫 shmem_file_setup 建立一個共享記憶體檔案。

第二步，mmap 系統呼叫在呼叫它的時候傳入的第三個 flag 引數是 MAP_SHARED，該引數是申請一塊跨程序可共享訪問的實體記憶體。

第三步，接著透過 Unix Domain Socket 中對應的 sendmsg 方法將這個共享記憶體檔案的控制代碼傳送出去。在傳送時，把檔案控制代碼對應的 struct file 指標找到並放到要封裝的 skb 資料包中了。

接收方程序的主要實現原理是 recvmsg 系統呼叫。在這個系統呼叫中，核心會把傳送方傳送過來的 struct file 指標取出來，然後再在當前程序下為其申請一個新的檔案控制代碼。這個檔案控制代碼返回給使用者程序後，使用者程序就可以用它來和另外一個程序共享地訪問同一塊記憶體了。

總體來看，共享記憶體本質上共享的是核心物件 struct file，透過在不同的程序之間使用同一個 struct file 來實現的共享。當然也得需要在虛擬記憶體物件 vma 帶上 VM_SHARED 標記來支援。
