現代的開發語言除了C++以外，大部分都對記憶體管理做好了封裝，一般的開發者根本都接觸不到記憶體的底層操作。更何況現在各種優秀的開源元件應用越來越多，例如mysql、redis等，這些甚至都不需要大家動手開發，直接拿來用就好了。所以有些同學也會覺得作為應用層開發的同學沒有學習的必要去學習底層。 但我想透過本文的實際案例告訴大家，哪怕不直接接觸記憶體底層操作，就只是用一些開源的工具，如果你能理解底層的工作原理，你也能夠用到極致。

使用者訪問歷史讀寫需求

假如現在有這樣一個業務需求，使用者每次重新整理都需要獲得要消費的新資料，但是不能和之前訪問過的歷史重複。你可以把它和你經常在用的今日頭條之類的資訊流app聯絡起來。每次都要看到新的新聞，但是你肯定不想看到過去已經看過的文章。 這樣在功能實現的時候，就必要儲存使用者的訪問歷史。當使用者再來重新整理的時候，首先得獲取使用者的歷史記錄，要保證推給使用者的資料和之前的不重複。當推薦完成的時候，也需要把這次新推薦過的資料id記錄到歷史裡。 為了適當降低實現複雜度，我們可以規定每個使用者只要不和過去的一萬條記錄重複就可以了。這樣每個使用者最多只需要儲存一萬條歷史id，如果存滿了就把最早的歷史記錄擠掉。我們進一步具體化一下這個需求的幾個關鍵點：

每個資料id是一個int整數來表示

每個使用者要儲存1萬條id

每次使用者重新整理開始的時候需要將這1萬條歷史全部讀取出來過濾一遍

每次使用者重新整理結束的時候需要將新訪問過的10條寫入一遍，如果超過1萬需將最早的記錄擠掉

可見，每次使用者訪問的時候，會涉及到一個1萬規模的資料集上的一次讀取和一次寫入操作。

好了，需求描述完了，我們怎麼樣進行我們的技術方案的設計呢？相信你也能想到很多實現方案，我們今天來對比兩個基於Redis下的儲存方案在效能方面的優劣。

方案一：用Redis的list來儲存

首先能想到的第一個辦法就是用Redis的List來儲存。因為這個資料結構設計的太適合上面的場景了。 List下的lrange命令可以實現一次性讀取使用者的所有資料id的需求。

lpush命令可以實現新的資料id的寫入，ltrim可以保證將使用者的記錄數量不超過1萬條。

我們準備一個使用者，提前存好一萬條id。寫入的時候每次只寫入10條新的id，讀取的時候透過lrange一次全部讀取出來。進行一下效能耗時測試，結果如下。

我能想到的另外一個技術方案就是直接用String來存。我們可以把1萬個int表示的資料id拼接成一個字串，用一個特殊的字元把他們分割開。例如："100000_100001_10002"這種。 儲存的時候，拼接一下，然後把這個大字串寫到Redis裡。讀取的時候，把大字串整體讀取出來，然後再用字元切割成陣列來使用。

結論

我們再直觀對比下兩個技術方案的效能資料。

| | 寫入耗時 | 讀取耗時 | 總耗時 | ---- | ---- | ---- | ---- | | list | 0.066ms | 4.238ms | 4.304ms| | string | 0.640ms | 0.496ms | 1.136ms|

基於list的方案裡，寫入速度非常快，只需要0.066ms，因為僅僅只需要寫入新新增的10條記錄就可以了，再加一次連結串列的截斷操作，但是讀取效能可就要慢很多了，超過了4ms。原因之一是因為讀取需要整體遍歷，但其實還有第二個原因。我們本案例中的資料量過大，所以Redis在內部實際上是用雙端連結串列來實現的。.

透過上圖你可能看出來，連結串列是透過指標串起來的。大量的node之間極大可能是隨機地分佈在記憶體的各個位置上，這樣你遍歷整個連結串列的時候，實際上大機率會導致記憶體的隨機模式下工作。

基於string方案在寫入的時候耗時比list要高，因為每次都得需要將1萬條全部寫入一遍。但是讀取效能卻比list高了10倍，總體上耗時加起來大約只有方案一的1/4左右。為什麼？我們再來看下redis string資料結構的記憶體佈局

可見，如果用string來儲存的話，不管使用者的資料id有多少，訪問將全部都是順序IO。順序IO的好處有兩點：

1.一記憶體的順序IO的耗時大約只是隨機IO的1/3-1/4左右，

2.對於讀取來說，順序訪問將極大地提升CPU的L1、L2、L3的cache命中率

所以如果你深入了記憶體的工作原理，哪怕你不能直接去操作記憶體，即使只是用一些開源的軟體，你也能夠將它的效能發揮到極致~
