# 盤點核心中常見的CPU效能卡點

> 原文標題：盘点内核中常见的CPU性能卡点

> 原文連結：http://kfngxl.cn/index.php/archives/671/

---

大家好，我是飛哥！ 我們的應用程式都是執行在各種語言的執行時、作業系統核心、以及 CPU 等硬體之上的。但這些語言的下面是由執行時、核心、硬體等多層支撐起來的。

我們的程式在執行的時候，很多時候效能卡點可能並不一定是自己的應用程式碼導致的。也有可能是下層的軟體的執行狀況不佳​造成的。

效能卡點有可能出現在硬體上。在 人人都應該知道的CPU快取執行效率 一文中我們瞭解了CPU硬體影響程式執行效能的關鍵指標，分別是平均每條指令的時鐘週期個數 CPI 和快取命中率。

效能卡點也有可能出現在核心軟體上。今天我們就來看下在核心中存在的可能會影響我們程式效能的幾個關鍵指標。

其實，核心開發者們也都知道核心執行的過程中，哪些開銷會比較高。所以老早就給我們提供了一種名為軟體效能事件的支援。以方便我們應用的開發者來觀測這些事件發生的次數，以及發生時所觸發的函式呼叫鏈。

一、軟體效能事件列表

透過 perf 的 list 子命令可以檢視到當前系統都支援哪些軟體效能事件。

其中上面命令中的 sw 是 software 的簡稱，其實指的就是核心。下面的列表列明瞭一些影響效能的事件，我們挨個來解釋。

alignment-faults

這個指的是對齊異常。簡單來說，當CPU訪問記憶體地址時，如果發現訪問的地址是不對齊的，那核心向記憶體請求資料的時候可能一次 IO 不夠，還得再觸發一次 IO 才能把資料給讀取回來。對齊異常會增加本來不需要的記憶體 IO，必然會拖累程式執行效能。

如果你還沒理解的話，可以看下圖。在下圖中 0-63 和 64-127 地址的資料都可以由一次記憶體 IO 完成。但如果你的應用程式非得從 40 位置開始要個長為 64 的資料。那就是不對齊的。

context-switches

程序上下文切換。在 程序/執行緒切換究竟需要多少開銷？ 一文中我們專門介紹過程序上下文切換的開銷。平均每次切換都得 3-5 us。這對於執行的飛快的作業系統來說，已經是一個非常長的時間了，而更為關鍵的是，對於使用者程式來說，這段時間完完全全就是浪費的。頻繁的上下文切換還會進一步導致 CPU 快取命中率變差，拉高 CPI。

cpu-migrations

程序如果每次排程的時候都能夠在同一個CPU核上執行，那大機率這個核的L1、L2、L3等快取裡儲存的資料還能用的上，快取命中率高可以避免對資料的訪問穿透到過慢的記憶體中。所以核心在排程器的實現上開發了wake_affine機制來使得排程儘可能地使用上一次用過的核。

但如果程序在排程器喚醒的時候發現上一次使用過的核被別的程序佔了，那該怎麼辦。總不至於不讓這個程序喚醒，硬等上一次用過的這個CPU核吧。給它分配一個別的核讓程序可以及時獲得CPU也許更好。但這時就會導致程序執行時在CPU之間跳來跳去，這種現象就叫做任務遷移。

顯然任務遷移是對CPU快取不太友好的。如果遷移次數過多必然會導致程序執行效能的下降。

emulation-faults

emulation-faults 錯誤是在 QEMU 虛擬機器中執行 x86 應用程式時出現的一種錯誤型別。x86 程式需要在 x86 架構的計算機上執行，並且依賴於該計算機的硬體架構和指令集。QEMU 作為一款模擬器，可以模擬 x86 硬體架構和指令集，但是由於模擬器與真實硬體之間存在差異，因此在執行 x86 應用程式時可能會產生 emulation-faults 錯誤。

page-faults

這是我們常說的缺頁中斷。使用者程序中在申請記憶體的時候，其實申請到的只是一個vm_area_struct而已，僅僅只是一段地址範圍。實體記憶體並不會立即就分配，具體的分配等到實際訪問的時候。當程序在執行的過程中在棧上開始分配和訪問變數的時候，如果物理頁還沒有分配，會觸發缺頁中斷。在缺頁中斷種來真正地分配實體記憶體。 關於缺頁中斷可以參考 程序棧記憶體底層原理 這篇文章。

其中缺頁中斷又分為兩種，分別是 major-faults 和 minor-faults。這兩種錯誤的區別在於 major-faults 會導致磁碟 IO 的發生，所以對程式執行的影響更大。

二、軟體效能事件的計數統計

瞭解了核心中可能會影響程式執行效能的幾種事件後，我們的一種需求就是看看系統中實際發生了多少次這樣的事件。這個使用 perf stat 子命令就可以辦到。

由於上述命令我是在我手頭的一臺開發機上操作的，所以很多指標都為 0 ，只發生了 56 次不太嚴重的 minor-faults。這個命令是統計的整個系統的情況。

如果只想檢視指定的程式或程序，那就在後面跟上程式名，或者透過 -p 指定程序 pid

也可以使用 perf report 命令進行一個簡單的統計

最好的辦法是用 Brendan Gregg 大神的FlameGraph專案，把取樣獲得的 perf.data 渲染成非常直觀的火焰圖。

生成方式非常的簡單，只需要把 FlameGraph 專案下載下來，再分別使用 stackcollapse-perf.pl 和 flamegraph.pl 兩個指令碼進行處理即可。

其中 stackcollapse-perf.pl 指令碼作用是將呼叫棧處理為一行。行前面表示的是呼叫棧，後面輸出的是取樣到該函式在執行的次數。比如下面這個處理結果表示取樣時發現 main;funcA;funcD;funcE;caculate 這個函式呼叫鏈路正在執行的次數為 554118432 次，main;funcB;caculate 這個函式呼叫鏈路正在執行的次數是 338716787。

flamegraph.pl 指令碼工作原理是將 stackcollapse-perf.pl 繪製成 svg 圖片。完整的火焰圖工作原理這裡不過多展開，大家可以看我之前發的一篇文章 剖析CPU效能火焰圖生成的內部原理

使用火焰圖對 context-switches 核心軟體事件取樣結果 perf.data 進行渲染後，這樣能清楚地看到哪個鏈路上的上下文切換髮生的最為頻發。

透過對火焰圖的觀測，就可以分析發現是哪些原因導致了最多的程序上下文切換的開銷了。
