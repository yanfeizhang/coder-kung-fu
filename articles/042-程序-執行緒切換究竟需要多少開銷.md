# 程序/執行緒切換究竟需要多少開銷？

> 原文標題：进程/线程切换究竟需要多少开销？

> 原文連結：http://kfngxl.cn/index.php/archives/604/

---

程序是作業系統的偉大發明之一，對應用程式遮蔽了CPU排程、記憶體管理等硬體細節，而抽象出一個程序的概念，讓應用程式專心於實現自己的業務邏輯既可，而且在有限的CPU上可以“同時”進行許多個任務。但是它為使用者帶來方便的同時，也引入了一些額外的開銷。如下圖，在程序執行中間的時間裡，雖然CPU也在忙於幹活，但是卻沒有完成任何的使用者工作，這就是程序機制帶來的額外開銷。

在程序A切換到程序B的過程中，先儲存A程序的上下文，以便於等A恢復執行的時候，能夠知道A程序的下一條指令是啥。然後將要執行的B程序的上下文恢復到暫存器中。這個過程被稱為上下文切換。上下文切換開銷在程序不多、切換不頻繁的應用場景下問題不大。但是現在Linux作業系統被用到了高併發的網路程式後端伺服器。在單機支援成千上萬個使用者請求的時候，這個開銷就得拿出來說道說道了。因為使用者程序在請求Redis、Mysql資料等網路IO阻塞掉的時候，或者在程序時間片到了，都會引發上下文切換。

## 一個簡單的程序上下文切換開銷測試實驗

廢話不多說，我們先用個實驗測試一下，到底一次上下文切換需要多長的CPU時間！實驗方法是建立兩個程序並在它們之間傳送一個令牌。其中一個程序在讀取令牌時就會引起阻塞。另一個程序傳送令牌後等待其返回時也處於阻塞狀態。如此往返傳送一定的次數，然後統計他們的平均單次切換時間開銷。
具體的實驗程式碼參見[test04](tests/test04/main.c)

```
# gcc main.c -o main
# ./main./main
Before Context Switch Time1565352257 s, 774767 us
After Context SWitch Time1565352257 s, 842852 us
```

每次執行的時間會有差異，多次執行後平均每次上下文切換耗時3.5us左右。當然了這個數字因機器而異，而且建議在實機上測試。

前面我們測試系統呼叫的時候，最低值是200ns。可見，上下文切換開銷要比系統呼叫的開銷要大。系統呼叫只是在程序內將使用者態切換到核心態，然後再切回來，而上下文切換可是直接從程序A切換到了程序B。顯然這個上下文切換需要完成的工作量更大。

## 程序上下文切換開銷都有哪些

那麼上下文切換的時候，CPU的開銷都具體有哪些呢？開銷分成兩種，一種是直接開銷、一種是間接開銷。

直接開銷就是在切換時，cpu必須做的事情，包括：

- 1、切換頁表全域性目錄

- 2、切換核心態堆疊

- 3、切換硬體上下文（程序恢復前，必須裝入暫存器的資料統稱為硬體上下文）ip(instruction pointer)：指向當前執行指令的下一條指令bp(base pointer): 用於存放執行中的函式對應的棧幀的棧底地址sp(stack poinger): 用於存放執行中的函式對應的棧幀的棧頂地址cr3:頁目錄基址暫存器，儲存頁目錄表的實體地址......

- 4、重新整理TLB

- 5、系統排程器的程式碼執行

間接開銷主要指的是雖然切換到一個新程序後，由於各種快取並不熱，速度執行會慢一些。如果程序始終都在一個CPU上排程還好一些，如果跨CPU的話，之前熱起來的TLB、L1、L2、L3因為執行的程序已經變了，所以以區域性性原理cache起來的程式碼、資料也都沒有用了，導致新程序穿透到記憶體的IO會變多。 其實我們上面的實驗並沒有很好地測量到這種情況，所以實際的上下文切換開銷可能比3.5us要大。

想了解更詳細操作過程的同學請參考《深入理解Linux核心》中的第三章和第九章。

## 一個更為專業的測試工具-lmbench

lmbench用於評價系統綜合效能的多平臺開源benchmark，能夠測試包括文件讀寫、記憶體操作、程序建立銷燬開銷、網路等效能。使用方法簡單，但就是跑有點慢，感興趣的同學可以自己試一試。
這個工具的優勢是是進行了多組實驗，每組2個程序、8個、16個。每個程序使用的資料大小也在變，充分模擬cache miss造成的影響。我用他測了一下結果如下：

```

                         ctxsw  ctxsw  ctxsw ctxsw  ctxsw   ctxsw   ctxsw

bjzw_46_7 Linux 2.6.32- 2.7800 2.7800 2.7000 4.3800 4.0400 4.75000 5.48000
```

lmbench顯示的程序上下文切換耗時從2.7us到5.48之間。

## 執行緒上下文切換耗時

前面我們測試了程序上下文切換的開銷，我們再繼續在Linux測試一下執行緒。看看究竟比程序能不能快一些，快的話能快多少。

在Linux下其實本並沒有執行緒，只是為了迎合開發者口味，搞了個輕量級程序出來就叫做了執行緒。輕量級程序和程序一樣，都有自己獨立的task_struct程序描述符，也都有自己獨立的pid。從作業系統視角看，排程上和程序沒有什麼區別，都是在等待佇列的雙向連結串列裡選擇一個task_struct切到執行態而已。只不過輕量級程序和普通程序的區別是可以共享同一記憶體地址空間、程式碼段、全域性變數、同一開啟檔案集合而已。

> 同一程序下的執行緒之所有getpid()看到的pid是一樣的，其實task_struct裡還有一個tgid欄位。 對於多執行緒程式來說，getpid()系統呼叫獲取的實際上是這個tgid，因此隸屬同一程序的多執行緒看起來PID相同。

我們用一個實驗來測試一下[test06](tests/test06/main.c)。其原理和程序測試差不多，建立了20個執行緒，線上程之間透過管道來傳遞訊號。接到訊號就喚醒，然後再傳遞訊號給下一個執行緒，自己睡眠。 這個實驗裡單獨考慮了給管道傳遞訊號的額外開銷，並在第一步就統計了出來。

```
# gcc -lpthread main.c -o main
0.508250
4.363495
```

每次實驗結果會有一些差異，上面的結果是取了多次的結果之後然後平均的，大約每次執行緒切換開銷大約是3.8us左右。從上下文切換的耗時上來看，Linux執行緒（輕量級程序）其實和程序差別不太大。

那麼進一步，我們看下到底是哪些程序導致了頻繁的上下文切換？

```
# pidstat -w 1

11:07:56 AM     32316      4.00      0.00  php-fpm
11:07:56 AM     32508    160.00     34.00  php-fpm
11:07:56 AM     32726    131.00      8.00  php-fpm
......
```

由於fpm是同步阻塞的模式，每當請求Redis、Memcache、Mysql的時候就會阻塞導致cswch/s自願上下文切換，而只有時間片到了之後才會觸發nvcswch/s非自願切換。可見fpm程序大部分的切換都是自願的、非自願的比較少。

如果想檢視具體某個程序的上下文切換總情況，可以在/proc介面下直接看，不過這個是總值。

```
grep ctxt /proc/32583/status
voluntary_ctxt_switches:        573066
nonvoluntary_ctxt_switches:     89260
```

## 本節結論

上下文切換具體做哪些事情我們沒有必要記，只需要記住一個結論既可，測得作者開發機上下文切換的開銷大約是2.7-5.48us左右，你自己的機器可以用我提供的程式碼或工具進行一番測試。
lmbench相對更準確一些，因為考慮了切換後Cache miss導致的額外開銷。

> 擴充套件：平時大家在作業系統理論學習的時候都知道CPU時間片的概念，時間片到了會將程序從CPU上趕下來，換另一個程序上。但其實在我們網際網路的網路IO密集型的應用裡，真正因為時間片到了而發生的非自願切換很少，絕大部分都是因為等待網路IO而進行的自願切換。 上面的例子你也可以看出，我的一個fpm程序主動切換有57W次，而被動切換隻有不到9W次。所以，在同步阻塞的開發模式裡，網路IO是導致上下文切換頻繁的元兇
