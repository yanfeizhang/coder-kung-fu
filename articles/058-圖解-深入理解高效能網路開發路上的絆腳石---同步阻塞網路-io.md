# 圖解 | 深入理解高效能網路 (Network) 開發路上的絆腳石 - 同步阻塞網路 IO (Synchronous Blocking Network `I/O`)

在網路開發模型中，有一種非常易於開發同學使用方式，那就是同步阻塞的網路 IO（在 Java 中習慣叫 BIO）。

例如我們想請求伺服器上的一段資料，那麼 C 語言的一段程式碼 demo 大概是下面這樣：

```
int main()
{
    int sk = socket(AF_INET, SOCK_STREAM, 0);
    connect(sk, ...)
    recv(sk, ...)
}
```

但是在高併發的伺服器開發中，這種網路 IO 的效能奇差。因為

- 1. 程序 (Process) 在   `recv` 的時候大機率會被阻塞掉，導致一次程序切換
- 2. 當連線上資料就緒的時候程序又會被喚醒，又是一次程序切換
- 3. 一個程序同時只能等待一條連線，如果有很多併發，則需要很多程序

如果用一句話來概括，那就是：同步阻塞網路 IO 是高效能網路開發路上的絆腳石！俗話說得好，知己知彼方能百戰百勝。所以我們今天先不講最佳化，只深入分析同步阻塞網路 IO 的內部實作。

在上面的 demo 中雖然只是簡單的兩三行程式碼，但實際上使用者程序和核心配合做了非常多的工作。先是使用者程序發起建立 `socket` 的指令，然後切換到核心態 (Kernel Mode) 完成了核心物件的初始化。接下來 Linux 在資料封包的接收上，是硬中斷 (Hardware Interrupt) 和 ksoftirqd 程序在進行處理。當 ksoftirqd 程序處理完以後，再通知到相關的使用者程序。

從使用者程序建立   `socket`，到一個網路封包 (Network Packet) 抵達網路卡 (Network Card) 到被使用者程序接收到，總體上的流程圖如下：

我們今天用圖解加原始碼分析的方式來詳細拆解一下上面的每一個步驟，來看一下在核心裡是它們是怎麼實作的。閱讀完本文，你將深刻地理解在同步阻塞的網路 IO 效能低下的原因！

## 一、建立一個 `socket`

開篇原始碼中的   `socket` 函式呼叫執行完以後，核心在內部建立了一系列的 `socket` 相關的核心物件（是的，不是隻有一個）。它們互相之間的關係如圖。當然了，這個物件比圖示的還要更復雜。我只在圖中把和今天的主題相關的內容展現了出來。

我們來翻翻原始碼，看下上面的結構是如何被創造出來的。

```
//file:net/socket.c
SYSCALL_DEFINE3(socket, int, family, int, type, int, protocol)
{
    ......
    retval = sock_create(family, type, protocol, &sock);
}
```

`sock_create` 是建立 `socket` 的主要位置。其中 `sock_create` 又呼叫了 \_\_sock_create。

```
//file:net/socket.c
int __sock_create(struct net *net, int family, int type, int protocol,
             struct socket **res, int kern)
{
    struct socket *sock;
    const struct net_proto_family *pf;

    ......

    //分配 socket 物件
    sock = sock_alloc();

    //獲得每個協定族的操作表
    pf = rcu_dereference(net_families[family]);

    //呼叫每個協定族的建立函式， 對於 AF_INET 對應的是
    err = pf->create(net, sock, protocol, kern);

```

在 \_\_sock_create 裡，首先呼叫   `sock_alloc` 來分配一個 struct sock 物件。 接著在取得協定族的操作函式表，並呼叫其 create 方法。 對於 `AF_INET` 協定族來說，執行到的是 `inet_create` 方法。

```

    //static struct inet_protosw inetsw_array[] =
    //{
    //    {
    //        .type =       SOCK_STREAM,

在   inet_create 中，根據型別 SOCK_STREAM 查詢到對於 tcp 定義的操作方法實作集合 inet_stream_ops 和 tcp_prot。並把它們分別設定到  socket->ops 和 sock-> sk_prot 上。
```

我們再往下看到了  `sock_init_data`。 在這個方法中將 sock 中的 `sk_data_ready` 函式指標進行了初始化，設定為預設 `sock_def_readable`()。

```
//file: net/core/sock.c
void sock_init_data(struct socket *sock, struct sock *sk)
{
    sk->sk_data_ready   =   sock_def_readable;
    sk->sk_write_space  =   sock_def_write_space;
    sk->sk_error_report =   sock_def_error_report;
}
```

當軟中斷 (Softirq) 上收到資料封包時會透過呼叫   `sk_data_ready` 函式指標（實際被設定成了 `sock_def_readable`()） 來喚醒在 sock 上等待的程序。這個我們後面介紹軟中斷的時候再說，這裡記住這個就行了。

至此，一個 tcp 物件，確切地說是   `AF_INET` 協定族下 `SOCK_STREAM` 物件就算是建立完成了。這裡花費了一次 `socket` 系統呼叫 (System Call) 的開銷。

## 二、等待接收訊息

接著我們來看 `recv` 函式依賴的底層實作。首先透過 `strace` 命令跟蹤，可以看到 clib 庫函式 `recv` 會執行到 recvfrom 系統呼叫。

進入系統呼叫後，使用者程序就進入到了核心態，透過執行一系列的核心協定層函式，然後到   `socket` 物件的接收佇列中檢視是否有資料，沒有的話就把自己新增到 `socket` 對應的等待佇列裡。最後讓出 CPU，作業系統 (Operating System) 會選擇下一個就緒狀態的程序來執行。 整個流程圖如下：

呼叫   `socket` 物件 ops 裡的 recvmsg， 回憶我們上面的 `socket` 物件圖，從圖中可以看到 recvmsg 指向的是 `inet_recvmsg` 方法。

這裡又遇到一個函式指標，這次呼叫的是   `socket` 物件裡的 `sk_prot` 下面的 recvmsg 方法。同上，得出這個 recvmsg 方法對應的是 `tcp_recvmsg` 方法。

```
//file: net/ipv4/tcp.c
int tcp_recvmsg(struct kiocb *iocb, struct sock *sk, struct msghdr *msg,
        size_t len, int nonblock, int flags, int *addr_len)
{
    int copied = 0;
    ...
    do {
        //遍歷接收佇列接收資料

```

終於看到了我們想要看的東西，  `skb_queue_walk` 是在存取 sock 物件下面的接收佇列了。

如果沒有收到資料，或者收到不足夠多，則呼叫 `sk_wait_data` 把當前程序阻塞掉。

```
//file: net/core/sock.c
int sk_wait_data(struct sock *sk, long *timeo)
{
    //當前程序(current)關聯到所定義的等待佇列項上
    DEFINE_WAIT(wait);

    // 呼叫 sk_sleep 取得 sock 物件下的 wait
    // 並準備掛起，將程序狀態設定為可打斷 INTERRUPTIBLE
    prepare_to_wait(sk_sleep(sk), &wait, TASK_INTERRUPTIBLE);
    set_bit(SOCK_ASYNC_WAITDATA, &sk->sk_socket->flags);

    // 透過呼叫schedule_timeout讓出CPU，然後進行睡眠
    rc = sk_wait_event(sk, timeo, !skb_queue_empty(&sk->sk_receive_queue));
    ...
```

我們再來詳細看下   `sk_wait_data` 是怎麼把當前程序給阻塞掉的。

首先在 `DEFINE_WAIT` 宏下，定義了一個等待佇列項 wait。 在這個新的等待佇列項上，註冊了回呼函式 `autoremove_wake_function`，並把當前程序描述符 current 關聯到其 .private 成員上。

```
//file: include/linux/wait.h
#define DEFINE_WAIT(name) DEFINE_WAIT_FUNC(name, autoremove_wake_function)

#define DEFINE_WAIT_FUNC(name, function)                \
    wait_queue_t name = {                        \
        .private    = current,                \
        .func        = function,                \
        .task_list    = LIST_HEAD_INIT((name).task_list),    \
    }
```

緊接著在   `sk_wait_data` 中呼叫 `sk_sleep` 取得 sock 物件下的等待佇列列表頭 `wait_queue_head_t`。 `sk_sleep` 原始碼如下：

```
//file: include/net/sock.h
static inline wait_queue_head_t *sk_sleep(struct sock *sk)
{
    BUILD_BUG_ON(offsetof(struct socket_wq, wait) != 0);
    return &rcu_dereference_raw(sk->sk_wq)->wait;
}
```

接著呼叫 `prepare_to_wait` 來把新定義的等待佇列項 wait 插入到 sock 物件的等待佇列下。

```
//file: kernel/wait.c
void
prepare_to_wait(wait_queue_head_t *q, wait_queue_t *wait, int state)
{
    unsigned long flags;

    wait->flags &= ~WQ_FLAG_EXCLUSIVE;
    spin_lock_irqsave(&q->lock, flags);
    if (list_empty(&wait->task_list))
        __add_wait_queue(q, wait);
    set_current_state(state);
    spin_unlock_irqrestore(&q->lock, flags);
}
```

這樣後面當核心收完資料產生就緒時間的時候，就可以查詢   `socket` 等待佇列上的等待項，進而就可以找到回呼函式和在等待該 `socket` 就緒事件的程序了。

最後再呼叫   `sk_wait_event` 讓出 CPU，程序將進入睡眠狀態，這會導致一次程序上下文的開銷。

接下來的小節裡我們將能看到程序是如何被喚醒的了。

## 三、軟中斷模組

接著我們再轉換一下視角，來看負責接收和處理資料封包的軟中斷這邊。關於網路封包到網路卡後是怎麼被網路卡接收，最後在交由軟中斷處理的，這裡就不多贅述了。感興趣的請看之前的文章 [《圖解 Linux 網路封包接收過程》](https://mp.weixin.qq.com/s/GoYDsfy9m0wRoXi_NCfCmg)。我們今天直接從 tcp 協定的接收函式 `tcp_v4_rcv` 看起。

軟中斷裡收到資料封包以後，發現是 tcp 的包的話就會執行到   `tcp_v4_rcv` 函式。接著走，如果是 ESTABLISH 狀態下的資料封包，則最終會把資料拆出來放到對應 `socket` 的接收佇列中。然後呼叫 `sk_data_ready` 來喚醒使用者程序。

我們看更詳細一點的程式碼：

```
// file: net/ipv4/tcp_ipv4.c
int tcp_v4_rcv(struct sk_buff *skb)
{
    ......
    th = tcp_hdr(skb); //取得tcp header
    iph = ip_hdr(skb); //取得ip header

    //根據資料封包 header 中的 ip、埠資訊查詢到對應的socket
    sk = __inet_lookup_skb(&tcp_hashinfo, skb, th->source, th->dest);
    ......

    //socket 未被使用者鎖定
    if (!sock_owned_by_user(sk)) {
        {
            if (!tcp_prequeue(sk, skb))
                ret = tcp_v4_do_rcv(sk, skb);
        }
    }
}
```

在   `tcp_v4_rcv` 中首先根據收到的網路封包的 header 裡的 source 和 dest 資訊來在本機上查詢對應的 `socket`。找到以後，我們直接進入接收的主體函式 `tcp_v4_do_rcv` 來看。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_do_rcv(struct sock *sk, struct sk_buff *skb)
{

            rsk = sk;
            goto reset;
        }
        return 0;
    }

    //其他非 ESTABLISH 狀態的資料封包處理
    ......

```

我們假設處理的是 ESTABLISH 狀態下的包，這樣就又進入 `tcp_rcv_established` 函式中進行處理。

```
//file: net/ipv4/tcp_input.c
int tcp_rcv_established(struct sock *sk, struct sk_buff *skb,
            const struct tcphdr *th, unsigned int len)
{
    ......

    //接收資料到佇列中
    eaten = tcp_queue_rcv(sk, skb, tcp_header_len,
                              &fragstolen);

    //資料 ready，喚醒 socket 上阻塞掉的程序
    sk->sk_data_ready(sk, 0);
```

在   `tcp_rcv_established` 中透過呼叫 `tcp_queue_rcv` 函式中完成了將接收資料放到 `socket` 的接收佇列上。

如下原始碼所示

```
//file: net/ipv4/tcp_input.c
static int __must_check tcp_queue_rcv(struct sock *sk, struct sk_buff *skb, int hdrlen,
          bool *fragstolen)
{
    //把接收到的資料放到 socket 的接收佇列的尾部
    if (!eaten) {
        __skb_queue_tail(&sk->sk_receive_queue, skb);
        skb_set_owner_r(skb, sk);
    }
    return eaten;
}
```

呼叫   `tcp_queue_rcv` 接收完成之後，接著再呼叫 `sk_data_ready` 來喚醒在 `socket` 上等待的使用者程序。 這又是一個函式指標。 回想上面我們在建立 `socket` 流程裡執行到的   `sock_init_data` 函式，在這個函式里已經把 `sk_data_ready` 設定成 `sock_def_readable` 函式了（可以 ctrl + f 搜尋前文）。它是預設的資料就緒處理函式。

```
//file: net/core/sock.c
static void sock_def_readable(struct sock *sk, int len)
{
    struct socket_wq *wq;

    rcu_read_lock();
    wq = rcu_dereference(sk->sk_wq);

    //有程序在此 socket 的等待佇列
    if (wq_has_sleeper(wq))
        //喚醒等待佇列上的程序
        wake_up_interruptible_sync_poll(&wq->wait, POLLIN | POLLPRI |
                        POLLRDNORM | POLLRDBAND);
    sk_wake_async(sk, SOCK_WAKE_WAITD, POLL_IN);
    rcu_read_unlock();
}

在   sock_def_readable 中再一次存取到了 sock->sk_wq 下的 wait。回憶下我們前面呼叫 recvfrom 執行的最後，透過 DEFINE_WAIT(wait) 將當前程序關聯的等待佇列新增到 sock-> sk_wq 下的 wait 裡了。
```

那接下來就是呼叫   `wake_up_interruptible_sync_poll` 來喚醒在 `socket` 上因為等待資料而被阻塞掉的程序了。

```
//file: include/linux/wait.h
#define wake_up_interruptible_sync_poll(x, m)                \
    __wake_up_sync_key((x), TASK_INTERRUPTIBLE, 1, (void *) (m))
```

```
//file: kernel/sched/core.c
void __wake_up_sync_key(wait_queue_head_t *q, unsigned int mode,
            int nr_exclusive, void *key)
{
    unsigned long flags;
    int wake_flags = WF_SYNC;

    if (unlikely(!q))
        return;

    if (unlikely(!nr_exclusive))
        wake_flags = 0;

    spin_lock_irqsave(&q->lock, flags);
    __wake_up_common(q, mode, nr_exclusive, wake_flags, key);
    spin_unlock_irqrestore(&q->lock, flags);
}
```

\_\_wake_up_common 實作喚醒。這裡注意下， 該函式呼叫是參數   `nr_exclusive` 傳入的是 1，這裡指的是即使是有多個程序都阻塞在同一個 `socket` 上，也只喚醒 1 個程序。其作用是為了避免驚群。

```
//file: kernel/sched/core.c
static void __wake_up_common(wait_queue_head_t *q, unsigned int mode,
            int nr_exclusive, int wake_flags, void *key)
{
    wait_queue_t *curr, *next;

    list_for_each_entry_safe(curr, next, &q->task_list, task_list) {
        unsigned flags = curr->flags;

        if (curr->func(curr, mode, wake_flags, key) &&
                (flags & WQ_FLAG_EXCLUSIVE) && !--nr_exclusive)
            break;
    }
}

在 \_\_wake_up_common 中找出一個等待佇列項 curr，然後呼叫其 curr->func。回憶我們前面在   recv 函式執行的時候，使用 DEFINE_WAIT() 定義等待佇列項的細節，核心把 curr->func 設定成了 autoremove_wake_function。
```

```
//file: include/linux/wait.h
#define DEFINE_WAIT(name) DEFINE_WAIT_FUNC(name, autoremove_wake_function)

#define DEFINE_WAIT_FUNC(name, function)                \
    wait_queue_t name = {                        \
        .private    = current,                \
        .func        = function,                \
        .task_list    = LIST_HEAD_INIT((name).task_list),    \
    }
```

在   `autoremove_wake_function` 中，呼叫了 `default_wake_function`。

```
//file: kernel/sched/core.c
int default_wake_function(wait_queue_t *curr, unsigned mode, int wake_flags,
              void *key)
{
    return try_to_wake_up(curr->private, mode, wake_flags);
}

呼叫   try_to_wake_up 時傳入的 task_struct 是 curr->private。這個就是當時因為等待而被阻塞的程序項。 當這個函式執行完的時候，在 socket 上等待而被阻塞的程序就被推入到可執行佇列裡了，這又將是一次程序上下文切換 (Process Context Switch) 的開銷。
```

## 小結

好了，我們把上面的流程總結一下。 核心在通知網路封包的執行環境分兩部分：

- 第一部分是我們自己程式碼所在的程序，我們呼叫的 `socket`() 函式會進入核心態建立必要核心物件。`recv`() 函式在進入核心態以後負責檢視接收佇列，以及在沒有資料可處理的時候把當前程序阻塞掉，讓出 CPU。
- 第二部分是硬中斷、軟中斷上下文（系統程序 ksoftirqd）。在這些元件中，將封包處理完後會放到 `socket` 的接收佇列中。然後再根據 `socket` 核心物件找到其等待佇列中正在因為等待而被阻塞掉的程序，然後把它喚醒。

每次一個程序專門為了等一個 `socket` 上的資料就得被從 CPU 上拿下來。然後再換上另一個程序。等到資料 ready 了，睡眠的程序又會被喚醒。總共兩次程序上下文切換 (Process Context Switch) 開銷，根據之前的測試來看，每一次切換大約是 3-5 us(微秒) 左右。 如果是網路 IO 密集型的應用的話，CPU 就不停地做程序切換這種無用功。

在伺服器端角色上，這種模式完全沒辦法使用。因為這種簡單模型裡的 `socket` 和程序是一對一的。我們現在要在單臺機器上承載成千上萬，甚至十幾、上百萬的使用者連線請求。如果用上面的方式，那就得為每個使用者請求都建立一個程序。 相信你在無論多原始的伺服器網路程式設計裡，都沒見過有人這麼做吧。
