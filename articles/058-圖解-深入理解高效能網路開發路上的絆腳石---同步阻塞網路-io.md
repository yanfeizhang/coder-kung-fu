在網路開發模型中，有一種非常易於開發同學使用方式，那就是同步阻塞的網路 IO（在 Java 中習慣叫 BIO）。

例如我們想請求伺服器上的一段資料，那麼 C 語言的一段程式碼 demo 大概是下面這樣：

但是在高併發的伺服器開發中，這種網路 IO 的效能奇差。因為

1.程序在 recv 的時候大機率會被阻塞掉，導致一次程序切換

2.當連線上資料就緒的時候程序又會被喚醒，又是一次程序切換

3.一個程序同時只能等待一條連線，如果有很多併發，則需要很多程序

如果用一句話來概括，那就是： 同步阻塞網路 IO 是高效能網路開發路上的絆腳石！ 俗話說得好，知己知彼方能百戰百勝。所以我們今天先不講最佳化，只深入分析同步阻塞網路 IO 的內部實現。

在上面的 demo 中雖然只是簡單的兩三行程式碼，但實際上使用者程序和核心配合做了非常多的工作。先是使用者程序發起建立 socket 的指令，然後切換到核心態完成了核心物件的初始化。接下來 Linux 在資料包的接收上，是硬中斷和 ksoftirqd 程序在進行處理。當 ksoftirqd 程序處理完以後，再通知到相關的使用者程序。

一、建立一個 socket

開篇原始碼中的 socket 函式呼叫執行完以後，核心在內部建立了一系列的 socket 相關的核心物件（是的，不是隻有一個）。它們互相之間的關係如圖。當然了，這個物件比圖示的還要更復雜。我只在圖中把和今天的主題相關的內容展現了出來。

我們來翻翻原始碼，看下上面的結構是如何被創造出來的。

sock_create 是建立 socket 的主要位置。其中 sock_create 又呼叫了 \_\_sock_create。

在 \_\_sock_create 裡，首先呼叫 sock_alloc 來分配一個 struct sock 物件。 接著在獲取協議族的操作函式表，並呼叫其 create 方法。 對於 AF_INET 協議族來說，執行到的是 inet_create 方法。

在 inet_create 中，根據型別 SOCK_STREAM 查詢到對於 tcp 定義的操作方法實現集合 inet_stream_ops 和 tcp_prot。並把它們分別設定到 socket->ops 和 sock->sk_prot 上。

我們再往下看到了 sock_init_data。 在這個方法中將 sock 中的 sk_data_ready 函式指標進行了初始化，設定為預設 sock_def_readable()。

當軟中斷上收到資料包時會透過呼叫 sk_data_ready 函式指標（實際被設定成了 sock_def_readable()） 來喚醒在 sock 上等待的程序 。這個咱們後面介紹軟中斷的時候再說，這裡記住這個就行了。

至此，一個 tcp物件，確切地說是 AF_INET 協議族下 SOCK_STREAM物件就算是建立完成了。 這裡花費了一次 socket 系統呼叫的開銷 。

三、軟中斷模組

接著我們再轉換一下視角，來看負責接收和處理資料包的軟中斷這邊。關於網路包到網絡卡後是怎麼被網絡卡接收，最後在交由軟中斷處理的，這裡就不多贅述了。感興趣的請看之前的文章 《圖解Linux網路包接收過程》 。我們今天直接從 tcp 協議的接收函式 tcp_v4_rcv 看起。

軟中斷（也就是 Linux 裡的 ksoftirqd 程序）裡收到資料包以後，發現是 tcp 的包的話就會執行到 tcp_v4_rcv 函式。接著走，如果是 ESTABLISH 狀態下的資料包，則最終會把資料拆出來放到對應 socket 的接收佇列中。然後呼叫 sk_data_ready 來喚醒使用者程序。

呼叫 tcp_queue_rcv 接收完成之後，接著再呼叫 sk_data_ready 來喚醒在socket上等待的使用者程序 。   這又是一個函式指標。 回想上面我們在 建立 socket 流程裡執行到的 sock_init_data 函式，在這個函式里已經把 sk_data_ready 設定成 sock_def_readable 函式了（可以ctrl + f 搜尋前文）。它是預設的資料就緒處理函式。

在 sock_def_readable 中再一次訪問到了 sock->sk_wq 下的wait。回憶下我們前面呼叫 recvfrom 執行的最後，透過 DEFINE_WAIT(wait) 將當前程序關聯的等待佇列新增到 sock->sk_wq 下的 wait 裡了。

那接下來就是呼叫 wake_up_interruptible_sync_poll 來喚醒在 socket 上因為等待資料而被阻塞掉的程序了。

\_\_wake_up_common 實現喚醒。這裡注意下， 該函式呼叫是引數 nr_exclusive 傳入的是 1，這裡指的是 即使是有多個程序都阻塞在同一個 socket 上，也只喚醒 1 個程序。其作用是為了避免驚群 。

在 \_\_wake_up_common 中找出一個等待佇列項 curr，然後呼叫其 curr->func。回憶我們前面在 recv 函式執行的時候，使用 DEFINE_WAIT() 定義等待佇列項的細節，核心把 curr->func 設定成了 autoremove_wake_function。

在 autoremove_wake_function 中，呼叫了 default_wake_function。

呼叫 try_to_wake_up 時傳入的 task_struct 是 curr->private。這個就是當時因為等待而被阻塞的程序項。 當這個函式執行完的時候， 在 socket 上等待而被阻塞的程序就被推入到可執行佇列裡了，這又將是一次程序上下文切換的開銷 。

小結

好了，我們把上面的流程總結一下。 核心在通知網路包的執行環境分兩部分：

第一部分是我們自己程式碼所在的程序，我們呼叫的 socket() 函式會進入核心態建立必要核心物件。 recv() 函式在進入核心態以後負責檢視接收佇列，以及在沒有資料可處理的時候把當前程序阻塞掉，讓出 CPU。

第二部分是硬中斷、軟中斷上下文（系統程序 ksoftirqd）。在這些元件中，將包處理完後會放到 socket 的接收佇列中。然後再根據 socket 核心物件找到其等待佇列中正在因為等待而被阻塞掉的程序，然後把它喚醒。

每次一個程序專門為了等一個 socket 上的資料就得被從 CPU 上拿下來。然後再換上另一個程序。等到資料 ready 了，睡眠的程序又會被喚醒。總共兩次程序上下文切換開銷，根據之前的測試來看，每一次切換大約是 3-5 us(微秒)左右。 如果是網路 IO 密集型的應用的話，CPU 就不停地做程序切換這種無用功。

在服務端角色上，這種模式完全沒辦法使用。因為這種簡單模型裡的 socket 和程序是一對一的。我們現在要在單臺機器上承載成千上萬，甚至十幾、上百萬的使用者連線請求。如果用上面的方式，那就得為每個使用者請求都建立一個程序。 相信你在無論多原始的伺服器網路程式設計裡，都沒見過有人這麼幹吧。

如果讓我給它起一個名字的話，它就叫 單路不復用 （飛哥自創名詞）。那麼有沒有更高效的網路 IO 模型呢？ 當然有，那就是你所熟知的 select、poll 和 epoll了。 下次飛哥再開始拆解 epoll 的實現原始碼，敬請期待！

這種模式在客戶端角色上，現在還存在使用的情形。因為你的程序可能確實得等 Mysql 的資料返回成功之後，才能渲染頁面返回給使用者，否則啥也幹不了。

不過現在有一些封裝的很好的網路框架例如 Sogou Workflow，Golang 的 net 包等在網路客戶端角色上也早已摒棄了這種低效的模式！
