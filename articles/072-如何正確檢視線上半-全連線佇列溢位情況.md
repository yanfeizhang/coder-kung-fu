# 如何正確檢視線上半/全連線佇列溢位情況？

> 原文標題：如何正确查看线上半/全连接队列溢出情况？

> 原文連結：http://kfngxl.cn/index.php/archives/325/

---

大家好，我是飛哥！

在[《深入解析常見三次握手異常》](https://mp.weixin.qq.com/s/7Cum6Y28H_gXLyrRFrthNw)這一文中，我們討論到如果發生連線佇列溢位而丟包的話，會導致連線耗時會上漲很多。 那如何判斷一臺伺服器當前是否有半/全連線佇列溢位丟包發生呢？

我在我早期的一篇文章裡提到過，可以透過 netstat 來檢視。

```
# netstat -s
    8 SYNs to LISTEN sockets ignored
    160 times the listen queue of a socket overflowed
    ...
```

- SYNs to LISTEN sockets ignored 前面的數字是半連線佇列的溢位，

- times the listen queue of a socket overflowed 前面的數字是全連線佇列的溢位。

如果這兩個數字在動態增長，那就說明當前有溢位發生了。

但可惜這個說法存在一些問題。其中對於全連線佇列溢位描述 ok，但半連線佇列的描述很不正確！所以我今天專門發篇文章糾正一下，來從原始碼角度來分析一下為啥這樣說。

### 一、全連線佇列溢位判斷

全連線佇列溢位判斷比較簡單，所以先說這個。

#### 1. 全連線溢位丟包

全連線佇列溢位都會記錄到 ListenOverflows 這個 MIB（Management Information Base，管理資訊庫）上的，對應 SNMP 統計資訊中的 ListenDrops 這一項。我們來展開看一下相關的原始碼。

伺服器在響應客戶端的 SYN 握手包的時候，有可能會在 tcp_v4_conn_request 這裡發生全連線佇列溢位而丟包。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_conn_request(struct sock *sk, struct sk_buff *skb)
{
    //看看半連線佇列是否滿了
    ...

    //看看全連線佇列是否滿了
    if (sk_acceptq_is_full(sk) && inet_csk_reqsk_queue_young(sk) > 1) {
        NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENOVERFLOWS);
        goto drop;
    }
    ...
drop:
    NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENDROPS);
    return 0;
}
```

從上述程式碼中可以看到，全連線佇列滿了以後呼叫 NET_INC_STATS_BH 增加了 LINUX_MIB_LISTENOVERFLOWS 和 LINUX_MIB_LISTENDROPS 這兩個 MIB。

伺服器在響應第三次握手的時候，​會再次判斷全連線佇列是否溢位。如果溢位，一樣​會增加這兩個 MIB。原始碼如下：

```
//file: net/ipv4/tcp_ipv4.c
struct sock *tcp_v4_syn_recv_sock(...)
{
    if (sk_acceptq_is_full(sk))
        goto exit_overflow;
    ...
exit_overflow:
    NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENOVERFLOWS);
exit:
    NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENDROPS);
    return NULL;
}
```

​在 proc.c 中，LINUX_MIB_LISTENOVERFLOWS 和 LINUX_MIB_LISTENDROPS 都被整合進了 SNMP 統計資訊。

```
//file: net/ipv4/proc.c
static const struct snmp_mib snmp4_net_list[] = {
    SNMP_MIB_ITEM("ListenDrops", LINUX_MIB_LISTENDROPS),
    SNMP_MIB_ITEM("ListenOverflows", LINUX_MIB_LISTENOVERFLOWS),
    ......
}
```

#### 2.netstat 工具原始碼

我們在執行 netstat -s 的時候，該工具會讀取 SNMP 統計資訊並展現出來。netstat 命令屬於 net-tool 工具集，所以得找 net-tool 的原始碼。我用 SYNs to LISTEN sockets dropped 這種關鍵詞去搜到了：

```
//file: https://github.com/giftnuss/net-tools/blob/master/statistics.c
struct entry Tcpexttab[] =
{
    { "ListenDrops", N_("%u SYNs to LISTEN sockets dropped"), opt_number },
    { "ListenOverflows", N_("%u times the listen queue of a socket overflowed"),
    ......
}
```

以上這些就是執行 netstat -s 時會執行到的原始碼。它從 SNMP 統計資訊中獲取到 ListenDrops 和 ListenOverflows 這兩項顯示了出來，分別對應 LINUX_MIB_LISTENDROPS 和 LINUX_MIB_LISTENOVERFLOWS 這兩個 MIB。

```
# watch 'netstat -s | grep overflowed'
    198 times the listen queue of a socket overflowed
```

所以，每當發生全連線佇列滿導致的丟包的時候，可以透過上述命令的結果裡體現出來。而且幸運的是，ListenOverflows 這個 SNMP 統計項在只有在全連線佇列滿的時候才會增加，核心原始碼其它地方沒有用到。

所以，透過 netstat -s 輸出中的 xx times the listen queue 中的檢視到數字如果有變化，那麼一定是你的伺服器上發生了全連線佇列溢位了！！

### 二、半連線佇列溢位判斷

再來看半連線佇列，溢位時是更新的是 LINUX_MIB_LISTENDROPS 這個 MIB，對應到 SNMP 就是 ListenDrops 這個統計項。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_conn_request(struct sock *sk, struct sk_buff *skb)
{
    //看看半連線佇列是否滿了
    if (inet_csk_reqsk_queue_is_full(sk) && !isn) {
        want_cookie = tcp_syn_flood_action(sk, skb, "TCP");
        if (!want_cookie)
            goto drop;
    }

    //看看全連線佇列是否滿了
    if (sk_acceptq_is_full(sk) && inet_csk_reqsk_queue_young(sk) > 1) {
        NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENOVERFLOWS);
        goto drop;
    }
    ...
drop:
    NET_INC_STATS_BH(sock_net(sk), LINUX_MIB_LISTENDROPS);
    return 0;
}
```

上述原始碼中可見，半連線佇列滿的時候 goto drop，然後增加了 LINUX_MIB_LISTENDROPS 這個 MIB。透過上一節 netstat -s 的原始碼我們看到也會展示它出來（對應 SNMP 中的 ListenDrops 這個統計項）。

但是問題在於，不僅僅只是在半連線佇列發生溢位的時候會增加該值。所以根據 netstat -s 看半連線佇列是否溢位是不靠譜的！

上面看到，即使半連線佇列沒問題，全連線佇列滿了該值也會增加。另外就是當在 listen 狀態握手發生錯誤的時候，進入 tcp_v4_err 函式時也會增加該值。

對於如何檢視半連線佇列溢位丟包這個問題，我的建議是不要糾結咋看是否丟包了。直接看伺服器上的 tcp_syncookies 是不是 1 就行。

如果該值是 1 ，那麼下面程式碼中 want_cookie 就返回是真，是根本不會發生半連線溢位丟包的。

```
//file: net/ipv4/tcp_ipv4.c
int tcp_v4_conn_request(struct sock *sk, struct sk_buff *skb)
{
    //看看半連線佇列是否滿了
    if (inet_csk_reqsk_queue_is_full(sk) && !isn) {
        want_cookie = tcp_syn_flood_action(sk, skb, "TCP");
        if (!want_cookie)
            goto drop;
    }
```

如果 tcp_syncookies 不是 1，則建議改成 1 就完事了。

如果因為各種原因就是不想開啟 tcp_syncookies。就想死磕看下是否有因為半連線佇列滿而導致的 SYN 丟棄，除了 netstat -s 的結果，我建議同時檢視下當前 listen 的埠上的 SYN_RECV 的數量。

```
# netstat -antp | grep SYN_RECV
256
```

在[《為什麼服務端程式都需要先 listen 一下？》](https://mp.weixin.qq.com/s/hv2tmtVpxhVxr6X-RNWBsQ)中我們討論了半連線佇列的實際長度怎麼計算。如果 SYN_RECV 狀態的連線數量達到你算出來的佇列長度了，那麼可以確定是有半連線佇列溢位了。如果想加大半連線佇列的長度，方法我們在上面文章裡也一併講過了。

### 三、總結

最後，總結一下。

對於全連線佇列來說，使用 netstat -s （最好再配合 watch 命令動態觀察）就可以判斷是否有丟包發生。如果看到 “xx times the listen queue of a socket overflowed” 中的數值在增長，那麼就確定是全連線佇列滿了。

```
# watch 'netstat -s | grep overflowed'
    198 times the listen queue of a socket overflowed
```

對於半連線佇列來說，只要保證 tcp_syncookies 這個核心引數是 1 就能保證不會有因為半連線佇列滿而發生的丟包。如果確實較真就像看一看，netstat -s | grep "SYNs" 這個是沒有辦法說明問題的。還需要你自己計算一下半連線佇列的長度，再看下當前 SYN_RECV 狀態的連線的數量。

```
# watch 'netstat -s | grep "SYNs"'
    258209 SYNs to LISTEN sockets dropped
# netstat -antp | grep SYN_RECV | wc -l
5
```

至於如何加大半連線佇列長度，參考[《為什麼服務端程式都需要先 listen 一下？》](https://mp.weixin.qq.com/s/hv2tmtVpxhVxr6X-RNWBsQ)這篇文章就行了。
