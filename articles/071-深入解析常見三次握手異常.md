# 深入解析常見三次握手異常

> 原文標題：深入解析常见三次握手异常

> 原文連結：http://kfngxl.cn/index.php/archives/324/

---

大家好，我是飛哥！

在後端介面效能指標中一類重要的指標就是介面耗時。具體包括平均響應時間 TP90、TP99 耗時值等。這些值越低越好，一般來說是幾毫秒，或者是幾十毫秒。如果響應時間一旦過長，比如超過了 1 秒，在使用者側就能感覺到非常明顯的卡頓。如果長此以往，使用者可能就直接用腳投票，解除安裝我們的 App 了。

在正常情況下一次 TCP 連線耗時也就大約是一次 RTT 多一點。但事情不一定總是這麼美好，總會有意外發生。在某些情況下，可能會導致連線耗時上漲、CPU 處理開銷增加、甚至是超時失敗。

今天飛哥就來說一下我線上上遇到過的那些 TCP 握手相關的各種異常情況。

一、客戶端 connect 異常

埠號和 CPU 消耗這二者聽起來感覺沒啥太大聯絡。但我卻遭遇過因為埠號不足導致 CPU 消耗大幅上漲的情況。來聽飛哥分析分析為啥會出現這種問題！

客戶端在發起 connect 系統呼叫的時候，主要工作就是埠選擇（參見 TCP連線中客戶端的埠號是如何確定的？ ）。

在選擇的過程中，有個大迴圈，從 ip_local_port_range 的一個隨機位置開始把這個範圍遍歷一遍，找到可用埠則退出迴圈。如果埠很充足，那麼迴圈只需要執行少數幾次就可以退出。但假設說埠消耗掉很多已經不充足，或者乾脆就沒有可用的了。那麼這個迴圈就得執行很多遍。我們來看下詳細的程式碼。

在每次的迴圈內部需要等待鎖，以及在雜湊表中執行多次的搜尋。注意這裡的是自旋鎖，是一種非阻塞的鎖，如果資源被佔用，程序並不會被掛起，而是會佔用 CPU 去不斷嘗試獲取鎖。

但假設埠範圍 ip_local_port_range 配置的是 10000 - 30000， 而且已經用盡了。那麼每次當發起連線的時候都需要把迴圈執行兩萬遍才退出。這時會涉及大量的 HASH 查詢以及自旋鎖等待開銷，系統態 CPU 將會出現大幅度的上漲。

這是線上擷取到的正常時的 connect 系統呼叫耗時，是 22 us（微秒）。

這個是我們一臺伺服器在埠不足情況下 connect 開銷，是 2581 us（微秒）。

從上兩張圖中可以看出，異常情況下的 connect 耗時是正常情況下的 100 多倍。雖然換算成毫秒只有 2 ms 多一點，但是要知道這消耗的全是 CPU 時間。

二、第一次握手丟包

伺服器在響應來自客戶端的第一次握手請求的時候，會判斷一下半連線佇列和全連線佇列是否溢位。如果發生溢位，可能會直接將握手包丟棄，而不會反饋給客戶端。接下來我們分別來詳細看一下。

2.1 半連線佇列滿

我們來看下半連線佇列在何種情況下會導致丟包。

在上面程式碼中，inet_csk_reqsk_queue_is_full 如果返回 true 就表示半連線佇列滿了，另外 tcp_syn_flood_action 判斷是否開啟了核心引數 tcp_syncookies，如果未開啟則返回 false。

也就是說， 如果半連線佇列滿了，而且 ipv4.tcp_syncookies 引數設定為 0，那麼來自客戶端的握手包將 goto drop，意思就是直接丟棄！

SYN Flood 攻擊就是透過消耗光伺服器上的半連線佇列來使得正常的使用者連線請求無法被響應。不過在現在的 Linux 核心裡只要開啟 tcp_syncookies，半連線佇列滿了仍然也還可以保證正常握手的進行。

2.2 全連線佇列滿

我們注意到當半連線佇列判斷透過以後，緊接著還有全連線佇列滿的相關判斷。如果這個條件成立，伺服器對握手包的處理還是會 goto drop，丟棄了之。我們來看下原始碼：

sk_acceptq_is_full 來判斷全連線佇列是否滿了，inet_csk_reqsk_queue_young 判斷的是有沒有 young_ack（未處理完的半連線請求）。

這段程式碼可以看到， 假如全連線佇列滿的情況下，且同時有 young_ack ，那麼核心同樣直接丟掉該 SYN 握手包 。

2.3 客戶端發起重試

假設說伺服器側發生了全/半連線佇列溢位而導致的丟包。那麼從轉換到客戶端視角來看就是 SYN 包沒有任何響應。

好在客戶端在發出握手包的時候，開啟了一個重傳定時器。如果收不到預期的 synack 的話，超時重傳的邏輯就會開始執行。不過重傳計時器的時間單位都是以秒來計算的，這意味著，如果有握手重傳發生，即使第一次重傳就能成功，那介面最快響應也是 1 s 以後的事情了。這對介面耗時影響非常的大。

我們來詳細看下重傳相關的邏輯。伺服器在 connect 發出 syn 後就開啟了重傳定時器。

在定時器設定中傳入的 inet_csk(sk)->icsk_rto 是超時時間，該值初始的時候被設定為了 1 秒。

在一些老版本的核心，比如 2.6 裡，重傳定時器的初始值是 3 秒。

如果能正常接收到伺服器響應的 synack，那麼客戶端的這個定時器會清除。這段邏輯在 tcp_rearm_rto 裡。 （tcp_rcv_state_process -> tcp_rcv_synsent_state_process -> tcp_ack -> tcp_clean_rtx_queue -> tcp_rearm_rto）

如果伺服器端發生了丟包，那麼定時器到時後會進行回撥函式 tcp_write_timer 中進行重傳。

tcp_retransmit_timer 是重傳的主要函式。在這裡完成重傳，以及下一次定時器到期時間的設定。

tcp_write_timeout 是判斷是否重試過多，如果是則退出重試邏輯。

接著在 tcp_retransmit_timer 重發了傳送佇列裡的頭元素。而且還設定了下一次超時的時間，為前一次的兩倍（左移操作相當於乘2）。

2.4 實際抓包結果

我們來看一個因為伺服器端響應第一次握手丟包的握手過程抓包截圖。

透過該圖可以看到，客戶端在 1 s 以後進行了第一次握手重試。重試仍然沒有響應，那麼接下來依次又分別在 3 s、7 s 15 s，31 s，63 s 等時間共重試了 6 次（我的 tcp_syn_retries 當時設定是 6）。

假如我們伺服器上在第一次握手的時候出現了半/全連線佇列溢位導致的丟包，那麼我們的介面響應時間將至少是 1 s 以上（在某些老版本的核心上，SYN 第一次的重試就需要等 3 秒），如果連續兩三次握手都失敗，那 7，8 秒就出去了。你想想這對使用者是不是影響很大。

三、第三次握手丟包

客戶端在收到伺服器的 synack 響應的時候，就認為連線建立成功了，然後會將自己的連線狀態設定為 ESTABLISHED，發出第三次握手請求。但伺服器在第三次握手的時候，還有可能會有意外發生。

從上述程式碼可以看出， 第三次握手時，如果伺服器全連線佇列滿了，來自客戶端的 ack 握手包又被直接丟棄了 。

想想也很好理解，三次握手完的請求是要放在全連線佇列裡的。但是假如全連線佇列滿了，仍然三次握手也不會成功。

不過有意思的是，第三次握手失敗並不是客戶端重試，而是由服務端來重發 synack。

我們搞一個實際的 Case 來直接抓包看一下。我專門寫了個簡單的 Server 只 listen 不 accept，然後找個客戶端把它的連線佇列消耗光。這時候，再用另一個客戶端向它發起請求時的抓包結果。

第一個紅框內是第三次握手，其實這個握手請求在伺服器端以及被丟棄了。但是這時候客戶端並不知情，它一直傻傻地以為三次握手已經妥了呢。不過還好，這時在伺服器的半連線佇列中仍然記錄著第一次握手時存的握手請求。

伺服器等到半連線定時器到時後，向客戶端重新發起 synack ，客戶端收到後再重新回覆第三次握手 ack。如果這期間伺服器端全連線佇列一直都是滿的，那麼伺服器重試 5 次（受核心引數 net.ipv4.tcp_synack_retries 控制）後就放棄了。

在這種情況下大家還要注意另外一個問題。在實踐中，客戶端往往是以為連線建立成功就會開始傳送資料，其實這時候連線還沒有真的建立起來。他發出去的資料，包括重試都將全部被伺服器無視。直到連線真正建立成功後才行。

四、總結

衡量工程師是否優秀的標準之一就是看他能否有能力定位和處理線上發生的各種問題。連看似簡單的一個 TCP 三次握手，工程實踐中可能會有各種意外發生。 如果對握手理解不深，那麼很有可能無法處理線上出現的各種故障。

今天的文章主要是描述了埠不足、半連線佇列滿、全連線佇列滿時的情況，

當埠不充足的時候 ，會導致 connect 系統呼叫的時候過多地執行自旋鎖等待與 Hash 查詢，會引起 CPU 開銷上漲。嚴重情況下會耗光 CPU，影響使用者業務邏輯的執行。 出現這種問題處理起來方法有這麼幾個。

透過調整 ip_local_port_range 來儘量加大埠範圍

儘量複用連線，使用長連線來削減頻繁的握手處理

第三個有用，但是不太推薦的是開啟 tcp_tw_reuse 和 tcp_tw_recycle

伺服器端在第一次握手時可能會丟包 ， 在如下兩種情況下會發生。

半連線佇列滿，且 tcp_syncookies 為 0

全連線佇列滿，且有未完成的半連線請求

在這兩種情況下，客戶端視角來看和網路斷了沒有區別，就是發出去的 SYN 包沒有任何反饋，然後等待定時器到時後重傳握手請求。 第一次重傳時間是 1 s ，接下來的等待間隔是翻倍地增長，2 s，4 s，8 s ...。總的重傳次數由 net.ipv4.tcp_syn_retries 核心引數影響（注意我的用詞是影響，而不是決定）。

伺服器在第三次握手時也可能會出問題 ，如果全連線佇列滿，仍將會發生丟包。不過第三次握手失敗時，只有伺服器端知道（客戶端誤以為連線已經建立成功了）。伺服器根據半連線佇列裡的握手資訊發起 synack 重試，重試次數由 net.ipv4.tcp_synack_retries 控制。

一旦你的線上出現了上面這些連線佇列溢位導致的問題，你的服務將會受到比較嚴重的影響。即使第一次重試就能夠成功，那你的介面響應耗時將直接上漲到 1 s（老版本上是 3 s）。如果重試上兩三次都沒有成功，Nginx 很有可能直接就報訪問超時失敗了。

正因為握手重試對我們服務影響很大，所以能深刻理解三次握手中的這些異常情況很有必要。再說說如果出現了丟包的問題，我們該如何應對。

方法1，開啟 syncookie

在現代的 Linux 版本里，我們可以透過開啟 tcp_syncookies 來防止過多的請求打滿半連線佇列包括 SYN Flood 攻擊，來解決伺服器因為半連線佇列滿而發生的丟包。

方法2，加大連線佇列長度

在 《為什麼服務端程式都需要先 listen 一下？》 中，我們討論過全連線佇列的長度是 min(backlog, net.core.somaxconn)半連線佇列長度是。 半連線佇列長度有點小複雜，是 min(backlog, somaxconn, tcp_max_syn_backlog) + 1 再上取整到 2 的冪次，但最小不能小於16。

如果需要加大全/半連線佇列長度，請調節以上的一個或多個引數來達到目的。只要佇列長度合適，就能很大程式降低握手異常機率的發生。

方法3，儘快地 accept

另外這個雖然一般不會成為問題，但也要注意一下。你的應用程式應該儘快在握手成功之後透過 accept 把新連線取走。不要忙於處理其它業務邏輯而導致全連線佇列塞滿了。

方法4，儘量減少 TCP 連線的次數

如果上述方法都未能根治你的問題，那說明你的伺服器上 TCP 連線請求太、太過於頻繁了。這個時候你應該思考下是否可以用長連線代替短連線，減少過於頻繁的三次握手。這個方法不但能解決握手出問題的可能，而且還順帶砍掉了三次握手的各種記憶體、CPU、時間上的開銷，對提升效能也有較大幫助。
