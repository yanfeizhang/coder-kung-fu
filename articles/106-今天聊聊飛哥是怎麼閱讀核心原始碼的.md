# 今天聊聊飛哥是怎麼閱讀核心原始碼的

> 原文標題：今天聊聊飞哥是怎么阅读内核源码的

> 原文連結：https://mp.weixin.qq.com/s/-WA6J9BZeZJIQTZtDHD5hA

大家好，我是飛哥！

經常在後臺收到讀者的交流，Linux 原始碼那麼龐大，飛哥你是如何讀的呢？由於問這個問題的太多，我想有必要專門寫一篇文章聊一聊。

首先，我先說一點，其實我本人不是從事核心相關工作的。我和大多數同學都一樣，從事的也是應用層上的開發，負責的是後端模組。

那我為什麼要研究原始碼這個之前我說過，是因為我在多年的工作中遇到的很多問題都是底層相關的。不深入底層看一看，感覺永遠是在隔靴撓癢，永遠理解不到問題的本質。（這裡說的底層其實也不只是包括 Linux 核心 (Linux Kernel)，還包括一些硬體的組成原理什麼的）。

飛哥走過的彎路

雖然我們今天的主題是原始碼，不過我並不建議你一開始就陷入到原始碼裡，這也是我走過的彎路。

在我剛開始想深入挖掘網路 (Network) 效能的時候，我買來了《深入理解 LINUX 核心》《深入理解 Linux 網路技術內幕》等幾本書。這本書裡介紹了核心中各個元件，如網路卡 (Network Card) 裝置、鄰居子系統、路由等，把相關原始碼都講了一遍。

我啃了好長時間，但結果是看完以後感覺還是一團漿糊。尤其是到了工作中具體的一個實際問題的時候，發現根本還是理解不了網路模組到底是怎麼運作的。例如一個包到底是如何從網路卡到應用程式中的，這些書看半天還是弄不明白這個問題。就更別提後續進行一些網路最佳化工作了。

到了後來，我改變了戰術，才算是柳暗花明又一村，找到了真正正確、高效的方法。

產生問題

我所找到的正確方法就是，以工作中的實際問題為核心。

回頭想想我們看原始碼的目的是什麼呢，是要理解 Linux？我想不是，理解 Linux 只是途徑，而我們的真正目的是為了提高我們手頭的工作。

例如，我想觀察我的服務中 Linux 的接收封包的過程是否出現了問題，以及想嘗試在這個接收過程中都有哪些最佳化方法。根據這個工作中的需求出發，然後我就四處開始翻資料，打算要把 Linux 是如何接收和處理一個網路封包 (Network Packet) 徹底釐清。包括我之前看過的原始碼的書，也查了好多網路上的文章。最後終於摸出了個十之八九，總結出了圖解 Linux 網路封包接收過程。

再例如我手頭的專案中很多地方需要維持長連線，那麼我就想理解一臺 Linux 伺服器最多能支撐多少個 TCP 連線？這種問題更是，幾乎沒有任何書，任何資料，任何文章能給一個讓我滿意的答案。這個時候光翻原始碼，看網路上的技術文也是遠遠不夠的，我動手寫了不少測試程式碼，親手進行實踐。寫出了

- 漫畫|一臺 Linux 伺服器最多能支撐多少個 TCP 連線？
- 漫畫 | 理解了 TCP 連線的實作以後，用戶端的併發也爆發了！
- 百看不如一練，動手測試單機百萬連線的保姆級教學！

再例如有同學問了我，127.0.0.1 是如何進行網路封包收發的，和跨機 IO 相比，能節約哪些開銷？為了解開這個疑問，我翻了原始碼又寫出了 127.0.0.1 之本機網路通訊過程知多少 ?！

但其實我所關注的點並不都在核心原始碼上。例如在我前期的一些文章裡，我想弄明白存取記憶體 (Memory) 的速度。我研究了 L1、L2、L3。還調研了記憶體的工作原理。隨後發現了記憶體在隨機 IO  的時候也是會比順序 IO 要慢幾倍的。後來我想理解固態硬碟 (Solid-State Drive, SSD) 和機械硬碟 (Hard Disk Drive, HDD) 的速度差異，我又去分析了固態硬碟的實體構成。而且所有的這些我都搭配了實際的效能測試。

今天的重點並不是給大家介紹這些文章，我想表達的意思是，產生問題非常重要。

這些問題最好是能和你手工工作相關，因為這樣你後期才能在工作中進行應用和提升。我覺得只有有用的技術，才是真正有價值的技術。至於說硬體組成原理，核心原始碼，極客時間上的一些優秀的網課，都是解決這些問題是的工具而已。

原始碼閱讀方法

在解決問題的時候，核心原始碼確實是很重要的一塊，也是我們今天介紹的主題。看程式碼我覺得有兩個方法，可以用地毯式的轟炸和精確制導來類比。

地毯式轟炸

地毯式轟炸就是不管三七二十一，把核心所有的原始碼全部硬啃一遍。各個元件都進去看一看，瞭解瞭解。

除非你本身就是從事核心相關工作的，否則我是不推薦大家去把核心原始碼通讀一遍的。這也是我前面和大家講過的我走的彎路。因為這樣做有如下的缺點：

第一，我們大部分的讀者都是已經工作了的同學。你沒有學生時代那麼大塊的時間去整塊整塊的啃。

第二，即使你啃完了，你和手頭的工作還是聯絡不起來。前面我說過，我啃完了《深入理解 Linux 網路技術內幕》，仍然連網路封包是如何從網路卡到使用者程序 (Process) 裡的還是沒理解。

這就好比在戰場上，動用大量的武器彈藥進行狂轟濫炸。這種方法非常浪費彈藥，而且很有可能還沒有炸到關鍵的碉堡。

精確制導

這個是我所推薦的方法。前面不是說過，我們一定要先產生一個問題麼。那麼我們看原始碼的目標就是要精確制導消滅這個物件。

等我們進入到核心原始碼裡的時候，你會發現這裡面邏輯關係錯綜複雜。如果每一個邏輯你都想鑽進去弄個明白，最後可能就是累死在核心原始碼的迷宮裡了。

所以我們在看原始碼的時候，要時刻牢記我們要消滅的問題是什麼。如果某段邏輯和你要解決的問題無關，那就直接繞過去，繞過去，不要戀戰！

你在我的文章裡應該也能發現，我雖然會貼核心原始碼，但是絕大部分的原始碼都包含省略號。這些就是我覺得和當前主題無關的原始碼，所以我都躲著它們走。

例如在介紹核心傳送資料過程的時候，我介紹到  `inet_sendmsg`，我是這樣展示的的。

```
//file:  net/ipv4/af_inet.c
int  inet_sendmsg(......)
{
......
return sk->sk_prot->sendmsg(iocb, sk, msg, size);
}
```

而實際上，核心的原始碼長的是這樣的。

```
int   inet_sendmsg(struct kiocb *iocb, struct socket *sock, struct msghdr *msg,
size_t size)
{
struct sock *sk = sock->sk;

sock_rps_record_flow(sk);

/* We may need to   bind the socket. */
if (! inet_sk(sk)-> inet_num && !sk-> sk_prot-> no_autobind &&
inet_autobind(sk))
return -EAGAIN;

return sk->sk_prot->sendmsg(iocb, sk, msg, size);
}
```

省略掉的這段邏輯我認為和我要解決的問題關係很小，所以都被我繞開了。

每次透過這種方法解決掉你的一個問題的時候，你就以點狀的形式在洞穿理解了核心某一片的邏輯。等當你解決掉很多問題的時候，點會逐漸的連成面。這時候反而能得到更全面的，更深刻的理解。

小結一下，要時刻記住要消滅的問題是什麼，無關的程式碼能繞開就都繞開。

吾生有涯，而知無涯，我們只挑對我們有用的進行學習。

開啟指定檔案

Linux 的目錄多，而且目錄下的檔案也太多。有的時候即使你知道原始碼在哪個目錄下，可能還是得翻半天才能找到。如果你明確知道原始碼檔案的位置，那麼可以直接開啟它就行。

例如 tcp 的關鍵接收入口函式  `tcp_v4_rcv`，它在 `net/ipv4/tcp_ipv4.c` 這個檔案下（我的文章裡我儘量會把每一個函式所處的位置都標清楚）。

那麼如果你想快速開啟這個函式，那麼你按下快捷鍵 cmd + p（Windows 下 ctrl + p）。直接輸入  tcp_ipv4.c 這個檔名就可以了。

?

這個時候開啟了這個檔案，想跳到函式位置，那就 cmd + f（Windows 下 ctrl + f） 搜尋下 `tcp_v4_rcv` 就行了。

我常用的就這麼幾個，如果想看所有的快捷鍵，那就 cmd + k,接著再 cmd + s （Windows 下是 ctrl + k, ctrl +s）可以檢視到所有的快捷鍵。

總結一下

不知道大家有沒有聽說過「勢道術」。

- 勢是未來發展的大勢
- 道是事物背後的規律
- 術是技術層面的操作方法

很明顯這三個層次裡越靠前是越牛的。我這裡套用一個這個概念，今天其實給大家分享了兩個層次的東西。

在術的層面，我分享了我是怎麼看 Linux 原始碼的，在哪裡下載原始碼，用的什麼工具，按的什麼快捷鍵。不過我覺得這個不是最重要的。

在道的層面，學習技術最主要的目的是要能解決我們手頭工作中的問題，明確你要解決的問題之後，精確制導，把所有的精力都圍繞著這個問題進行。至於說底層的硬體組成原理也好，核心原始碼也罷，極客時間上的優秀網課，都只不過是我在解決這些問題是的工具而已。不要本末倒置了，學以致用，學的目的就是用。

有的讀者和我反饋說，很多知識自己也不是沒看過，但是看過就忘。其實我覺得這裡面可能主要的原因就是沒有和手頭的工作結合起來，沒有用起來。如果你用這些知識解決過自己的工作中的實際問題，甚至是有過效能最佳化之類的經驗，我想這樣你學過的東西是忘不了的。
