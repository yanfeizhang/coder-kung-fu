# 檔案過多時ls命令為什麼會卡住？

> 原文標題：文件过多时ls命令为什么会卡住？

> 原文連結：https://www.cnblogs.com/kfngxl/p/13929801.html

---

不知道你有沒有遇到過當一個資料夾下檔案特別多，在下面執行`ls`命令的時候要等好長時間才能展現出來的問題？如果有，你有想過這是為什麼嗎，我們該如何解決?
要想深入理解這個的問題產生的原因，我們就需要從資料夾佔用的磁碟空間開始討論了。

## inode消耗驗證

在《新建一個空檔案佔用多少磁碟空間？》中我提到了每一個檔案會消耗其所在資料夾中的一點空間。資料夾呢，其實也一樣會消耗inode的。 我們先看一下當前inode的佔用情況

```
# df -i
Filesystem            Inodes   IUsed   IFree IUse% Mounted on
......
/dev/sdb1            2147361984 12785020 2134576964    1% /search
```

再建立一個空資料夾

```
# mkdir temp
# df -i
Filesystem            Inodes   IUsed   IFree IUse% Mounted on
......
/dev/sdb1            2147361984 12785021 2134576963    1% /search
```

透過IUsed可以看到，和空檔案一樣，空的資料夾也會消耗掉一個inode。不過這個很小，我的機器上才是256位元組而已，應當不是造成`ls`命令卡主的元兇。

## block消耗驗證

資料夾的名字存在哪兒了呢？嗯，和《新建一個空檔案佔用多少磁碟空間？》裡的檔案類似，會消耗一個`ext4_dir_entry_2`（今天用ext4舉例，它在linux原始碼的fs/ext4/ex4.h檔案裡定義）,放到其父目錄的block裡了。根據這個，相信你也很快能想到，如果它自己節點下建立一堆檔案的話，就會佔用它自己的block。我們來動手驗證一下：

```
# mkdir test
# cd test
# du -h
4.0K    .
```

這裡的4KB就表示消耗掉了一個block。 空檔案不消耗block，空目錄為啥一開始就消耗block了呢，那是因為其必須預設帶兩個目錄項"."和".."。另外這個4K在你的機器上不一定是這麼大，它其實是一個block size，在你格式化的時候決定的。

我們再新建兩個空的檔案，再檢視一下：

```
# touch aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaab
# touch aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
# du -h
4.0K    .
```

貌似，沒有什麼變化。這是因為

- 第一、新的空檔案不佔用block，所以這裡顯示的仍然是目錄佔用的block。

- 第二、之前資料夾建立時候分配的4KB裡面空閒空間還有，夠放的下這兩個檔案項

那麼我再多建立一些試試，動用指令碼建立100個檔名長度為32Byte的空檔案。

```
#!/bin/bash
for((i=1;i<=100;i++));
do
        file="tempDir/"$(echo $i|awk '{printf("%032d",$0)}')
        echo $file
        touch $file
done
```

```
# du -h
12K    .
```

哈哈，這時我們發現目錄佔用的磁碟空間變大了，成了3個Block了。當我們建立到10000個檔案的時候，

```
# du -h
548K     .
```

在每一個`ext4_dir_entry_2`裡都除了檔名以外，還記錄著inode號等資訊，詳細定義如下：

```
struct ext4_dir_entry_2 {
        __le32  inode;                  /* Inode number */
        __le16  rec_len;                /* Directory entry length */
        __u8    name_len;               /* Name length */
        __u8    file_type;
        char    name[EXT4_NAME_LEN];    /* File name */
};
```

我們計算一下，平均每個檔案佔用的空間=548K/10000=54位元組。也就是說，比我們的檔名32位元組大一點點，基本對上了。 這裡我們也領會到一個事實，檔名越長，在其父目錄中消耗的空間也會越大。

## 本文結論

一個資料夾當然也是要消耗磁碟空間的。

- 首先要消耗掉一個inode，我的機器上它是256位元組

- 需要消耗其父目錄下的一個目錄項`ext4_dir_entry_2`，儲存自己inode號，目錄名。

- 其下面如果建立資料夾或者檔案的話，它就需要在自己的block裡`ext4_dir_entry_2`陣列

目錄下的檔案/子目錄越多，目錄就需要申請越多的block。另外`ext4_dir_entry_2`大小不是固定的，檔名/子目錄名越長，單個目錄項消耗的空間也就越大。

對於開篇的問題，我想你現在應該明白為什麼了,問題出在資料夾的block身上。
這就是當你的資料夾下面檔案特別多，尤其是檔名也比較長的時候，它會消耗掉非常多的block。當你遍歷資料夾的時候，如果Page Cache中沒有命中你要訪問的block，就會穿透到磁碟上進行實際的IO。在你的角度來看，就是你執行完`ls`後，卡住了。

那麼你肯定會問，我確實要儲存許許多多的檔案，我該怎麼辦? 其實也很簡單，多建立一些資料夾就好了，一個目錄下別存太多，就不會有這個問題了。工程實踐中，一般的做法就是透過一級甚至是二級hash把檔案雜湊到多個目錄中，把單目錄檔案數量控制在十萬或萬以下。

## ext的bug

貌似今天的實踐應該結束了，現在讓我們把剛剛建立的檔案全部刪掉，再看一下。

```
# rm -f *
# du -h
72K     .
```

等等，什麼情況？資料夾下的檔案都已經刪了，該資料夾為什麼還佔用72K的磁碟空間？
這個疑惑也伴隨了我很長時間，後來才算是解惑。問題關鍵在於`ext4_dir_entry_2`中的`rec_len`。這個變數儲存了當前整個`ext4_dir_entry_2`物件的長度，這樣作業系統在遍歷資料夾的時候，就可以透過當前的指標，加上這個長度就可以找到資料夾中下一個檔案的`dir_entry`了。這樣的優勢是遍歷起來非常方便，有點像是一個連結串列，一個一個穿起來的。
但是，如果要刪除一個檔案的話，就有點小麻煩了，當前檔案結構體變數不能直接刪，否則連結串列就斷了。
Linux的做法是在刪除檔案的時候，在其目錄中只是把inode設定為0就拉倒，並沒有回收整個`ext4_dir_entry_2`物件。其實和大家做工程的時候經常用到的假刪除是一個道理。現在的xfs檔案系統好像已經沒有這個小問題了，但具體咋解決的，暫時沒有深入研究，如果你有答案，歡迎留言！
