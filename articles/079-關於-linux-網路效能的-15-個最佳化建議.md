# 關於 Linux 網路效能的 15 個最佳化建議！

大家好，我是飛哥！ 最近我出了一本非常受歡迎的新書──​《深入理解Linux網路》。在這本書中我們深入地討論了很多核心網路模組相關的問題。討論了一個網路包是如何從網絡卡到達使用者程序的，聊了同步阻塞和多路複用 epoll，也詳細討論了資料是如何從程序傳送出去的等等一系列深度的網路工作原理。

這本書首發當日就登上了京東的科技類銷量日冠軍，剛上市三個星期就已經開始了第三次的加印，可以說是非常的熱門。如果你能看完這本書，你就會正和庖丁一樣，從今日往後我們看到的也不再是整個的 Linux （整頭牛）了，而是核心的內部各個模組（筋⻣肌理）。

那麼具備了對網路的深刻的理解之後，我們在效能方面有哪些最佳化手段可用呢？我這裡給出一些開發或者運維中的效能最佳化建議。這些建議都是從書中摘錄的。不過要注意的是，每一種效能最佳化方法都有它適用或者不適用的應用場景。你應當根據你當前的專案現狀靈活來選擇用或者不用。

建議1：儘量減少不必要的網路 IO

我要給出的第一個建議就是不必要用網路 IO 的儘量不用。

是的，網路在現代的網際網路世界裡承載了很重要的角色。使用者透過網路請求線上服務、伺服器透過網路讀取資料庫中資料，透過網路構建能力無比強大分散式系統。網路很好，能降低模組的開發難度，也能用它搭建出更強大的系統。但是這不是你濫用它的理由！

原因是即使是本機網路 IO 開銷仍然是很大的。先說傳送一個網路包，首先得從使用者態切換到核心態，花費一次系統呼叫的開銷。進入到核心以後，又得經過冗長的協議棧，這會花費不少的 CPU 週期，最後進入環回裝置的“驅動程式”。接收端呢，軟中斷花費不少的 CPU 週期又得經過接收協議棧的處理，最後喚醒或者通知使用者程序來處理。當服務端處理完以後，還得把結果再發過來。又得來這麼一遍，最後你的程序才能收到結果。你說麻煩不麻煩。另外還有個問題就是多個程序協作來完成一項工作就必然會引入更多的程序上下文切換開銷，這些開銷從開發視角來看，做的其實都是無用功。

上面我們還分析的只是本機網路 IO，如果是跨機器的還得會有雙方網絡卡的 DMA 複製過程，以及兩端之間的網路 RTT 耗時延遲。所以，網路雖好，但也不能隨意濫用！

建議3：呼叫者與被呼叫機器儘可能部署的近一些

在前面的章節中我們看到在握手一切正常的情況下， TCP 握手的時間基本取決於兩臺機器之間的 RTT 耗時。雖然我們沒辦法徹底去掉這個耗時，但是我們卻有辦法把 RTT 降低，那就是把客戶端和伺服器放的足夠地近一些。儘量把每個機房內部的資料請求都在本地機房解決，減少跨地網路傳輸。

舉例，假如你的服務是部署在北京機房的，你呼叫的 mysql、redis最好都位於北京機房內部。儘量不要跨過千里萬里跑到廣東機房去請求資料，即使你有專線，耗時也會大大增加！在機房內部的伺服器之間的 RTT 延遲大概只有零點幾毫秒，同地區的不同機房之間大約是 1 ms 多一些。但如果從北京跨到廣東的話，延遲將是 30 - 40 ms 左右，幾十倍的上漲！

建議4：內網呼叫不要用外網域名

假如說你所在負責的服務需要呼叫兄弟部門的一個搜尋介面，假設介面是："http://www.sogou.com/wq?key=開發內功修煉"。

那既然是兄弟部門，那很可能這個介面和你的服務是部署在一個機房的。即使沒有部署在一個機房，一般也是有專線可達的。 所以不要直接請求 www.sogou.com， 而是應該使用該服務在公司對應的內網域名 。在我們公司內部，每一個外網服務都會配置一個對應的內網域名，我相信你們公司也有。

為什麼要這麼做，原因有以下幾點

1） 外網介面慢 。本來內網可能過個交換機就能達到兄弟部門的機器，非得上外網兜一圈再回來，時間上肯定會慢。

2） 頻寬成本高 。在網際網路服務裡，除了機器以外，另外一塊很大的成本就是 IDC 機房的出入口頻寬成本。 兩臺機器在內網不管如何通訊都不涉及到頻寬的計算。但是一旦你去外網兜了一圈回來，行了，一進一出全部要繳頻寬費，你說虧不虧！！

3） NAT 單點瓶頸 。一般的伺服器都沒有外網 IP，所以要想請求外網的資源，必須要經過 NAT 伺服器。但是一個公司的機房裡幾千臺伺服器中，承擔 NAT 角色的可能就那麼幾臺。它很容易成為瓶頸。我們的業務就遇到過好幾次 NAT 故障導致外網請求失敗的情形。  NAT 機器掛了，你的服務可能也就掛了，故障率大大增加。

建議5：調整網絡卡 RingBuffer 大小

在 Linux 的整個網路棧中，RingBuffer 起到一個任務的收發中轉站的角色。對於接收過程來講，網絡卡負責往 RingBuffer 中寫入收到的資料幀，ksoftirqd 核心執行緒負責從中取走處理。只要 ksoftirqd 執行緒工作的足夠快，RingBuffer 這個中轉站就不會出現問題。

但是我們設想一下，假如某一時刻，瞬間來了特別多的包，而 ksoftirqd 處理不過來了，會發生什麼？這時 RingBuffer 可能瞬間就被填滿了，後面再來的包網絡卡直接就會丟棄，不做任何處理！

透過 ethtool 就可以加大 RingBuffer 這個“中轉倉庫”的大小。。

這樣網絡卡會被分配更大一點的”中轉站“，可以解決偶發的瞬時的丟包。不過這種方法有個小副作用，那就是排隊的包過多會增加處理網路包的延時。所以應該讓核心處理網路包的速度更快一些更好，而不是讓網路包傻傻地在 RingBuffer 中排隊。我們後面會再介紹到 RSS ，它可以讓更多的核來參與網路包接收。

建議7：使用 eBPF 繞開協議棧的本機 IO

如果你的業務中涉及到大量的本機網路 IO 可以考慮這個最佳化方案。本機網路 IO 和跨機 IO 比較起來，確實是節約了驅動上的一些開銷。傳送資料不需要進 RingBuffer 的驅動佇列，直接把 skb 傳給接收協議棧(經過軟中斷)。但是在核心其它元件上，可是一點都沒少，系統呼叫、協議棧(傳輸層、網路層等)、裝置子系統整個走 了一個遍。連“驅動”程式都走了(雖然對於迴環裝置來說這個驅動只是一個純軟體的虛擬出來的東東)。

如果想用本機網路 IO，但是又不想頻繁地在協議棧中繞來繞去。那麼你可以試試 eBPF。使用 eBPF 的 sockmap 和 sk redirect 可以繞過 TCP/IP 協議棧，而被直接傳送給接收端的 socket，業界已經有公司在這麼做了。

建議8： 儘量少用 recvfrom 等程序阻塞的方式

在使用了 recvfrom 阻塞方式來接收 socket 上資料的時候。每次一個程序專⻔為了等一個 socket 上的資料就得被從 CPU 上拿下來。然後再換上另一個 程序。等到資料 ready 了，睡眠的程序又會被喚醒。總共兩次程序上下文切換開銷。如果我們伺服器上需要有大量的使用者請求需要處理，那就需要有很多的程序存在，而且不停地切換來切換去。這樣的缺點有如下這麼幾個：

因為每個程序只能同時等待一條連線，所以需要大量的程序。

程序之間互相切換的時候需要消耗很多 CPU 週期，一次切換大約是 3 - 5 us 左右。

頻繁的切換導致 L1、L2、L3 等快取記憶體的效果大打折扣

大家可能以為這種網路 IO 模型很少見了。但其實在很多傳統的客戶端 SDK 中，比如 mysql、redis 和 kafka 仍然是沿用了這種方式。

建議9：使用成熟的網路庫

使用 epoll 可以高效地管理海量的 socket。在伺服器端。我們有各種成熟的網路庫進行使用。這些網路庫都對 epoll 使用了不同程度的封裝。

首先第一個要給大家參考的是 Redis。老版本的 Redis 裡單程序高效地使用 epoll 就能支援每秒數萬 QPS 的高效能。如果你的服務是單程序的，可以參考 Redis 在網路 IO 這塊的原始碼。

如果是多執行緒的，執行緒之間的分工有很多種模式。那麼哪個執行緒負責等待讀 IO 事件，那個執行緒負責處理使用者請求，哪個執行緒又負責給使用者寫返回。根據分工的不同，又衍生出單 Reactor、多 Reactor、以及 Proactor 等多種模式。大家也不必頭疼，只要理解了這些原理之後選擇一個效能不錯的網路庫就可以了。比如 PHP 中的 Swoole、Golang 的 net 包、Java 中的 netty 、C++ 中的  Sogou Workflow 都封裝的非常的不錯。

建議10：使用 Kernel-ByPass 新技術

如果你的服務對網路要求確實特別特特別的高，而且各種最佳化措施也都用過了，那麼現在還有終極最佳化大招 -- Kernel-ByPass 技術。

核心在接收網路包的時候要經過很⻓的收發路徑。在這期間牽涉到很多核心元件之間的協同、協議棧的處理、以及核心態和使用者態的複製和切換。 Kernel-ByPass 這類的技術方案就是繞開核心協議棧，自己在使用者態來實現網路包的收發。這樣不但避開了繁雜的核心協議棧處理，也減少了頻繁了核心態使用者態之間的複製和切換，效能將發揮到極致！

目前我所知道的方案有 SOLARFLARE 的軟硬體方案、DPDK 等等。如果大家感興趣，可以多去了解一下！

建議11：配置充足的埠範圍

客戶端在呼叫 connect 系統呼叫發起連線的時候，需要先選擇一個可用的埠。核心在選用埠的時候，是採用從可用埠範圍中某一個隨機位置開始遍歷的方式。如果埠不充足的話，核心可能需要迴圈撞很多次才能選上一個可用的。這也會導致花費更多的 CPU 週期在內部的雜湊表查詢以及可能的自旋鎖等待上。因此不要等到埠用盡報錯了才開始加大埠範圍，而且應該一開始的時候就保持一個比較充足的值。

如果埠加大了仍然不夠用，那麼可以考慮開啟埠 reuse 和 recycle。這樣埠在連線斷開的時候就不需要等待 2MSL 的時間了，可以快速回收。開啟這個引數之前需要保證 tcp_timestamps 是開啟的。

建議12：小心連線佇列溢位

伺服器端使用了兩個連線佇列來響應來自客戶端的握手請求。這兩個佇列的長度是在伺服器 listen 的時候就確定好了的。如果發生溢位，很可能會丟包。所以如果你的業務使用的是短連線且流量比較大，那麼一定得學會觀察這兩個佇列是否存在溢位的情況。因為一旦出現因為連線佇列導致的握手問題，那麼 TCP 連線耗時都是秒級以上了。

對於半連線佇列， 有個簡單的辦法。那就是隻要保證 tcp_syncookies 這個核心引數是 1 就能保證不會有因為半連線佇列滿而發生的丟包。

對於全連線佇列來說，可以透過 netstat -s 來觀察。netstat -s 可檢視到當前系統全連線佇列滿導致的丟包統計。但該數字記錄的是總丟包數，所以你需要再借助 watch 命令動態監控。

如果輸出的數字在你監控的過程中變了，那說明當前伺服器有因為全連線佇列滿而產生的丟包。你就需要加大你的全連線佇列的⻓度了。全連線佇列是應用程式呼叫 listen時傳入的 backlog 以及核心引數 net.core.somaxconn 二者之中較小的那個。如果需要加大，可能兩個引數都需要改。

如果你手頭並沒有伺服器的許可權，只是發現自己的客戶端機連線某個 server 出現耗時長，想定位一下是否是因為握手佇列的問題。那也有間接的辦法，可以 tcpdump 抓包檢視是否有 SYN 的 TCP Retransmission。如果有偶發的 TCP Retransmission， 那就說明對應的服務端連線佇列可能有問題了。

建議13：減少握手重試

在 6.5 節我們看到如果握手發生異常，客戶端或者服務端就會啟動超時重傳機制。這個超時重試的時間間隔是翻倍地增長的，1 秒、3 秒、7 秒、15 秒、31 秒、63 秒 ......。對於我們提供給使用者直接訪問的介面來說，重試第一次耗時 1 秒多已經是嚴重影響使用者體驗了。如果重試到第三次以後，很有可能某一個環節已經報錯返回 504 了。所以在這種應用場景下，維護這麼多的超時次數其實沒有任何意義。倒不如把他們設定的小一些，儘早放棄。 其中客戶端的 syn 重傳次數由 tcp_syn_retries 控制，伺服器半連線佇列中的超時次數是由 tcp_synack_retries 來控制。把它們兩個調成你想要的值。

建議14： 如果請求頻繁，請棄用短連線改用長連線

如果你的伺服器頻繁請求某個 server，比如 redis 快取。和建議 1 比起來，一個更好一點的方法是使用長連線。這樣的好處有

1） 節約了握手開銷 。短連線中每次請求都需要服務和快取之間進行握手，這樣每次都得讓使用者多等一個握手的時間開銷。

2） 規避了佇列滿的問題 。前面我們看到當全連線或者半連線佇列溢位的時候，伺服器直接丟包。而客戶端呢並不知情，所以傻傻地等 3 秒才會重試。要知道 tcp 本身並不是專門為網際網路服務設計的。這個 3 秒的超時對於網際網路使用者的體驗影響是致命的。

3） 埠數不容易出問題 。端連線中，在釋放連線的時候，客戶端使用的埠需要進入 TIME_WAIT 狀態，等待 2 MSL的時間才能釋放。所以如果連線頻繁，埠數量很容易不夠用。而長連線就固定使用那麼幾十上百個埠就夠用了。

建議15：TIME_WAIT 的最佳化

很多線上服務如果使用了短連線的情況下，就會出現大量的 TIME_WAIT。

首先，我想說的是沒有必要見到兩三萬個 TIME_WAIT 就恐慌的不行。從記憶體的⻆度來考慮，一條 TIME_WAIT 狀態的連線僅僅是 0.5 KB 的記憶體而已。從埠占用的角度來說，確實是消耗掉了一個埠。但假如你下次再連線的是不同的 Server 的話，該埠仍然可以使用。只有在所有 TIME_WAIT 都聚集在和一個 Server 的連線上的時候才會有問題。

那怎麼解決呢? 其實辦法有很多。第一個辦法是按上面建議開啟埠 reuse 和 recycle。  第二個辦法是限制 TIME_WAIT 狀態的連線的最大數量。

如果再徹底一些，也可以乾脆直接用⻓連線代替頻繁的短連線。連線頻率大大降低以後，自然也就沒有 TIME_WAIT 的問題了。
