# 一次系統呼叫 (System Call) 開銷到底有多大？

> 原文標題：一次系统调用开销到底有多大？

> 原文連結：https://mp.weixin.qq.com/s/2nIDLeMR984_Sdgh01BHIQ

---

相信各位同學都聽說過一個建議，就是系統呼叫比函式呼叫開銷大很多，要儘量減少系統呼叫的次數，以提高你的程式碼的效能。那麼問題來了，我們是否可以給出量化的指標。一次系統呼叫到底要多大的開銷，需要消耗掉多少 CPU 時間？

首先說說系統呼叫是什麼，當你的程式碼需要做 IO 操作（open、  `read`、`write`）、或者是進行記憶體 (Memory) 操作（mmpa、sbrk）、甚至是說要取得一個系統時間（gettimeofday），就需要透過系統呼叫來和核心進行互動。無論你的使用者程式是用什麼語言實作的，是 php、c、java 還是 go，只要你是建立在 Linux 核心 (Linux Kernel) 之上的，你就繞不開系統呼叫。

大家可以透過 `strace` 命令來檢視到你的程式正在執行哪些系統呼叫。例如我檢視了一個正在生產環境上執行的 nginx 當前所執行的系統呼叫，如下:


簡單介紹了下系統呼叫，那麼相信各位同學都聽說過一個建議，就是系統呼叫的開銷很大，要儘量減少系統呼叫的次數，以提高你的程式碼的效能。那麼問題來了，我們是否可以給出量化的指標。一次系統呼叫到底要多大的開銷，需要消耗掉多少 CPU 時間？好了，廢話不多說，我們直接進行一些測試，用資料來說話。

## 實驗 1

首先我對線上正在服務的 nginx 進行 `strace` 統計，可以看出系統呼叫的耗時大約分佈在 1-15us 左右。因此我們可以大致得出結論，系統呼叫的耗時大約是 1us 級別的，當然由於不同系統呼叫執行的操作不一樣，執行當時的環境不一樣，因此不同的時刻，不同的呼叫之間會存在耗時上的上下波動。

## 系統呼叫到底在做什麼？

## 先看看系統呼叫花費的 CPU 指令數

x86-64 CPU 有一個特權級別的概念。核心執行在最高階別，稱為 Ring0，使用者程式執行在 Ring3。正常情況下，使用者程序 (Process) 都是執行在 Ring3 級別的，但是磁碟 (Disk)、網路卡 (Network Card) 等外設只能在核心 Ring0 級別下來來存取。因此當我們使用者態程式需要存取磁碟等外設的時候，要透過系統呼叫進行這種特權級別的切換

對於普通的函式呼叫來說，一般只需要進行幾次暫存器操作，如果有參數或回傳函式的話，再進行幾次使用者堆疊操作而已。而且使用者堆疊早已經被 CPU cache 接住，也並不需要真正進行記憶體 IO。

但是對於系統呼叫來說，這個過程就要麻煩一些了。系統呼叫時需要從使用者態切換到核心態 (Kernel Mode)。由於核心態的堆疊用的是核心堆疊，因此還需要進行堆疊的切換。SS、ESP、EFLAGS、CS 和 EIP 暫存器全部都需要進行切換。

而且堆疊切換後還可能有一個隱性的問題，那就是 CPU 排程的指令和資料一定程度上破壞了區域性性原理，導致一二三級資料快取、TLB 頁表 (Page Table) 快取的命中率一定程度上有所下降。

除了上述堆疊和暫存器等環境的切換外，系統呼叫由於特權級別比較高，也還需要進行一系列的許可權校驗、有效性等檢查相關操作。所以系統呼叫的開銷相對函式呼叫來說要大的多。我們在 test02 的基礎上計算一下每個系統呼叫需要執行的 CPU 指令數。

## 再深挖系統呼叫的實作

如果非要扒到核心的實作上，我建議大家參考一下《深入理解 LINUX 核心-第十章系統呼叫》。最初系統呼叫是透過彙編指令 int（中斷）來實作的，當使用者態程序發出 int $0x80 指令時，CPU 切換到核心態並開始執行 `system_call` 函式。 只不過後來大家覺得系統呼叫實在是太慢了，因為 int 指令要執行一致性和安全性檢查。後來 Intel 又提供了「快速系統呼叫」的 sysenter 指令，我們驗證一下。

```
# perf stat -e syscalls:sys_enter_read ./main

 Performance counter stats for './main':

            1,000,001 syscalls:sys_enter_read

       0.006269041 seconds time elapsed
```

上述實驗證明，系統呼叫確實是透過   `sys_enter` 指令來進行的。

## 相關命令

- `strace -p $PID`: 實時統計程序陷入的系統呼叫
- `strace -cp $PID`: 對程序執行一段時間內的彙總，然後以排行榜的形式給出來，非常實用
- `perf list`: 列出所有可供 `perf` 取樣的事件
- `perf stat`: 統計 CPU 指令數、上下文切換 (Context Switch) 等指標
- `perf stat -e 事件`: 指定取樣事件進行統計
- `perftop`: 統計整個系統中消耗最多的函式或指令
- `perf top -e`: 同上，但可以指定取樣事件

## 結論

- 系統呼叫雖然使用了「快速系統呼叫」指令，但耗時仍大約在 200ns+，多的可能到十幾 us
- 每個系統呼叫核心要進行許多工作，大約需要執行 1000 條左右的 CPU 指令

> 系統呼叫確實開銷蠻大的，函式呼叫時 ns 級別的，系統呼叫直接上升到了百 ns，甚至是十幾 us，所以確實應該儘量減少系統呼叫。但是即使是 10us，仍然是 1ms 的百分之一，所以還沒到了談系統呼叫色變的程度，能理性認識到它的開銷既可。為什麼系統呼叫之間的耗時相差這麼多？因為系統呼叫花在核心態使用者態的切換上的時間是差不多的，但區別在於不同的系統呼叫當進入到核心態之後要處理的工作不同，呆在核心態裡的時候相差較大。
